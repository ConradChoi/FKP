## 1. 배경 (Background)

2026-06-12에 v0.1 랜딩페이지(`/en`, `/ja`)가 96% 완성도로 배포되었다. 3단계 접수폼 → Google Apps Script → Google Sheets + 운영자 이메일 알림 구조다.

그로부터 **2개월이 지난 지금(2026-08-24), 우리는 "리드가 몇 건 들어왔는지"를 신뢰할 수 있게 답하지 못한다.** 이것이 이번 v0.2의 출발점이다.

### 1.1 코드 확인 결과 (PRD 작성 중 실제 확인한 사실)

| # | 확인 내용 | 근거 파일 | 판단 |
|---|-----------|-----------|------|
| F-1 | 루트 `/` 를 처리하는 라우트가 **존재하지 않음**. `app/page.tsx` 없음, `middleware.ts` 없음. `public/index.html`(meta refresh → `/en`)만 존재하는데, Next.js는 `public/index.html`을 `/` 경로로 서빙하지 않는다(`/index.html`로만 접근 가능) | `app/` 전체, `public/index.html` | **R4는 "가능성"이 아니라 거의 확정.** 정적 export 시절엔 동작했으나 SSR 전환으로 깨졌을 개연성이 매우 높음 → Phase 0 최우선 |
| F-2 | `submitRequest`가 `fetch` 응답을 확인하지 않고 무조건 `{ success: true }` 반환 | `lib/forms/submitRequest.ts:16-21` | **R2 확정.** Apps Script가 죽어 있어도 사용자는 "성공" 화면을 본다 |
| F-3 | `trackEvent('form_submit')`은 `result.success`가 true일 때만 발동하는데, F-2로 인해 **항상 true** → GA4 전환수는 "제출 시도 수"이지 "성공 수"가 아님 | `components/RequestForm/RequestForm.tsx:101` | **계측 수치가 구조적으로 부풀려짐.** 데이터 신뢰 불가 |
| F-4 | `trackEvent`는 `window.gtag`가 정의된 경우에만 동작. `gtag`는 `NEXT_PUBLIC_GA_ID`가 있을 때만 주입됨. 6월 리포트 기준 GA_ID는 **미발급 상태로 마감** | `lib/analytics.ts:9`, `app/[locale]/layout.tsx:77-89` | **R3 확정.** GA_ID가 아직 비어 있다면 2개월간 모든 이벤트가 조용히 버려졌다 |
| F-5 | 개인정보 처리방침 페이지, 동의 체크박스, 보관기간 정책이 코드/문서 어디에도 없음. 폼은 이메일(연락처) + 회사정보를 수집 중 | `components/RequestForm/Step3.tsx`, `components/Footer.tsx` | **R1 확정.** 일본(APPI)·EU(GDPR)·한국(PIPA) 방문자 대상 노출 |
| F-6 | 런타임 의존성이 `next`/`react`/`react-dom` 3개뿐. v0.1 제약이 "외부 의존성 최소화, UI 라이브러리 금지" | `package.json` | Supabase 도입은 **첫 런타임 의존성 추가** → 명시적 제약 예외 결정 필요 (§7 TV-6) |
| F-7 | `Locale = 'en' | 'ja'` 하드코딩. `Dictionary.header.languageSwitcher`도 `{ en, ja }` 고정 | `lib/i18n/types.ts:2,34-37` | ko/zh 추가는 타입·사전·`alternates.languages`·`sitemap.ts`·`LanguageSwitcher` 동시 변경 필요 |

> **PM 판단**: R1~R4는 "이번 로드맵에 반영할지 검토"가 아니라 **전부 반영해야 한다.** 다만 별도 과제로 세우지 않고, 승인된 4대 변경 안에 자연스럽게 흡수시킨다(§4.5). 유일한 예외는 R4로, 이건 지금 당장 유입이 0일 수 있으므로 Phase 0에서 단독으로 먼저 막는다.

## 3. 목표 및 성공 지표 (Goals & Metrics)

### 3.1 북극성 지표 (North Star)

> **월간 유효 리드 수 (Qualified Leads / Month)**
> 정의: Supabase `requests` 테이블에 적재되고, 스팸/테스트/중복이 아니며, 연락 가능한 연락처를 포함한 요청 건수.

v0.1의 지표는 "GA4 form_submit 이벤트 수"였는데, F-3/F-4로 인해 이 숫자는 신뢰할 수 없다. **v0.2부터 북극성 지표의 단일 진실 공급원은 GA4가 아니라 Supabase DB다.** GA4는 퍼널 분석 보조 도구로만 쓴다.

### 3.2 보조 지표 (Supporting Metrics)

| 지표 | 정의 | 목표 | 측정 시점 |
|------|------|------|-----------|
| 폼 제출 성공률 | DB 적재 성공 / 제출 시도 | ≥ 99% | Phase 1 이후 |
| 계측 신뢰도 갭 | \|GA4 form_submit − DB row\| / DB row | ≤ 5% | Phase 1 이후 |
| 루트 진입 성공률 | `/` 요청 중 2xx/3xx 비율 | 100% | Phase 0 직후 |
| 폼 시작률 | form_start / page_view | 베이스라인 측정 후 +50% | Phase 2 전후 비교 |
| 폼 완료율 | form_submit / form_start | 베이스라인 대비 하락 없음 | Phase 2 전후 비교 |
| 리드 최초 응답 시간(TTFR) | 접수 시각 → 운영자 첫 상태변경 | ≤ 24h | Phase 3 이후 |
| 언어별 리드 분포 | locale별 리드 비중 | ja/zh/ko 합계 ≥ 20% | Phase 4 이후 |
| 동의 획득률 | 동의 체크 제출 / 전체 제출 | 100% (동의 없으면 제출 불가) | Phase 1 이후 |

### 3.3 베이스라인 미확보 경고

위 목표치 중 "+50%", "≥20%" 등은 **현재 베이스라인이 없어 임의로 설정한 값**이다. Phase 0에서 계측이 복구되고 2주간 데이터가 쌓인 뒤 project-manager와 함께 재조정한다. 근거 없는 숫자를 그대로 KPI로 굳히지 않는다.

> **researcher 에이전트 검증 요청 대기 항목**: §7 TV-5(중국 본토 접속성), §8 OQ-6(ko 화면 타겟), 경쟁사 접수폼 배치 관행(E2 근거 보강).

## 4. 요구사항 (Requirements)

### 4.1 Epic 1 — 리드 적재 방식 Supabase 전환

**User Story (운영자)**
> FKP 운영자로서, 나는 접수된 모든 요청이 **누락 없이 구조화된 DB에 저장되고 실패 시 그 사실을 알 수 있기를** 원한다. 그래야 리드 수를 신뢰하고 사업 방향을 판단할 수 있다.

**User Story (방문자)**
> 요청을 제출하는 해외 기업 담당자로서, 나는 **제출이 실패했을 때 실패했다는 사실과 재시도 방법을 알기를** 원한다. 그래야 응답을 헛되이 기다리지 않는다.

**User Story (정보주체)**
> 개인정보를 제공하는 방문자로서, 나는 **내 정보가 누구에게 어떤 목적으로 얼마나 보관되는지 알고 동의한 뒤 제출하기를** 원한다.

| ID | 요구사항 | 우선순위 |
|----|----------|:--------:|
| E1-R1 | 폼 제출은 클라이언트 → **Next.js 서버 라우트(API Route/Server Action)** → Supabase 순으로 처리한다. 브라우저에서 Supabase에 직접 쓰지 않는다 | **Must** |
| E1-R2 | 서버는 성공/실패를 명확한 상태코드와 에러코드로 응답하고, 클라이언트는 응답을 **반드시 검증**한다 (F-2 근본 해결) | **Must** |
| E1-R3 | 서버측 재검증: 필수값, 이메일 형식, 허용 enum 값(category/budget/timeline 등), honeypot, 길이 상한 | **Must** |
| E1-R4 | 저장 스키마에 **동의 관련 컬럼**을 포함한다: `privacy_consent(bool)`, `consent_version(text)`, `consented_at(timestamptz)` (R1 흡수) | **Must** |
| E1-R5 | 저장 스키마에 **운영 컬럼**을 포함한다: `status`, `assignee_id`, `internal_note`, `source`, `locale`, `created_at`, `updated_at` (E3 요청관리의 전제) | **Must** |
| E1-R6 | 접수 시 운영자 알림 — §8 OQ-14 결정에 따라 **Phase 1에서는 보류**, Phase 3(Admin 인앱 알림 + 카카오 알림톡)에서 구현 | Deferred to Phase 3 |
| E1-R7 | 개인정보 처리방침 페이지(`/[locale]/privacy`)와 폼 내 **명시적 동의 체크박스**(기본 미체크, 미체크 시 제출 불가) | **Must** |
| E1-R8 | RLS(Row Level Security)를 켜고, anon 키로는 `requests` 테이블 읽기/쓰기가 불가능해야 한다. 쓰기는 서버 전용 키로만 | **Must** |
| E1-R9 | 저장 실패 시 서버 로그에 페이로드를 남겨 **수동 복구 가능**하게 한다(개인정보 마스킹 규칙은 privacy-security-officer 확정) | **Should** |
| E1-R10 | 봇 방지 강화(rate limit 또는 Turnstile류). honeypot만으로는 서버 엔드포인트 공개 시 부족 | **Should** |
| E1-R11 | 기존 Apps Script 경로를 일정 기간 병행 적재(이중 쓰기)해 안전망 확보 | **Could** |
| E1-R12 | 6월 Google Sheets 데이터 이관 | **Won't** (대표 결정) |

### 4.2 Epic 2 — User 접수 UX 개선

**User Story**
> 랜딩에 처음 도착한 해외 기업 담당자로서, 나는 **스크롤을 끝까지 내리지 않아도 요청을 시작할 수 있기를** 원한다. 그래야 관심이 식기 전에 행동할 수 있다.

| ID | 요구사항 | 우선순위 |
|----|----------|:--------:|
| E2-R1 | Hero 영역에서 접수를 **시작**할 수 있어야 한다. 시작 지점은 최소 입력(예: "무엇을 찾으시나요" 1개 필드 또는 카테고리 선택)으로 진입 장벽을 낮춘다 | **Must** |
| E2-R2 | Home(Main)에 접수로 가는 **명시적 내비게이션 진입점**을 둔다(헤더 메뉴 또는 상시 노출 CTA) | **Must** |
| E2-R3 | Hero에서 입력한 값은 **손실 없이 후속 단계로 이어진다**(재입력 금지) | **Must** |
| E2-R4 | 기존 하단 3단계 폼과의 관계를 명확히 정의한다(대체 / 병존 / 연결). 동일 폼이 2개 존재해 리드가 중복 집계되는 상황을 만들지 않는다 | **Must** |
| E2-R5 | 퍼널 계측 이벤트를 세분화한다: `form_start`, `step_complete(step_no)`, `form_abandon`, `form_submit` | **Must** |
| E2-R6 | 모바일(375px)에서 Hero 폼이 헤드라인·CTA를 밀어내 첫 화면 메시지를 해치지 않아야 한다 | **Must** |
| E2-R7 | 접수 전용 페이지(`/[locale]/request`)를 두어 아웃리치 시 직접 링크 가능하게 한다 | **Should** |
| E2-R8 | A/B 테스트로 배치안을 검증 | **Could** (트래픽 규모상 유의미한 검정 어려움 — Phase 2에서는 전후 비교로 갈음) |
| E2-R9 | 구체적 화면 설계·카피·인터랙션 | **본 문서 범위 밖** → service-planner → ui-ux-designer → ux-writer |

> **PM 노트**: E2-R4가 이 Epic의 핵심 위험이다. "Hero에도 폼, 하단에도 폼"은 구현은 쉽지만 데이터가 오염되고 사용자가 혼란스러워진다. service-planner는 **단일 접수 플로우**를 전제로 설계할 것.

### 4.3 Epic 3 — Admin 콘솔 신규 구축

**User Story (운영자)**
> FKP 운영자로서, 나는 **접수된 요청을 목록에서 확인하고 상태를 바꾸고 메모를 남기기를** 원한다. 그래야 후속 리서치와 매칭을 놓치지 않는다.

**User Story (관리자)**
> FKP 관리자로서, 나는 **운영 인력을 초대하고 각자가 볼 수 있는 메뉴를 제어하기를** 원한다. 그래야 외부 인력이 합류해도 리드 개인정보 노출 범위를 통제할 수 있다.

**User Story (관리자 — 메뉴 동적 관리)**
> FKP 관리자로서, 나는 **새 메뉴가 생겨도 개발자 배포 없이 권한관리 화면에서 메뉴를 등록/숨김/정렬하고 역할별 접근을 지정하기를** 원한다.

| ID | 요구사항 | 우선순위 |
|----|----------|:--------:|
| E3-R1 | **인증**: Supabase Auth 기반 로그인/로그아웃/세션. 공개 회원가입은 **차단**(초대 전용) | **Must** |
| E3-R2 | **요청관리**: 리드 목록(검색/필터/정렬/페이지네이션), 상세, 상태 변경, 담당자 지정, 내부 메모 | **Must** |

#### 4.3.1 권한관리 데이터 모델 초안 (개념 수준)

> 상세 스키마·인덱스·제약·마이그레이션은 **backend-developer 담당**. 여기서는 개념과 불변 규칙만 정의한다.

**개체(Entity)**

| 개체 | 목적 | 핵심 개념 필드 |
|------|------|----------------|
| `admin_user` | 운영자 계정. Supabase Auth 사용자와 1:1 | auth 사용자 참조, 표시명, 상태(invited/active/suspended), 마지막 로그인 |
| `role` | 역할. 예: 최고관리자 / 운영자 / 조회전용 | 불변 코드(code), 표시명, 설명, 시스템역할 여부(is_system) |
| `admin_user_role` | 계정 ↔ 역할 매핑 (N:M) | user 참조, role 참조 |
| `menu` | 메뉴 트리. **UI 내비게이션의 단일 진실 공급원** | 불변 코드(code), 상위메뉴(parent, self-reference), 표시명, 경로(path), 아이콘, 정렬순서, 유형(group/page), 활성여부 |
| `role_menu_permission` | 역할 ↔ 메뉴 권한 매핑 | role 참조, menu 참조, 권한 플래그(read/create/update/delete/export) |
| `audit_log` | 감사 추적 | 행위자, 행위, 대상 테이블/ID, 변경 전후 요약, IP, User-Agent, 시각 |

**개념 관계**

```
admin_user ──N:M── role ──N:M── menu
   (admin_user_role)   (role_menu_permission: read/create/update/delete/export)

menu ──self-reference── menu   (parent_id, 2~3 depth 계층)
모든 권한 변경/개인정보 접근 ──▶ audit_log
```

**불변 규칙(Invariants)** — 이후 설계·구현에서 반드시 지켜야 할 제약

| # | 규칙 | 이유 |
|---|------|------|
| INV-1 | `menu.code`는 **불변**. 코드 내 권한 체크는 `path`가 아니라 `code`로 한다 | 메뉴 경로가 바뀌어도 권한이 깨지지 않게 |
| INV-2 | 메뉴 트리는 DB가 SSOT. 프론트는 로그인 후 "내 권한으로 접근 가능한 메뉴 트리"를 **API 1회 호출**로 받아 사이드바를 그린다 | 하드코딩 금지 요건(E3-R5) 충족 |
| INV-3 | 메뉴에서 숨겨졌다는 것은 **보안이 아니다.** 모든 서버 엔드포인트/RSC는 요청 시점에 권한을 독립 검증한다 | E3-R7. 클라이언트 신뢰 금지 |
| INV-4 | 권한 판정은 **명시적 허용(allow-list)** 방식. 매핑이 없으면 접근 불가 | 신규 메뉴 추가 시 의도치 않은 전체 공개 방지 |
| INV-5 | 다중 역할 보유 시 권한은 **합집합(union)** | 예측 가능한 단순 규칙 우선. 거부 우선(deny-override)은 v1 미도입 |
| INV-6 | 시스템 역할(최고관리자)은 삭제·권한박탈 불가. 활성 최고관리자 최소 1명 보장 | E3-R9 self-lockout 방지 |
| INV-7 | 권한 캐시는 짧게(세션 또는 수 분). 권한 회수가 지연 없이 반영되어야 함 | 퇴사·사고 대응 |
| INV-8 | Supabase RLS와 애플리케이션 권한 체크의 **이중 방어**. RLS만 믿거나 앱만 믿지 않는다 | 키 유출·경로 우회 대비 |

**초기 역할 세트(제안)**

| 역할 코드 | 접근 범위 | 비고 |
|-----------|-----------|------|
| `super_admin` | 전 메뉴 + 권한관리 + 내보내기 | 시스템 역할. 삭제 불가 |
| `operator` | 대시보드, 요청관리(read/update), 콘텐츠관리 | 내보내기 불가, 권한관리 접근 불가 |
| `viewer` | 대시보드, 요청관리(read only) | 개인정보 마스킹 여부는 privacy-security-officer 판단 |

### 4.4 Epic 4 — 국가별 자동 언어 설정

**User Story**
> 일본/중국/한국에서 접속한 방문자로서, 나는 **첫 화면부터 내 언어로 보기를** 원한다. 동시에, 내가 원하면 **언제든 다른 언어로 바꿀 수 있기를** 원한다.

| ID | 요구사항 | 우선순위 |
|----|----------|:--------:|
| E4-R1 | 접속 국가에 따라 기본 언어를 결정: KR→ko, CN→zh, JP→ja, 그 외→en | **Must** |
| E4-R2 | 자동 감지는 **기본값일 뿐**이다. User Header의 언어 선택으로 **항상 override 가능** | **Must** |

| E4-R4 | ko, zh locale 신규 추가 (타입·사전·언어전환 UI·hreflang·sitemap 동시 반영) | **Must** |

| E4-R7 | 검색엔진 크롤러가 국가 감지로 인해 특정 언어만 색인하게 되면 안 된다. hreflang alternates 정확히 유지 | **Must** |

| E4-R11 | 4개 언어 카피 품질 확보 | **본 문서 범위 밖** → ux-writer. 기계번역 그대로 배포 금지 |

> **PM 경고 2건**
> 1. **ko 화면의 타겟이 정의되지 않았다.** 현재 서비스 카피는 전부 "해외 기업 → 한국 파트너를 찾아드립니다" 방향이다. 한국에서 접속한 사람에게 이 메시지를 한국어로 보여주는 것은 **메시지-오디언스 불일치**다. 한국어 화면의 진짜 목적(한국 파트너사 유입? 국내 신뢰도?)이 정해지지 않으면 번역 작업이 낭비된다 → §8 OQ-6. **이것이 Phase 4를 Phase 3보다 뒤에 두지 않고 병렬로 둔 이유이자, 동시에 ko를 zh보다 뒤로 미룰 수도 있는 이유다.**
> 2. **중국(zh) 지원의 실효성 검증 필요.** GTM/GA4/Google Fonts(Inter)가 중국 본토에서 차단·지연될 수 있고, Supabase 접근성도 확인이 필요하다. 번역만 하고 페이지가 안 열리면 의미가 없다 → §7 TV-5.

### 5.2 RICE 순위를 그대로 실행 순서로 쓰지 않는 이유

RICE는 유용하지만 여기서는 **단독으로 신뢰할 수 없다.** 세 가지 이유를 명시한다.

1. **Reach의 단위가 다르다.** E3의 Reach는 "운영자 3명"이지만, 그 3명이 처리하는 것은 리드 전량이다. 내부 도구는 RICE의 Reach 정의와 근본적으로 맞지 않는다.
2. **의존성을 표현하지 못한다.** E3 요청관리는 E1(Supabase 적재)이 없으면 **조회할 데이터 자체가 존재하지 않는다.** RICE 1.8이라고 마지막에 해도 되는 게 아니라, 애초에 E1 없이는 시작조차 불가능하다.
3. **깨진 양동이 문제.** E2(RICE 1위)로 폼 진입을 늘려도, R2(제출 실패 은폐)와 R3(계측 끊김)이 남아 있으면 **늘어난 리드가 새는지 담기는지 알 수 없다.** 물을 더 붓기 전에 양동이를 고쳐야 한다.

### 5.3 최종 실행 순서 결정 근거

| 결정 | 근거 |
|------|------|
| Phase 0을 모든 것 앞에 | R4가 사실이면 현재 유입 0. 수정 비용은 극히 낮고 손실은 100%. 기대값 압도적 |
| E1을 E2보다 먼저 | ① 양동이 먼저 수리(§5.2-3) ② E2는 폼 구조를 바꾸는데 E1은 폼 제출 경로를 바꾼다 — **같은 코드를 두 번 건드리면 재작업 발생.** 백엔드 계약 확정 → 프론트 UX 개편 순서가 총 공수가 적다 |
| E2를 E3보다 먼저 | E2는 저비용·고임팩트(RICE 1위)이고 매출에 직결. E3는 고비용이며 "리드가 충분히 들어올 때" 가치가 커진다. 리드가 월 5건인데 Admin부터 만드는 건 순서가 틀렸다 |

| 콘텐츠관리를 마지막 분리 | "콘텐츠"가 무엇인지 정의되지 않았다(OQ-1). 정의 없는 기능을 스케줄에 넣으면 스코프가 무한 확장된다 |

### Phase 3 — Admin 콘솔 MVP (E3 핵심)

**목적**: 쌓인 리드를 **실제로 처리할 수 있게** 하고, 운영 인력 확장의 안전한 기반을 만든다.
**규모**: L — **이번 로드맵에서 가장 큰 덩어리.** 하위 분할 필수.
**전제조건**: Phase 1 완료 (조회 대상 데이터가 존재해야 함)

**하위 분할 (권장 실행 순서)**

| # | 서브 Phase | 내용 | 비고 |
|---|-----------|------|------|
| 3-A | 인증 + 셸 | Supabase Auth 로그인, Admin 레이아웃, 세션/보호 라우트 | 공개 가입 차단 |
| 3-B | 권한 기반 | role / menu / role_menu_permission / admin_user_role 모델, 권한 판정 로직, 서버 강제 | **여기서 대충 하면 이후 전부 다시 만든다.** 대표 지시대로 처음부터 세밀 RBAC |
| 3-C | 요청관리 | 리드 목록/상세/상태/메모/담당자 | 운영자가 가장 먼저 필요로 하는 화면 |
| 3-D | 대시보드 | 핵심 지표 위젯 | 지표 정의(OQ-12) 선행 필요 |
| 3-E | 운영자관리 + 권한관리 화면 | 계정 초대/비활성화, 메뉴관리 UI, 메뉴권한 매트릭스 UI | 3-B의 데이터 모델을 화면으로 노출 |
| 3-F | 감사 로그 | 개인정보 접근/권한 변경 기록 | privacy-security-officer 요구사항 반영 |

> **왜 3-B(권한 기반)를 3-C(요청관리)보다 먼저 두는가**: 요청관리 화면을 먼저 만들면 권한 체크 없이 동작하는 화면이 생기고, 나중에 RBAC를 끼워 넣으며 모든 화면을 다시 손대게 된다. 대표가 "처음부터 메뉴 단위 세밀 RBAC"를 지시한 것과 같은 맥락이다. 다만 3-B가 길어져 운영자가 계속 Sheets를 쓰는 상황은 피해야 하므로, 3-B는 **모델 + 판정 로직까지만** 하고 관리 UI(3-E)는 뒤로 미룬다.

**완료 조건 (DoD)**
- [ ] 메뉴 트리가 DB에서 로드되며, 코드에 메뉴 배열이 하드코딩되어 있지 않음
- [ ] 권한 없는 역할로 로그인 시 **메뉴가 안 보이는 것뿐 아니라 URL 직접 입력으로도 접근 불가**함을 테스트로 증명
- [ ] 새 메뉴를 관리 화면에서 추가 → 역할에 부여 → 해당 계정에서 즉시 노출되는 시나리오 통과
- [ ] 최고관리자가 자신의 권한관리 접근권을 제거하려 하면 차단됨 (INV-6)
- [ ] 리드 개인정보 조회/내보내기가 감사 로그에 남음
- [ ] privacy-security-officer 점검 통과 (운영자 계정 + 리드 개인정보 접근 — CLAUDE.md 필수)
- [ ] qa-reviewer 리뷰 통과

**다음 투입 에이전트**
`service-planner`(Admin 정보구조·리드 상태 워크플로우 정의) → `privacy-security-officer`(권한 모델·접근통제·감사 요건 사전 검토) → `ui-ux-designer`(Admin 디자인 시스템 — 외부 UI 라이브러리 없이 Tailwind만으로 테이블/모달/폼 패턴 정의) → `backend-developer`(RBAC 모델 + API 계약) → `frontend-developer` → `qa-reviewer` → `privacy-security-officer`(배포 전 최종) → `project-manager`(3-A~3-F 일정 분할)
