| 질문 | 답 |
|------|-----|
| 기술적으로 가능한가? | **가능하다.** 데이터 모델(TR-1/TR-2)이 애초에 이걸 염두에 두고 설계돼 있다 |

## 1. 배경 — 이미 확정돼 있는 것

PRD §3.2.4가 정한 4개 조항의 현재 상태:

| ID | 조항 요약 | 실제 구현 상태 |
|----|-----------|----------------|
| TR-1 | 자유서술은 **원문 + `original_locale`** 저장이 Source of Truth | **지켜짐** (단, 컬럼명은 `original_locale`이 아니라 필드별 접미사 방식 — 아래 §2.3) |
| TR-2 | 번역문은 **별도 레코드**로, `translation_source`(human/ai) + `source_synced_at` 추적. "기존 `content_translation` 패턴 재사용" | **부분 구현 — 중대한 갭 있음** (§2 참조) |
| TR-3 | **매칭 판단은 번역문이 아니라 구조화 필드로.** 자유서술은 운영자 참고용 | 지켜짐 (매칭 필터가 카테고리/국가/언어 기반 — M-R1) |
| TR-4 | **v1.0에서 자동 번역 파이프라인 안 만든다.** 운영자 수동 en 요약으로 충분 | 지켜짐 (재검토 시점: §5 L633이 **"P5 이후"** 로 이미 명시) |

> 즉 이번 요청은 완전히 새로운 제안이 아니라, **PRD가 이미 "P5 이후"로 예약해둔 항목을 지금 당길지**를 묻는 것이다. 그리고 PRD는 그 시점을 임의로 정한 게 아니라 **P5(파트너 공개 노출)가 곧 번역문의 소비처이기 때문에** 그렇게 정했다.

## 2. 검토 1 — `content_translation` 패턴은 실제로 어디에 있는가

### 2.1 실재한다 (TR-2의 "기존 패턴"은 허구가 아님)

`supabase/migrations/20260827100000_phase5_content_management_schema.sql`

- **`public.content_translation`** (L321~) — `content_item`(랜딩 카피/블로그/사례/FAQ)의 번역 레코드
  - `unique (content_item_id, locale)`, `locale in ('en','ja','ko','zh')`
  - `status in ('draft','translated','published')` — 수동 발행 워크플로 축
  - **`source_synced_at`** — 소스 로케일의 `updated_at`을 스탬프해 두고, 소스의 현재 `updated_at`과 비교해 **stale 여부를 플래그 없이 판정**하는 설계 (파일 헤더 L17~22에 의도가 명시돼 있음)
  - 쓰기는 RPC `public.upsert_content_translation(uuid, text, jsonb, text)` 경유 + `private.log_audit` 자동 기록 (L464~531)
- **`public.content_category_translation`** — 같은 패턴, RPC `upsert_category_translation`
- **`public.standard_category_translation`** (`20260829150000_standard_category_schema.sql` L130~) — SEEPN 표준 374노드용. 헤더 주석에 *"content_category_translation 패턴 reused verbatim"* 이라고 명시. `locale`은 `20260830100000_add_zh_locale_standard_category.sql`로 **zh까지 확장 완료**
- 운영 유틸: `lib/admin/translationStatus.ts` (stale 판정 로직), `lib/content/getPublishedContent.ts`, `lib/content/getLandingCopy.ts`

**판정: 패턴은 3개 테이블에 안정적으로 구현돼 있고, 자동번역 연동 시 그대로 확장 가능하다.** `source_synced_at` 기반 stale 판정은 자동번역 재실행 트리거로 **그대로 재사용 가능**하다(소스가 바뀌면 stale → 재번역 큐에 투입). 이 부분은 설계 부채가 없다.

### 2.2 그러나 — `translation_source` 컬럼은 **존재하지 않는다** (갭 1)

코드베이스 전체 검색 결과, `translation_source`는 **PRD 문서 L309 한 줄에만 등장하고 어떤 마이그레이션에도 없다.**

```
translation_source  →  docs/01-plan/features/seepn-unified-platform-v1.0.prd.md:309  (유일한 히트)
```

세 번역 테이블의 컬럼은 `locale / name|body / status / source_synced_at / updated_at / updated_by`뿐이다.

**이게 왜 중요한가**: `translation_source`는 TR-2가 정한 **"이 문장이 사람이 쓴 것인가 기계가 쓴 것인가"를 구분하는 유일한 장치**다. 이게 없는 상태로 자동번역을 넣으면:

- 운영자가 손본 문장을 다음 배치가 **말없이 덮어쓴다** (사람의 교정 노동이 소실된다)
- 화면에 "자동 번역됨" 고지를 띄울 근거 데이터가 없다 → 오역 시 면책 장치가 없다
- 사후에 "어디까지가 기계 번역이었나"를 감사할 수 없다

→ **자동번역 도입의 선행조건이며, 컬럼 1개 추가로 끝나는 작은 작업이다.** (권고: `translation_source text not null default 'human' check (in ('human','ai','ai_reviewed'))` — `ai_reviewed`는 기계 초벌을 사람이 검수 완료한 상태. 최종 스펙은 backend-developer가 확정)

### 2.3 파트너·요청 데이터에는 번역 레코드가 **아예 없다** (갭 2)

| 데이터 | 원문 저장 | 번역 레코드 |
|--------|-----------|-------------|
| 파트너 회사소개 `partner.company_intro_text` (≤5000자) | 있음 + `company_intro_locale` (`ko/en/ja/zh`) — **TR-1 충족** | **없음** |
| 파트너 `representative_offerings` (jsonb, 최대 3개) | 있음 | **없음** (jsonb 내부 문자열이라 번역 대상 경로 설계 필요) |
| 파트너 `certifications` (text[]) | 있음 | **없음** |
| FKP 요청 `requests.what_looking_for` (≤300자), `requests.description` (≤5000자) | 있음 | **없음.** `original_locale`에 해당하는 필드조차 없다 |
| 매칭 메모 `selection_memo`/`exclusion_memo`/`meeting_note` 등 4종 | 있음 | 없음 (번역 대상 아님 — §5 참조) |

근거: `20260829140000_partner_schema.sql` L110~116, `20260824120000_phase1_requests_pipeline.sql` L77·L87

**판정**: TR-1은 파트너 쪽에서 지켜졌지만 **TR-2의 "별도 번역 레코드"는 사용자 생성 콘텐츠(파트너/요청)에 대해 아직 하나도 구현되지 않았다.** 즉 자동번역을 붙이려면 API 연동 이전에 **`partner_translation` 성격의 테이블 신설 + RLS + RPC + Admin UI**가 먼저 필요하다. 이건 API 키를 꽂는 작업이 아니라 **P5급 스키마 작업**이다.

> **PM 노트**: 대표 질문의 전제("Google API를 쓸 수 있느냐")에 대한 정확한 답은 **"API 자체는 하루면 붙지만, 붙일 자리(번역 레코드 테이블)가 파트너·요청 데이터에는 아직 없다"** 이다. 작업량의 80%가 Google 쪽이 아니라 우리 쪽 스키마·화면이다.

## 3. 검토 2 — 범위별 우선순위

대표가 말한 4개 범위는 사용자·가치·리스크가 전부 다르다. **하나의 "자동번역 기능"으로 묶으면 안 된다.**

### 3.1 범위별 분해

| # | 범위 | 읽는 사람 | 원문→대상 | v1.0에 소비 화면이 있나? | 오역 리스크 |
|---|------|-----------|-----------|--------------------------|-------------|
| ① | FKP 요청사항 (`requests` 자유서술) | **운영자(한국어)** — 매칭 탭 | en/ja → ko | **있음** (Admin 리드 상세) | 낮음(내부 참고용) |
| ② | 파트너 입력정보 (회사소개·대표 제품/서비스) | **해외 바이어** | ko → en/ja/zh | **없음** (B-9/B-10 = Could/P5) | **높음**(대외 신뢰도) |
| ③ | 카테고리 (표준 374노드) | 바이어 + 파트너 | ko → en/ja/zh | 있음(파트너 앱 셀렉트) | 낮음(단어 수준) |
| ④ | "SEEPN 페이지 전체" | 방문자 | ko/en → ja/zh | 부분 | 중간(브랜드 카피) |

### 3.2 ④ "SEEPN 페이지 전체"는 범위가 뭉쳐 있어 분리가 필요하다

이 표현이 이번 검토에서 가장 위험한 부분이다. 실제로는 성격이 다른 3덩어리다:

| ④ 하위 범위 | 실제 위치 | 판정 |
|-------------|-----------|------|
| **④-a 정적 UI 문구** (버튼/라벨/네비/히어로 카피) | `lib/i18n/en.ts`, `lib/i18n/ja.ts` (파일 기반, 사람이 직접 작성) | **자동번역 대상 아님 (Won't).** 브랜드 카피는 마케팅 자산이지 번역 대상이 아니다. 이미 사람이 쓴 en/ja가 있고, 이걸 기계 번역으로 대체하면 **품질이 내려간다.** 신규 zh 사전이 필요해지면 그때 "기계 초벌 + 사람 검수" 1회성으로 |
| **④-b CMS 콘텐츠** (랜딩 카피/블로그/사례/FAQ) | `content_item` + `content_translation` | **Could.** 패턴이 이미 있어 기술 난도는 가장 낮다. 다만 블로그·사례는 **마케팅 문서라 기계 번역 그대로 발행하면 브랜드 손상.** `status='draft'`로만 채우고 사람이 발행하는 방식이면 유효 |
| **④-c 파트너 공개 프로필** | = ② 와 동일 | ②로 통합해 판단 |

> ④를 "SEEPN 페이지 전체"로 뭉뚱그려 승인하면 **④-a(사람이 쓴 브랜드 카피)까지 기계 번역으로 덮는 결정**이 섞여 들어온다. 이건 대표 의도가 아닐 것이다.

### 3.3 우선순위 스코어 (Impact / Effort)

Effort는 **Google API 연동이 아니라 "소비 화면 + 번역 레코드 스키마 + 검수 UI"까지 포함**한 값이다.

| # | 범위 | Impact (1-5) | Effort (1-5) | 점수 | 판정 |
|---|------|--------------|--------------|------|------|
| ② | 파트너 공개 프로필 (ko→en/ja/zh) | **5** — 해외 바이어에게 파트너를 이해시키는 핵심 자산. FKP의 존재 이유 | **4** — `partner_translation` 신설 + 검수 UI + **소비 화면(P5) 자체가 없음** | **1.25** | **P5와 동시 착수 (1단계)** |
| ① | FKP 요청 자유서술 (en/ja→ko) | 2 — 운영자 편의. **복사-붙여넣기 우회가 이미 존재**하고 운영자는 영어를 읽는다 | 2 — 저장 없이 온디맨드면 가벼움 | 1.00 | **Could (2단계)** |
| ④-b | CMS 콘텐츠 초벌 번역 | 2 — 콘텐츠 생산량이 아직 적다 | 1 — 패턴·RPC 완비, 컬럼 1개만 추가 | 2.00 | **Could (2단계, 가장 싼 실험)** |
| ③ | 카테고리 | 1 — **374노드 × ko/en/ja/zh 이미 완료.** 신규 노드 추가 시에만 발생(월 수 건) | 1 | 1.00 | **지금 불필요 (Won't now)** |
| ④-a | 정적 UI 문구 | 0 — 이미 사람이 쓴 en/ja 존재. 대체 시 **품질 하락** | — | — | **기존 en/ja 대체는 Won't (영구).** 단 신규 로케일 추가 시 기계 초벌+사람 검수 1회성 생성은 허용 (A-2 개정, 2026-09-07) |

**해석**:
- **가장 가치 큰 ②의 점수를 끌어내리는 건 Google API가 아니라 "소비 화면이 없다"는 사실**이다. 번역을 만들어도 v1.0에서는 아무도 못 본다.
- **④-b가 점수는 가장 높지만 Impact 자체가 낮다** — "싸니까 해볼 만한 실험"이지 사업 임팩트가 아니다. 여기에 4주 MVP의 주의력을 쓸 이유가 없다.
- **③은 이미 끝난 일이다.** 대표가 "카테고리"를 범위에 넣은 건 현황(374노드 4개 언어 번역 완료)이 공유되기 전이라 그럴 가능성이 높다. **단, 그 번역은 LLM이 수작업으로 한 1회성 결과이고 `translation_source` 컬럼이 없어 "사람이 한 것"과 구분되지 않는 상태**라는 점은 별개로 정리 대상(§2.2).

## 4. 검토 3 — 비용 추정

### 4.1 요금 체계 (2026-09 기준, 승인 시점 재확인 필요)

| 항목 | 요금 |
|------|------|
| **무료 구간** | **매월 첫 50만 자 무료** (모든 프로젝트 공통, 결제 계정 활성화 필요) |
| Basic (v2) NMT | **$20 / 100만 자** |
| Advanced (v3) NMT | **$20 / 100만 자** (동일). 글로서리·배치·문서번역 기능이 추가됨 |
| Translation LLM | 입력 $10 + 출력 $10 / 100만 자 (≈ NMT와 등가) |
| AutoML 커스텀 모델 / Adaptive | $80 / 100만 자 |

과금 단위: **대상 언어별 입력 문자 수**. 즉 1,000자를 en/ja/zh 3개 언어로 번역하면 **3,000자로 과금**된다. 공백 포함, HTML 태그 포함.

**Basic vs Advanced 판단**: 우리는 **Advanced(v3)** 를 권고한다. 요금이 동일한데 **글로서리(용어집)** 를 쓸 수 있기 때문이다. "나라장터", "표준 카테고리", 파트너 회사명·브랜드명·인증명 같은 **고유명사를 기계가 멋대로 의역하는 것을 막는 유일한 수단**이 글로서리이고, 이게 §5 품질 리스크의 핵심 완화책이다.

### 4.2 이 프로젝트 규모의 월 비용 추정

전제: 파트너 30~50곳, MVP 4주, 요청 유입 월 50~200건.

| 범위 | 소스 문자량 | 대상 언어 수 | 과금 문자 |
|------|-------------|--------------|-----------|
| ② 파트너 프로필 **최초 전량** (50곳 × 약 2,000자: 회사소개 + offerings 3개 + 인증) | 100,000 | 3 (en/ja/zh) | **300,000** (1회성) |
| ② 파트너 프로필 **월 갱신분** (월 30%가 수정된다고 가정) | 30,000 | 3 | **90,000 / 월** |
| ① FKP 요청 (월 200건 × 약 700자) | 140,000 | 1 (ko) | **140,000 / 월** |
| ③ 카테고리 신규 노드 (월 10노드 × 15자) | 150 | 3 | **450 / 월** |
| ④-a 정적 UI 1회 zh 추가 (`en.ts` 약 238행 ≈ 1만 자 수준) | 10,000 | 1 | **10,000** (1회성) |
| ④-b CMS 콘텐츠 (월 5건 × 3,000자) | 15,000 | 3 | **45,000 / 월** |

- **전 범위 동시 도입 시 정상 상태 월 과금 문자: 약 275,000자 → 무료 구간(50만 자) 이내 → 월 $0**
- **최초 마이그레이션이 겹치는 첫 달: 약 585,000자 → 초과분 85,000자 → 약 $1.7**
- **트래픽이 10배로 늘어도**: 약 2.75M자 → (2.75M − 0.5M) × $20/M ≈ **월 $45**

> **결론: 비용은 이 의사결정의 변수가 아니다.** 월 $0~2다. 따라서 **"비싸서 안 한다"는 논리를 쓰면 안 되고**, 반대로 **"싸니까 전부 켜자"는 논리도 위험하다.** 실제 비용은 요금이 아니라 **오역 검수에 드는 운영자 시간**과 **개인정보 국외이전 리스크**다. 파트너 50곳 × 3언어 = 150개 번역문을 사람이 훑는 데 드는 시간이 API 요금보다 몇 백 배 비싸다.

## 5. 검토 4 — 품질/오역 리스크

### 5.1 리스크의 크기는 "누가 읽는가"에 비례한다

| 대상 | 오역 시 결과 | 심각도 |
|------|--------------|--------|
| ② 파트너 회사소개·제품설명 | **해외 바이어가 파트너를 오해한다.** "당사는 OEM 생산은 하지 않습니다" → 부정어 누락 시 정반대 의미. 파트너 입장에서는 **자기가 쓰지도 않은 문장 때문에 거래 기회를 잃는다** → 플랫폼 신뢰 붕괴 + 파트너 이탈 | **높음** |
| ② 인증·규격명 (`certifications`) | "ISO 9001", "KC 인증" 같은 고유명사 오역 → **허위 표시로 오인될 소지**. 인증 관련 오역은 단순 품질 문제가 아니라 **법적 표시 문제**가 될 수 있다 | **높음** |
| ① 요청 자유서술 | 운영자가 잘못 이해 → 매칭 품질 저하. 단 **운영자가 원문을 함께 볼 수 있으면 회복 가능** | 중간 |
| ③ 카테고리 | 단어 수준, 이미 사람이 검수 | 낮음 |
| ④-a 브랜드 카피 | 어색한 문장이 랜딩 첫 화면에 노출 | 중간 |

### 5.2 TR-3 방어선은 **반드시 유지되어야 한다**

TR-3("매칭 판단은 번역문이 아니라 구조화 필드로 한다")은 원래 **번역 품질 편차로부터 매칭 로직을 격리**하려고 친 방어선이다. 자동번역을 도입하면 이 방어선의 **중요도가 올라간다** — 기계 번역문이 대량으로 생기면 "그걸로 검색·매칭하면 편하지 않나"는 압력이 반드시 생기기 때문이다.

**권고: TR-3을 유지하고, 자동번역 도입 시 오히려 강화해 명시한다.**

> **TR-3′ (제안)**: 매칭 후보 탐색·필터·정렬은 구조화 필드(카테고리/국가/언어/MOQ/인증)로만 수행한다. **`translation_source`가 `'ai'` 또는 `'ai_reviewed'`인 텍스트는 검색 인덱스·매칭 근거·대외 계약 문서에 사용하지 않는다**(승인본 기준 — 로케일·콘텐츠 종류와 무관하게 항상 적용). 운영자 참고 및 바이어 열람 보조 용도로만 노출하며, 노출 시 기계 번역임을 고지한다.

### 5.3 필수 완화 장치 (도입 시)

| ID | 장치 | 이유 |
|----|------|------|
| Q-1 | **`translation_source` 컬럼 신설** (§2.2) | 사람 교정분을 기계가 덮어쓰는 사고 방지. 모든 나머지 장치의 전제 |
| Q-2 | **원문 병기 + "자동 번역됨" 고지 UI** | 바이어가 이상하다고 느끼면 원문을 확인할 수 있어야 한다. 법적 면책의 최소선 |
| Q-3 | **파트너 본인 검수·수정 경로** | 자기 회사 소개문이다. **파트너가 자기 번역문을 고칠 수 있어야 한다**(고치면 `ai_reviewed`/`human`으로 승격). 이게 없으면 파트너가 통제 못 하는 문장이 자기 이름으로 공개된다 |
| Q-4 | **Advanced 글로서리 등록** (회사명/브랜드/인증명/카테고리 표준어) | 고유명사 오역 차단 |
| Q-5 | **`ai` 상태 번역문은 `status='published'`로 자동 승격 금지** | 사람이 발행 버튼을 누르는 축(`status`)과 번역 출처 축(`translation_source`)을 직교로 유지 — 기존 `content_translation` 설계 철학과 일치 |
| Q-6 | **인증·규격·법적 표시 필드는 자동번역 제외** | §5.1. 원문 그대로 노출하거나 사람이 번역 |

## 6. 검토 5 — 개인정보 예비 체크 (**정식 판단 아님**)

> **이 절은 예비 확인이며, privacy-security-officer의 정식 검토를 대체하지 않는다.** 도입이 승인될 경우 **착수 전 정식 검토가 반드시 선행되어야 한다.**

### 6.1 짚어야 할 사실관계

1. **자유서술 필드에 PII가 섞여 들어오는 것은 이미 확인된 사실이다.**
   [`partner-signup-privacy-review.md`](../../03-security/partner-signup-privacy-review.md)의 **PR-14("자유서술 필드 PII 유입")** 가 이를 "통제 불가능한 개인정보 유입 경로"로 규정했고, [`human-matching-privacy-review.md`](../../03-security/human-matching-privacy-review.md) L166이 이를 승계하며 *"'김OO 대리와 통화, 다음 주 재연락' 같은 기재는 실무에서 반드시 발생한다"* 고 명시했다.
   → 즉 **회사소개·요청 설명·메모에 담당자 실명이나 제3자 정보가 들어 있을 가능성을 "없다"고 가정할 수 없다.**

2. **`requests.description`(≤5000자)과 `requests.what_looking_for`는 바이어가 자유롭게 쓰는 필드**이고, 같은 테이블에 `contact`(이메일)가 함께 있다. 본문 안에 연락처·담당자명이 재기재될 개연성이 있다.

3. **API 호출은 텍스트를 Google(해외 사업자)에게 전송하는 행위**다.

### 6.2 예비 쟁점 (정식 판단은 privacy-security-officer)

| 쟁점 | 예비 견해 (확정 아님) |
|------|----------------------|
| **국외 이전에 해당하는가** | 개인정보가 포함된 텍스트를 국외 사업자의 API로 전송·처리하게 하는 것이므로, **개인정보 처리위탁 겸 국외 이전에 해당할 가능성이 높다**고 본다. "번역만 하고 저장 안 한다"는 것은 이전 여부가 아니라 보유기간의 문제다 |
| **처리방침 반영 필요성** | 필요할 가능성이 높다. 수탁자(Google LLC 등)·이전 국가·이전 항목·이전 목적·보유기간의 **공개 또는 고지**가 요구될 수 있다 |
| **동의 근거** | 파트너 정보는 SS-9(공개 동의) 흐름에 **"번역 후 공개"** 를 포함시키는 방식이 자연스러워 보인다. 반면 **바이어 요청(①)은 기존 동의문에 번역 위탁이 들어 있지 않을 가능성**이 있어 더 까다롭다 |
| **기존 문서 부재 이슈와의 충돌** | PRD **PR-3**이 *"파트너 대상 이용약관 + 개인정보 처리방침이 현재 없다 → 신규 작성 필요(P1 차단 요소)"* 라고 이미 표시해 뒀다. **번역 위탁 조항은 그 신규 문서에 처음부터 포함시키는 것이 개정 비용이 가장 싸다** |
| **데이터 최소화** | 매칭 메모 4종(`selection_memo` 등)은 PR-14 유입 위험이 가장 높고 **내부 문서라 번역 필요가 없다** → **자동번역 대상에서 명시적으로 제외** 권고 |
| **Google 측 데이터 사용** | Cloud Translation은 일반적으로 고객 데이터를 모델 학습에 쓰지 않는다고 안내하나, **데이터 처리 약관(DPA)·리전 설정을 정식 검토에서 실제 문서로 확인**해야 한다 |

### 6.3 예비 권고

- **PSO-1**: 자동번역 착수 전 **privacy-security-officer 정식 검토 필수** (본 문서는 예비 확인일 뿐)
- **PSO-2**: 검토 범위에 ①(바이어 요청) 포함 시 **동의·고지 난도가 ②보다 높다**는 점을 전제로 판단 요청
- **PSO-3**: 매칭 메모 4종은 **범위에서 선제적으로 제외**
- **PSO-4**: PR-3의 신규 파트너 약관·처리방침 작성 시 **번역 위탁/국외이전 조항을 처음부터 포함**할지 판단 요청 (사후 개정보다 저렴)

## 8. 결론 — TR-4를 지금 개정할 것인가

### 8.1 권고: **전면 개정하지 않는다. 조건부 조항으로 개정한다.**

**TR-4를 지금 폐기하고 자동번역을 v1.0에 넣는 것에 반대한다.** 근거:

1. **소비자 부재가 결정적이다.** ②(최고 가치)의 소비 화면 B-9/B-10은 PRD에서 **Could / P5**이고, P5는 MVP 명시 제외(L576)다. **아무도 못 보는 번역문을 4주 MVP 기간에 만드는 것은 정의상 낭비다.**
2. **작업량의 대부분이 Google 쪽이 아니다.** 파트너·요청 데이터에는 번역 레코드 테이블 자체가 없다(§2.3). "API만 붙이면 된다"는 인식은 사실과 다르다.
3. **비용이 싸다는 것이 지금 해야 할 이유가 되지 못한다.** 월 $0~2다. **싸기 때문에 늦게 시작해도 손해가 없다.** 반대로 지금 넣으면 4주 MVP의 검증 목표(매칭 워크플로)에서 주의력을 뺏는다.
4. **법적 선결 조건이 미해소다.** PR-14 유입 경로 + 국외 이전 쟁점 + PR-3(파트너 약관 부재, 이미 P1 차단 요소)가 겹쳐 있다.

### 8.2 그러나 **"아무것도 안 한다"도 아니다** — TR-4 개정안

> ⚠️ **이 TR-4′ 중간안은 폐기되었다.** ceo-advisor 검토 결과 **TR-4″**(원문 작성자 기준 이원화)로 대체 확정 — 2026-09-07. 현재 유효한 조항은 PRD §3.2.4의 TR-4″다. 아래는 논의 이력으로만 보존한다.

> **TR-4′ (개정 제안 — 폐기, 이력 보존용)**
> v1.0 MVP 기간에는 자동 번역 파이프라인을 **구축하지 않는다.** 다만 **P5(SEEPN 파트너 공개 노출) 착수 시 파트너 공개 프로필(회사소개·대표 제품/서비스)에 한해 Google Cloud Translation Advanced를 도입한다**(§7 1단계). 그 전까지 v1.0 기간에는 **선행조건만 해소**한다: ①`translation_source` 컬럼 신설, ②privacy-security-officer 국외이전 정식 검토, ③TR-3′ 확정. 정적 UI 문구·매칭 메모·인증 표시 필드는 **영구 제외**한다.

이 개정의 효과: 대표 요구("전체 범위 자동번역")를 **거절하는 것이 아니라 순서를 정하는 것**이다. 실행 시점이 명확해지고("P5"), 그때 바로 착수할 수 있도록 지금 자물쇠를 푼다.

### 8.3 승인 요청 — **ceo-advisor 승인 필요**

**TR-4는 PRD §3.2.4에 확정 문서화된 조항이고, §5 Out of Scope에도 등재(L633)되어 있다. 이를 개정하려면 ceo-advisor 승인이 필요하다.** CLAUDE.md 운영 원칙("방향이 애매한 결정은 ceo-advisor에게 승인을 받는다")에 따른다.

> **승인 결과 (2026-09-07, ceo-advisor)**: A-1은 **TR-4′가 아니라 TR-4″(원문 작성자 기준 이원화)로 확정**, A-2는 **문구 수정 후 승인**, A-3·A-4·A-5는 **원안 승인**. 확정 조항은 PRD §3.2.4에 반영됨.

| 승인 항목 | 내용 | 승인 결과 |
|-----------|------|-----------|
| **A-1** | ~~TR-4 → TR-4′ 개정 (§8.2). "v1.0 전면 도입" 요구를 "P5 시점 파트너 프로필 한정 도입"으로 축소~~ | **수정 승인 → TR-4″**. 운영자 작성 콘텐츠는 v1.0 중 Admin 온디맨드 초벌 허용, 사용자 생성 콘텐츠만 P5까지 유보 |
| **A-2** | ~~④-a 정적 UI 문구~~ + 매칭 메모 4종 + 인증/규격/법적 표시 필드의 **영구 제외** | **문구 수정 후 승인**. 매칭 메모·인증 필드는 영구 제외 유지. 정적 UI 문구는 **"사람이 작성한 번역문의 기계 대체 금지"** 로 재정의하고, **신규 로케일 추가 시 기계 초벌 + 사람 검수 1회성 생성은 허용** |
| **A-3** | TR-3 → TR-3′ 강화 (`ai` 번역문을 매칭·검색 근거로 쓰지 않음, §5.2) | **원안 승인** (즉시 적용). `ai_reviewed`도 동일하게 금지 대상에 포함 |
| **A-4** | 0단계(§7) 4개 항목의 v1.0 기간 중 실행 승인 (XS~S 규모) | **원안 승인**. 단 `translation_source`는 human/ai 2값이 아니라 **human/ai/ai_reviewed 3값 enum**으로 신설 (TR-2′) |
| **A-5** | Advanced(v3) + 글로서리 채택 (Basic 대비 추가 비용 없음, §4.1) | **원안 승인** |

~~**대표에게 확인이 필요한 사항**~~ → **확인 완료(2026-09-07)**: "SEEPN 페이지 등 전체 범위"에 ④-a(사람이 이미 번역해 둔 정적 UI/브랜드 카피) 기계 대체는 **포함되지 않는다**. 대표의 실제 의도는 **"사용자가 자기 언어로 입력한 콘텐츠를 운영자가 수작업으로 다시 번역 등록하는 부담을 없애는 것"** 이었고, 이에 따라 완화 범위가 TR-4″(1) 운영자 작성 콘텐츠로 한정됐다.
