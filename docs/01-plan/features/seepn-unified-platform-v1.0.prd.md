## 1. 제품 정의 / North Star

### 1.1 한 문장 정의

> **SEEPN은 해외·국내 바이어가 "한국에서 누구와 일해야 하는지"를 가장 빠르게 알아내는 Korea Partner Intelligence Platform이다.**
> `findkoreanpartners.com`은 해외 바이어가 요구사항을 남기는 채널이고, `seepn.me`는 한국 파트너의 역량이 등록·노출되는 플랫폼이며, **둘은 하나의 Supabase Core DB를 공유한다.**

### 1.2 대표 확정 사항 (재논의 대상 아님 — 본 PRD의 전제)

| # | 확정 사항 | 본 PRD에 미치는 영향 |
|---|-----------|---------------------|
| D-1 | **Core DB = FKP Supabase 1개.** SEEPN Firebase 코드/데이터 이관 없음(금일 삭제 예정) | 신규 Entity는 전부 Supabase. SEEPN 데이터 마이그레이션 기능은 **범위 밖** |
| D-2 | **FKP = 해외 바이어 전용 인테이크 채널** (3단계 Request Flow, en/ja, 현행 유지) | Buyer 측 신규 기능은 최소화. §3.1 |
| D-3 | **SEEPN = 마스터 브랜드**, 국내+해외 바이어 포괄. FKP 니즈 ↔ Korean Partner 매칭 | SEEPN Web은 v1.0에서 **파트너 인입/노출** 역할부터. §3.2 |
| D-4 | **Supplier 자가등록(계정 생성 + 프로필 관리)을 1단계(P1/MVP) 범위에 포함한다.** — 2026-08-28 대표 확정(OQ-2) | PM의 "경량폼 우선" 권고를 **대표가 반려**. §3.2.1 전면 개정, 로드맵에서 P1으로 승격 |
| D-5 | **신규 Admin 기능은 기존 FKP 메뉴관리(동적 메뉴 트리 + RBAC) 위에 메뉴 추가.** 1차는 "공급사 관리", "표준 카테고리 관리" 2개만 | §3.3. 별도 Admin 앱 신설 금지 |
| D-6 | **파트너 데이터는 파트너 본인의 자가등록을 기본 경로로 한다.** 오프라인 인력의 역할은 대행 입력이 아니라 **가입 권유·초대 아웃리치**로 재정의 — 2026-08-28 대표 확정(OQ-4) | 대행 입력(`admin_entry`)은 폐기가 아니라 **예외 경로로 격하**. §3.2.3 개정 |
| D-7 | **Matching은 Phase 0(Human Matching)부터.** 후보/선정이유/제외이유/Meeting/Quote/Deal 기록 필수 | `/admin/leads`의 직계 확장으로 설계. §3.4 |
| D-8 | **AI 번역문을 Source of Truth로 저장하지 않는다.** 원문 보존 + 구조화 필드 + 로케일별 뷰 | 기존 `content_translation`의 `source_locale` + `source_synced_at` 패턴을 파트너 데이터에도 적용. §3.2.4 |
| D-9 | **MVP = 일본 × Vertical B(한국 서비스 파트너) 확정.** Vertical A(K-Beauty/Lifestyle)는 후순위 — 2026-08-28 대표 확정(OQ-1) | 스키마는 A/B 둘 다 수용하되 **B의 필드·카테고리·검증을 먼저 완성**. §3.2.2(C), §3.5 |
| D-10 | **보안 수준 유지.** RLS deny-by-default, Admin MFA(AAL2), RBAC, Consent, Audit log | 신규 파트너 테이블도 동일 패턴. privacy-security-officer 사전검토 대상 |
| **D-11** | **카테고리 체계 = SEEPN 표준 374노드 채택 + 누락 서비스 카테고리 신설.** 단 **FKP 바이어 화면에 노출할 카테고리는 관리자가 선택(curation)할 수 있어야 한다** — 2026-08-28 대표 확정(OQ-3) | §3.5 전면 개정. 카테고리 2레이어 구조 + `standard_category_management`에 노출 큐레이션 기능 추가 |

### 1.3 North Star & 지표

**북극성 지표 (v1.0)**

> **Match-to-Meeting Rate** = (Shortlist에 포함되어 실제 Meeting이 성사된 Match 수) / (운영자가 Shortlist로 확정한 Match 수)

**왜 이 지표인가**: v0.2의 북극성은 "월간 유효 리드 수"였다. 이건 *입구*만 측정한다. 통합 플랫폼의 핵심 가설은 "우리가 고른 Top 3가 실제로 만남으로 이어지는가"이고, 이것이 검증되지 않으면 AI 매칭·유료화·데이터 Moat 전부 무의미하다. 사업계획서 §7.3의 초기 North Star 후보와도 일치한다.

**단, v1.0 초기에는 표본이 10건 수준이므로 단독 판단 금지.** 아래 보조 지표를 함께 본다.

| 계층 | 지표 | 정의 | v1.0 목표 | 측정 가능 시점 |
|------|------|------|-----------|----------------|
| Acquisition | Qualified Request 수 | 스팸/테스트 제외, 연락 가능한 요청 | 4주 10건 | 기존 계측(v0.2)로 즉시 |
| Supply | Registered Partner 수 | Capability 필수항목 충족 파트너 | 4주 30~50곳 | P1 이후 |
| Supply | Capability Completeness | 필수+권장 항목 입력률 평균 | ≥ 70% | P1 이후 |
| Matching | **Time to Shortlist** | Request 접수 → Top 3 확정까지 경과시간 | ≤ 48h | P4 이후 |
| Matching | **Match-to-Meeting Rate** (NSM) | 위 정의 | 4주 내 Meeting 5건 | P4 이후 |
| Transaction | Meeting-to-Quote Rate | Quote/Proposal 발생 Match / Meeting 발생 Match | 4주 2~3건 | P4 이후 |
| Transaction | Deal Signal | Deal 가능성 기록된 Match 수 | 4주 1건 이상 | P4 이후 |
| Supply Quality | Partner Response Rate | 운영자 컨택에 응답한 파트너 비율 | 베이스라인 측정 | P4 이후 |

> **경고 (v0.2 §3.3과 동일한 이유)**: "30~50곳", "10건", "5건"은 사업계획서 §7.2 4주 실행안에서 가져온 값이며 **실측 베이스라인이 아니다.** P1~P4 완료 후 project-manager와 재조정한다. 특히 Match-to-Meeting Rate는 분모가 10 미만일 때 퍼센트로 말하지 않는다 — 건수로 보고한다.

## 2. 문제 정의 (Problem Statement)

기능 목록이 아니라 문제 목록에서 출발한다.

| # | 문제 | 누구의 문제 | 현재 상태의 손실 | 대응 |
|---|------|-------------|------------------|------|
| **P-1** | 바이어 요구사항(FKP `requests`)은 쌓이는데, **연결할 한국 파트너 데이터가 시스템에 0건**이다 | 운영자 | 리드가 들어와도 Concierge 리서치를 매번 맨땅에서 시작. Time to Shortlist 통제 불가 | E1 (파트너 데이터 모델 + Admin 입력) |
| **P-2** | 오프라인 인력이 발굴한 파트너 정보가 **개인 파일/메신저에 흩어진다** | 운영자 + 오프라인 인력 | 인력 이탈 시 데이터 증발. 중복 발굴. 매칭 근거 재현 불가 | E1 |
| **P-3** | 한국 파트너가 **자기 정보를 넣고 싶어도 넣을 데가 없다** | 한국 공급사 | 공급 측 Cold Start. 오프라인 인력 수집 속도가 곧 공급 상한 | E2 (파트너 신청폼) |
| **P-4** | 운영자가 Top 3를 골라도 **왜 골랐고 왜 뺐는지가 남지 않는다** | 운영자 + 향후 AI | Phase 1 Rule Matching / Phase 3 Outcome Learning의 **학습 데이터가 영영 생기지 않는다** | E3 (Human Matching) |
| **P-5** | Match 이후 Meeting/Quote/Deal이 **어디에도 기록되지 않는다** | 운영자 + 대표 | 북극성 지표를 계산할 수 없다. 사업 검증 자체가 불가 | E3 |
| **P-6** | FKP 카테고리는 5종, SEEPN 표준은 374노드. **두 체계가 서로 모른다** | 운영자 + 바이어 | Requirement와 Capability를 같은 축에서 비교할 수 없음 → 매칭의 1차 필터가 성립 안 함 | E4 (카테고리 통합) |
| **P-7** | 파트너 정보의 **신뢰도를 판단할 근거가 없다** (누가 검증했나? 응답은 하나?) | 바이어 + 운영자 | "우리가 검증했다"는 SEEPN의 핵심 약속을 지킬 수 없음 | E5 (인증/신뢰도, 단계적) |
| **P-8** | 파트너 정보는 한국어, 바이어는 영어/일본어. **같은 데이터의 언어가 다르다** | 양측 전부 | 매칭 근거가 번역 품질에 종속되면 D-8 원칙 위반 | E6 (원문+구조화 필드) |

> **PM 판단**: P-1과 P-4가 v1.0의 실질적 전부다. P-1은 "매칭할 재료가 없다", P-4는 "매칭한 결과가 안 남는다"이며, 이 둘만 풀어도 4주 Concierge MVP는 돌아간다. P-7(인증/신뢰도)은 **데이터가 쌓인 뒤의 문제**이므로 v1.0에서는 필드만 준비하고 로직은 미루는 것이 옳다.

## 3. 핵심 기능 정의 (Feature Definition)

### 3.0 Domain Model 용어 통일

통합개발 요구사항 §10을 따라 코드/문서/화면 전반에서 아래 용어를 고정한다.

| 용어 | 정의 | v1.0 시점의 물리적 위치 |
|------|------|------------------------|
| **Buyer** | 한국의 제품/서비스/파트너를 찾는 기업·담당자 | FKP 요청 제출자 (계정 없음) |
| **Buyer Requirement** | Buyer가 해결하려는 요구사항 | 현행 `public.requests` (**개명하지 않음** — §3.1.2) |
| **Korean Partner** | Requirement를 해결할 수 있는 한국 기업. Supplier보다 넓은 개념 | 신규 Partner Entity |
| **Capability** | Korean Partner가 제공 가능한 역량 | 신규 Capability Entity |
| **Match** | Requirement × Capability의 연결 (후보 포함) | 신규 Match Entity |
| **Match Outcome** | Match 이후 실제 진행 상태(열람/응답/미팅/견적/딜) | Match의 상태 이력 |

> **명칭 규칙**: 신규 화면·필드의 표시 문구는 한국어로 "**파트너**"를 쓴다. "공급사"는 대표 확정 D-5의 메뉴명("공급사 관리")에서만 유지하고, 그 외에는 Vertical B(서비스 파트너)를 배제하는 어감이 있으므로 쓰지 않는다. — **OQ-6**

#### 3.1.2 `requests` 테이블 처리 방침

통합요구사항 §4.3이 3개 선택지를 열어뒀다. **PM 권고: 1번(현행 `requests`를 Buyer Requirement의 v1으로 계속 사용)**.

| 대안 | 장점 | 단점 | 판정 |
|------|------|------|------|
| ① 현행 `requests` 유지 + 컬럼 확장 | 마이그레이션 0, RLS/RPC/Admin 화면 전부 그대로 동작, 4주 MVP에 즉시 착수 가능 | 이름이 도메인 용어와 불일치 | **권고** |
| ② `buyer_requirements` 신설 + 마이그레이션 | 이름이 깔끔 | Phase 1 RPC·RLS·Admin 화면·감사로그 전부 재작성. **MVP 검증 전에 지불하는 비용** | 기각(현 시점) |
| ③ 호환 View | 양쪽 장점 | 두 개의 진실. RLS를 View에 다시 설계해야 함 | 기각 |

> 개명은 **P8(정리 단계)** 또는 Monorepo 전환 시점에 ADR로 다시 다룬다. 지금 개명하면 "MVP 검증"이 아니라 "리팩터링"을 하게 된다.

#### 3.1.3 SEEPN 노출 시 Buyer 경험

D-3에 따라 SEEPN은 국내 바이어도 포괄한다. 다만 v1.0에서는:

| ID | 기능 | v1.0 |
|----|------|------|

#### 3.2.1 Partner 자가등록 — P1/MVP 범위로 확정 (D-4, D-6)

**2026-08-28 대표 결정**: PM이 제안했던 "P3 경량 신청폼 → P6 풀 계정"의 2단계 분리안을 **반려**하고, **풀 자가등록(계정 생성 + 프로필 직접 관리)을 1단계(P1/MVP)에서 진행**한다. 동시에 OQ-4에 대해 "웬만하면 파트너들이 **직접** 등록하도록 하겠다"고 확정했다.

**왜 경량 신청폼만으로는 부족한가 — PM 재분석**

| # | 경량 신청폼(로그인 없음)의 한계 | 왜 v1.0에서 치명적인가 |

| L-1 | 제출 후 **본인이 다시 볼 수 없다** | 자가등록이 기본 경로가 되면 오탈자·연락처 변경·카탈로그 교체를 전부 운영자가 대신 고쳐야 한다. 파트너 30곳에서도 운영 부하가 즉시 발생 |

#### 3.2.3 인테이크 경로 및 오프라인 인력의 역할 재정의 (D-6)

**2026-08-28 대표 결정으로 경로의 주종이 바뀌었다.**

| 경로 | 이전 위상 | **v1.0 확정 위상** |
|------|-----------|-------------------|
| `self_service` — 파트너 본인이 계정 만들고 직접 등록 | 미래(P6) | **기본 경로 (Primary)** |
| `admin_entry` — 운영자가 대신 입력 | 주 경로 | **예외 경로 (Exception)** — 파트너가 온라인 입력이 어려운 경우에 한해, 대면/유선 확인 하에 운영자가 대신 입력 |
| ~~`self_apply` — 익명 신청폼~~ | 보조 | **폐기** (§3.2.1) |

**오프라인 인력의 역할 재정의**

| 이전 정의 | **v1.0 확정 정의** |
|-----------|-------------------|
| 파트너 정보를 발굴·수집해 **Admin에 직접 입력** | 파트너를 발굴해 **가입을 권유·초대**하는 아웃리치. 데이터 입력은 파트너 본인이 한다 |

이 재정의의 효과: **동의 없이 수집된 PII를 시스템에 넣는 상황 자체가 설계상 발생하지 않는다.** OQ-4의 법적 리스크를 통제가 아니라 **회피**로 해결한다.

**데이터 모델 요건 (개정)**

| 요건 | 내용 |
|------|------|
| PC-1 | 모든 Partner 레코드는 `intake_source`를 가진다: `self_service`(기본) / `admin_entry`(예외). 예외 경로 비율을 지표로 모니터링한다 |
| PC-2 | `verification_state`: `draft` → `submitted` → `under_review` → `verified` / `rejected` / `suspended`. **자가등록이라고 자동 verified가 되지 않는다.** 운영자 검증은 그대로 유지 |
| PC-3 | `owner_account_id`: 이 레코드를 갱신할 권한을 가진 파트너 계정. `admin_entry`로 생성된 레코드는 owner가 비어 있으며, 나중에 파트너가 가입하면 **소유권 이전(claim)** 이 가능해야 한다 |
| PC-4 | 동일 사업자등록번호 중복 방지(SS-5). 자가등록분과 예외 입력분이 충돌하면 **자동 병합 금지**, Admin에 중복 후보로 노출하고 사람이 판단 |
| PC-5 | `referred_by`(가입을 권유한 오프라인 인력), `referred_at` 기록 — 아웃리치 성과 측정. **초대 링크/코드 방식이면 자동 귀속 가능** → service-planner 설계 대상 |
| PC-6 | **공개 노출은 파트너 본인의 명시적 동의(SS-9)를 전제로 한다.** `admin_entry` 예외 경로로 만들어진 레코드는 본인 동의 확보 전까지 **공개 노출 불가**(A1-R9 기본 off 유지) |
| PC-7 | `admin_entry` 사용 시 **동의 확보 근거를 기록**한다(대면/유선 확인 일시, 확인한 담당자). 예외 경로를 열어두되 감사 가능하게 만든다 |

> **PM 노트**: PC-6/PC-7이 이전 버전의 "가장 큰 법적 리스크"를 대체한다. 리스크가 사라진 것이 아니라 **예외 경로에만 국한**됐고, 그 예외에는 기록 의무가 붙었다. privacy-security-officer는 여전히 이 경로의 적법성(제3자 개인정보의 수집·이용 근거)을 검토해야 한다.

#### 3.2.4 다국어/번역 처리 (D-8)

| 요건 | 내용 |
|------|------|
| TR-1 | 자유서술 필드(회사소개, 제품설명, 레퍼런스)는 **원문 + `original_locale`** 을 저장한다. 이것이 Source of Truth |

| M-R4 | **선정 이유 기록**: 구조화 태그(다중) + 자유 메모. 태그 예: 카테고리 적합 / MOQ 충족 / 언어 대응 / 해외경험 / 인증 보유 / 가격대 적합 / 납기 적합 / 응답 이력 양호 | **Must** |
| M-R5 | **제외 이유 기록**: 구조화 태그(다중) + 자유 메모. 태그 예: MOQ 미달 / 카테고리 불일치 / 언어 미대응 / 응답 없음 / 가격 불일치 / 납기 불가 / 파트너 거절 / 중복 | **Must** |
| M-R6 | **Shortlist 확정**: Top 3 확정 액션. 확정 시각을 기록해 **Time to Shortlist를 자동 산출** | **Must** |
| M-R7 | **Outcome 상태 추적**: Match별로 `recommended` → `viewed` → `responded` → `meeting` → `quote` → `sample` → `negotiation` → `deal` → `repeat`. **단조 진행 강제 금지**(운영 현실상 건너뛰기 발생) + 각 전이 시각 기록 | **Must** |
| M-R8 | **Meeting / Quote / Deal 플래그 + 상세**: 미팅일자, 견적금액(선택·통화), 딜 여부/금액(선택) | **Must** |
| M-R9 | **Requirement 상태 연동**: Shortlist 확정 시 `requests.status`를 `matching` → `matched`로 자동 전이 제안(자동 변경 아님, 운영자 확인) | **Should** |
| M-R10 | 파트너에게 보낸 컨택 기록(채널/일시/응답여부) — Partner Response Rate의 소스 | **Should** |
| M-R11 | 매칭 활동 감사로그 (누가 누구를 왜 추천/제외했는지) | **Must** — PII 접근 포함 |
| M-R12 | 자동 점수 / AI 추천 / Match Score % 표시 | **Won't (v1.0)** — 통합요구사항 §12 "처음부터 AI 점수 92% 같은 숫자를 임의 생성하지 않는다" |
| M-R13 | 파트너에게 자동 알림 발송 | **Won't (v1.0)** — 운영자가 직접 연락. 알림은 P6 이후 |

#### 3.4.2 왜 M-R4/M-R5(이유 기록)가 Must인가

이것이 v1.0에서 **가장 저평가되기 쉬운 요구사항**이다. 화면상으로는 "메모칸 두 개"지만, 이 데이터가 없으면:

- Phase 1 Rule Matching의 규칙을 **무엇을 근거로** 만들 것인가? → 운영자의 기억
- Phase 3 Outcome Learning의 라벨은 무엇인가? → 없음
- "우리가 왜 이 회사를 추천했나"라는 바이어 질문에 답할 수 있는가? → 없음

사업계획서 §10.4가 말한 "AI 모델이 아니라 데이터가 Moat"의 실체가 바로 이 두 필드다. **자유 텍스트만 받으면 안 되고 구조화 태그를 반드시 함께 받아야 한다** — 자유 텍스트는 나중에 집계가 불가능하다.

#### 3.5.3 PM 권고: C안 (이중 계층 + 매핑), 단 조건부

**권고 이유**

1. **바이어와 파트너는 같은 정밀도를 원하지 않는다.** 바이어는 "K-Beauty 찾아요"라고 말하고, 파트너는 "스킨케어 > 앰플/세럼 > OEM"이라고 말한다. 하나의 체계로 둘 다 만족시키려는 시도는 대개 양쪽 다 불만족으로 끝난다. **Requirement는 거칠게, Capability는 정밀하게** 받고 매칭 시점에 운영자가 좁히는 것이 Phase 0 Human Matching의 본질에도 맞다.
2. **되돌리기 비용이 가장 낮다.** 매핑 테이블만 고치면 되고, 이미 적재된 `requests` 데이터를 건드리지 않는다.
3. **MVP 버티컬만 활성화하는 운영이 가능하다** (A2-R2). 374노드를 전부 켤 필요가 없다.

**단, 두 가지 조건**

- **조건 1**: 표준 374노드가 Vertical A(K-Beauty/Lifestyle)와 Vertical B(마케팅/IT/AI/콘텐츠/번역)를 실제로 커버하는지 검증되어야 한다. → **실측 완료(2026-08-29), 아래 참조.**
- **조건 2**: v1.0에서는 **매핑을 자동화하지 않는다.** 운영자가 Admin에서 수동 매핑한다. 자동 매핑(임베딩 등)은 AI 로드맵 영역.

> **실측 결과 (2026-08-29, `seepn_standard_categories_2.0.xlsx` 직접 파싱)**: L1 20개는 `비품/소모품, 사무/교육/가구, 정보통신, 시설/건물관리, 시설공사, 소방/안전/의료, 임대/리스, 전기/기계/설비, 물류관리, 마케팅/홍보, 전문용역서비스, 연구개발, 복지서비스, 출장서비스, 교육서비스, 인쇄/제작서비스, 보험서비스, 차량관리, 사무보조서비스, 생산관리`. 이 체계는 **나라장터(조달청 입찰) 기반의 국내 기업 조달/구매 관점 분류**임이 확인됐다.
>
> **Vertical B 커버리지 대조 (251행 전수 확인)**:
> - 마케팅/PR → `마케팅/홍보`(L2 12개/L3 24개)로 **충분히 커버**
> - AI 자동화 → `정보통신 > AI/빅데이터 서비스 > AI 서비스`로 **커버**
> - IT·웹·앱 개발 → `정보통신 > 시스템 개발`, `연구개발 > 개발 용역 서비스 > 소프트웨어 개발 용역`은 있으나 **"웹 개발"/"앱 개발"처럼 세분화된 노드가 없다** — 뭉뚱그려짐
> - **번역·로컬라이제이션 → 251행 전체에 "번역"이라는 단어가 단 한 번도 없다. 카테고리 자체가 존재하지 않는다.** FKP 현행 `content-media`에는 이미 "번역 및 현지화" 키워드가 있어 대비된다.
>
> **결론**: 조건 1은 **부분 충족**. C안(이중 계층 + 매핑)을 그대로 채택하되, **번역·로컬라이제이션 L3 신설이 P2의 필수 작업**이고, IT·웹·앱 개발도 L3 세분화(예: "웹/앱 개발", "시스템 통합")가 필요하다. A2-R8(신설 카테고리, 출처 표시)이 정확히 이 문제를 위한 요구사항이다. **대표도 2026-08-29 이 결과를 그대로 승인**했다("열어서 확인 후 적용 요청").

#### 3.5.5 FKP 노출 큐레이션 (D-11 상세)

**대표 확정(2026-08-29, OQ-3 답변)**: "FKP에 노출하고 싶은 카테고리는 선택할 수 있도록 기능이 필요합니다. 바이어들은 카테고리가 많으면 선택하기 어렵고, 아예 선택을 안 할 수도 있습니다."

**문제**: C안 채택으로 Capability 마스터가 374(+신설분, 약 380~390)노드가 된다. 이 전체를 FKP 요청 폼의 `<select>`(B-5)에 그대로 노출하면 **바이어 이탈**을 유발한다. 반대로 FKP 5종을 그대로 두면 Capability 마스터와 단절되어 P-6 문제가 재발한다.

**설계: 카테고리는 2개의 레이어를 가진다**

**메커니즘**

| ID | 요구사항 | 비고 |

| W4 | Meeting 5 / Quote 2~3 / Deal 1 | Outcome 추적 (M-R7, M-R8) + 대시보드 지표 | P4 |

**즉 MVP = P1 + P2 + P4 + (B-6, B-7 폼 필드 2개).** P3(신청폼)은 있으면 좋지만 4주 내 공급 확보는 오프라인 인력이 담당하므로 필수가 아니다.

**MVP에서 명시적으로 빼는 것**: SEEPN Web 신규 화면(P5), 파트너 계정(P6), 배지/신뢰도 지수(P7), 자동 매칭(P8), 알림, 파일 업로드 자동화, CSV 일괄등록.

### 7.3 ui-ux-designer 핸드오프 포인트

- Admin 신규 화면은 **기존 FKP Admin 디자인 시스템을 그대로 따른다**(신규 디자인 언어 도입 금지). 참고: `/admin/leads`, `/admin/permissions/menus`(트리 UI), `/admin/content`
- 카테고리 트리 UI는 **`/admin/permissions/menus`의 정렬순서 이동 패턴을 재사용**한다 (A2-R1)
- SEEPN Web(P5) 디자인은 **P5 착수 시점에 별도 진행** — v1.0 MVP 범위 밖

### 7.4 backend-developer 핸드오프 포인트

- **API 계약(요청/응답/에러)을 먼저 확정하고 frontend-developer와 공유**한 뒤 구현 (CLAUDE.md 원칙)
- 기존 패턴 승계 필수: RLS deny-by-default + `force row level security`, GRANT revoke, SECURITY DEFINER RPC 경유 write, `private` 스키마 분리(PII), `private.has_menu_permission()` 기반 권한 게이트, `private.log_audit()` 감사기록 — 근거: `supabase/migrations/20260824120000_phase1_requests_pipeline.sql`, `20260825120000_phase3_admin_rbac.sql`
- 신규 메뉴는 `public.menu` INSERT로 추가 (코드 하드코딩 금지)
- **스키마 제안서를 먼저 작성하고 승인 전 마이그레이션을 실행하지 않는다** (통합요구사항 §4.3)

### 7.5 project-manager 핸드오프
