# 공지사항(Notice) 게시판 — 기능 기획서 v3.0 (Final)

> **한 줄 요약**: 공지사항은 "게시판 하나가 빠진 문제"가 아니라 **"약관·개인정보처리방침을 개정할 때 파트너에게 사전 공지할 화면이 우리에게 없다"** 는 이행 의무의 공백이다. 대상은 **파트너용(ko 단일, 지금 소비 화면까지 구현)** 과 **SEEPN 사용자용(ko 원문 + en/ja 번역, 소비 화면은 seepn.me 구축 시 Phase 1)** 2종이고, FKP 공개 사이트는 제외한다. 구현은 **기존 블로그 게시판을 물리적으로 전환**(게시글 0건 확인)해 재사용하며, **이미지 업로드를 포함한 리치 텍스트 에디터**가 별도 워크스트림으로 붙는다.

### 1.2 재평가를 촉발한 변화 — 파트너 앱이 실재하게 됐다

A-11을 백로그로 판정한 시점(2026-08-29)에는 **로그인하는 사용자가 운영자뿐**이었다. 그 사이 파트너 자가등록 앱과 파트너 전용 약관·개인정보처리방침이 만들어졌고, 그 문서들은 다음을 **회사의 의무로 이미 선언**했다:

- `partner-terms-v1.0-2026-09-ko.md` §3: "약관을 개정할 경우 적용일자 **7일 전부터 서비스 화면에 공지**합니다. 불리하거나 중대한 사항은 **30일 전부터 공지**하고 이메일로도 통지합니다."
- `partner-privacy-v1.0-2026-09-ko.md`: "변경사항 시행 **7일 전**부터 파트너 서비스 화면과 이 문서를 통해 공지합니다. 중대한 변경은 **30일 전**."
- 약관 §3-4: 공지 기간 내 거부 의사가 없으면 **동의한 것으로 간주** — 공지 화면은 **묵시적 동의 성립의 요건**이다.

**우리는 "서비스 화면에 공지한다"고 약속해 놓고, 그 화면을 만들지 않았다.**

## 3. 타겟 사용자 / 노출 대상 / 언어

### 3.1 결정 D-N1 (최종) — 대상 2종 × 대상별 언어 정책

| 대상 값 | 독자 | 소비 화면 | **언어(D-N0-5)** | v1.0 처리 |
|---|---|---|---|---|
| **`partner`** | 로그인한 파트너(공급사) | `/supplier/notices` — **신규 구현** | **ko 단일**(번역 없음) | **Phase 0 + 소비 화면까지 지금 구현** |
| **`seepn_user`** | SEEPN 사용자 | seepn.me — **아직 없음** | **ko(원문) + en + ja** | **Phase 0만**: Admin 등록·태깅·번역 입력. 소비 화면은 Phase 1 |
| ~~FKP 공개 사이트(바이어)~~ | — | — | — | **제외 확정(D-N0-1)** |

**공통 원칙 — 모든 공지의 원문 로케일은 `ko`다.** 작성자가 대표(한국어)이기 때문이며, 이는 기존 콘텐츠(`content_item.source_locale` 기본값 `'en'`)와 **다르다.** 이 한 줄이 §7.5 G-3(함수 시그니처 변경)의 근거다.

```
partner    공지 = ko 1건        (번역 대상 없음 → AI 초벌 버튼 노출 금지, G-6)
seepn_user 공지 = ko 원문 + en + ja  (번역 대상 존재 → 향후 AI 초벌 적용 가능, §12)
```

### 3.2 전환 후의 게시판 지도

| 게시판 | 상태 | 독자 | 언어 |
|---|---|---|---|
| **공지사항** (`notice`, 신규) | 신설 — 블로그 인프라 재사용 | `partner` / `seepn_user` | ko / ko+en+ja |
| 사례 (`case_study`) | 변경 없음 | FKP 공개 사이트 | en/ja |
| FAQ (`faq`) | 변경 없음 | FKP 공개 사이트 | en/ja |
| ~~블로그 (`blog`)~~ | **폐지**(물리적 전환, §7.3) | — | — |

### 3.3 Phase 0 / Phase 1 분리 (D-N0-2)

이 프로젝트가 이미 쓰는 패턴이다: **"데이터·관리 화면을 먼저 만들고, 소비 화면은 준비되면 붙인다."**(상위 PRD §3.2.6 "공식과 변수는 지금 확정해 수집을 시작한다", TR-4″의 단계 분리와 같은 사고)

| | Phase 0 (이번 범위) | Phase 1 (seepn.me 구축 시) |
|---|---|---|
| `partner` 공지 | Admin 등록·관리 + `/supplier/notices` | — (Phase 0에서 완결) |
| `seepn_user` 공지 | Admin 등록·관리·태깅 + **ko/en/ja 번역 입력까지** | seepn.me 목록/상세(ko/en/ja) |

> **Phase 0의 필수 안전장치(N-R6)**: `seepn_user` 공지는 **올려도 아무도 볼 수 없다.** 대표가 이를 모르고 중요 공지를 올리면 "공지했다고 생각했는데 아무도 못 본" 최악의 상황이 된다. Admin에 **"이 대상은 아직 소비 화면이 없습니다(seepn.me 준비 중)"** 경고 상시 노출은 **Must이며 생략 불가**다.

### 3.4 결정 D-N3 (v3.0 신규) — 대상(`target_audience`) 변경 정책

대상에 따라 언어 구성이 달라지므로(ko 단일 vs ko/en/ja), 생성 후 대상을 바꾸면 **번역 행이 고아가 되는 상태**가 생긴다(`partner`로 바꿨는데 en/ja 번역이 남아 있는 등).

> **권고 규칙: 대상은 원칙적으로 불변. 단 `ko` 외 번역 행이 하나도 없으면 변경을 허용한다.**
> — 실수 직후(번역 입력 전)에는 고칠 수 있고, 번역까지 채운 뒤에는 잠긴다. 잠긴 뒤 대상을 바꿔야 하면 삭제 후 재작성한다(공지는 외부 백링크가 없는 자산이라 삭제 비용이 낮다). 최종 UX는 service-planner 확인.

## 4. 목표 및 성공 지표

### 4.1 목표

1. 약관·개인정보처리방침 개정 시 **7일/30일 사전 공지 의무를 화면으로 이행**한다(P-N1).
2. 대표가 **10분 안에** 공지를 작성·게시한다 — 개발자 호출 없이, **마크다운 문법을 몰라도**(P-N2, P-N6).
3. seepn.me가 생기는 시점에 **스키마 재작업 없이 소비 화면만 붙이면 되게** 한다(P-N5).
4. **새 테이블·새 권한 코드를 만들지 않고**, 기존 블로그 자산을 재사용한다(D-N0-3).

## 6. 콘텐츠 형태 결정

### 6.1 결정 D-N2 — 기존 블로그 shape(title/excerpt/body) 승계

전환(D-N0-3)이 전제이며 형태도 적절하다: 공지는 "제목 + 한 줄 요약 + 본문"이 자연스럽다. `ArticleRow`/`NewArticleForm`/`loadArticleRecords`를 재사용할 수 있어 Effort가 가장 작다. `content_key` 컨벤션(`notice.{slug}`)과 슬러그 불변 정책도 승계한다.

### 6.2 `target_audience` — v1.0 판정을 뒤집는다 (필요)

> v1.0은 "특수 필드 전부 불필요"라고 판정했으나 그 판정은 **"독자가 하나뿐"** 이라는 전제 위에 있었다. D-N0-1로 전제가 깨졌으므로 이 항목만 재검토했다.

| 대안 | 판정 | 근거 |
|---|:---:|---|
| **`content_item`에 `target_audience` 컬럼** | ✅ **채택** | 대상은 **글 단위로 하나로 결정되는 속성**, **조회 필터 조건**, **오발행 시 피해가 큼**. 게다가 **대상이 언어 구성까지 결정**(ko 단일 vs ko/en/ja)하므로 조회·화면 양쪽의 분기 키다 |
| `content_type`을 2개로 분리 | ❌ | `content_type`은 **본문 shape를 결정하는 축**이다. 독자 축을 섞으면 두 축이 곱해져 화면·상수·RPC가 2배가 된다 |
| `content_key` 프리픽스 | ❌ | 문자열 규칙은 DB가 강제하지 못한다. 오타 하나로 잘못된 대상에 뜬다 |
| 본문 jsonb 내부 키 | ❌ | **본문은 로케일별로 존재한다.** ko와 en이 서로 다른 대상을 가리키는 모순이 가능하다. 다국어 확정(D-N0-5)으로 이 위험이 더 커졌다 |

**추가 판단**: 이 컬럼은 `notice`에만 의미가 있다(blog/case_study/faq는 대상 고정). 따라서 nullable + **`content_type='notice'`이면 NOT NULL**을 DB 제약으로 권고한다. 값은 **2개만** 만든다.

### 6.3 나머지 특수 필드 — v1.0 판정 그대로 유지 (불필요)

| 요구 | v3.0 재확인 | 처리 |
|---|---|---|
| 상단 고정(pinned) | 대상·언어와 무관 | **불필요.** `sort_order` 큰 값이 곧 고정(N-R19) |
| 중요도 배지 | 무관 | **불필요.** 제목에 `[중요]` |
| 게시 시작일(예약) | 무관 | **불필요.** `draft` → 당일 `published` |
| 만료일(자동 내림) | 무관 | **불필요.** `is_active` 수동 토글 |
| 분류(점검/약관/기능) | 무관 | **불필요.** 총량 두 자릿수 전에는 필터 무의미 |

> **재검토 트리거**: ① 대상 1개당 누적 20건 초과, ② 월 2건 이상 발행이 3개월 지속, ③ `partner` 공지 다국어화(N-R24), ④ 대상 3개 이상으로 증가. 하나라도 발생 시 재평가.

### 6.4 리치 텍스트 에디터 — 최종 요구사항 (D-N0-4 + D-N0-6)

**PM이 정하는 것**: N-R13~N-R16 (에디터 필요 / 최소 기능선 / 기존 마크다운 호환 / **이미지 업로드 포함**).
**넘기는 것**: 라이브러리 선택, 툴바 구성, 화면 배치 → service-planner → ui-ux-designer → frontend-developer.

**PM이 못 박는 제약 3가지** (미루면 데이터 재작업이 발생한다):

| 제약 | 내용 |
|---|---|
| **C-1. 저장 포맷은 공지 운영 시작 전에 확정** | 에디터 구현이 뒤로 밀리더라도 **포맷 결정은 WS-1 착수 전에** 끝낸다. 마크다운으로 수십 건 쌓은 뒤 HTML로 바꾸면 전량 변환이 생긴다 |
| **C-2. PM 권고 = 마크다운 유지**(에디터가 마크다운을 생성) | 근거: (1) 기존 사례/FAQ 본문이 전부 마크다운이라 N-R15를 자동 충족. (2) 현재 렌더러가 **raw HTML을 파싱하지 않는 것이 현행 XSS 방어선**이다 — HTML 저장은 sanitizer 도입 + 정식 보안검토를 동반한다(NS-4). **최종 선택은 frontend-developer + privacy-security-officer 합의이며, HTML을 택하면 그 2건이 견적에 포함되어야 한다** |
| **C-3.** *(v3.0 신규)* **이미지는 "에디터 기능"이 아니라 "파이프라인"이다** | N-R16을 충족하려면 최소 4가지가 함께 필요하다: ① 업로드 엔드포인트, ② **전용 Storage 버킷**(§7.6), ③ **렌더러의 이미지 문법 지원 추가** — 현행 렌더러는 이미지를 아예 지원하지 않는다(5-D 스펙 §5.3), ④ URL 스킴 검증(기존 링크 방어 로직과 동일 수준). **에디터 라이브러리를 고르는 것만으로는 이미지가 동작하지 않는다** — WS-3 견적에 반드시 반영할 것 |

> **참고 — 해소된 제약**: 기존 스펙(5-D §5.2)의 "새 npm 의존성 추가 금지" 원칙은 근거 중 하나가 "새 런타임 의존성은 대표 승인 필요"였다. **D-N0-4가 대표 직접 요청이므로 해소되었다.** 다만 취지(불필요한 의존성 억제)는 유효하므로 **에디터 1개 도입으로 끝내고 렌더러를 통째로 교체하지는 않는 것**을 권고한다(C-2 + C-3의 렌더러 "확장").

### 6.5 알려진 한계 — "발행일"이 정확하지 않다

`content_item`에 발행일 컬럼이 없어 N-R17의 날짜는 `created_at` 프록시다. **초안으로 만들고 며칠 뒤 게시하면 표시 날짜가 실제 게시일보다 이르다.** 7일/30일 사전 공지를 다루는 기능에서 무시할 수 없으므로 **운영 규칙으로 우회한다**: 공지는 **작성과 동시에 게시**한다. 지켜지지 않으면 §6.3 트리거와 무관하게 `published_at` 도입을 우선 검토한다.

### 6.6 다국어 운영 흐름 (D-N0-5, `seepn_user` 전용)

```
1. 대표가 ko로 작성 (source_locale='ko', status='draft')
2. en / ja 번역 입력  ← 현재는 수작업. 향후 AI 초벌 채우기 적용 후보(§12)
3. 로케일별로 status를 published로 전환
4. (Phase 1) seepn.me가 요청 로케일 우선 + ko 폴백으로 렌더링
```

- **로케일별 독립 발행 정책을 승계한다**: ko가 published인데 ja가 draft면, seepn.me의 ja 방문자에게는 **ko 폴백**이 보인다(기존 `getLandingCopyMap` 폴백 규칙과 동일). 소스 로케일이 en에서 **ko로 바뀌었으므로 폴백 기준도 ko**임을 Phase 1 구현자가 알아야 한다.
- 번역 stale 추적(`source_synced_at`)은 기존 로직이 그대로 동작한다 — **단 `source_locale='ko'`가 실제로 저장되어야만 그렇다**(G-3).

## 7. 스키마 확장 / 전환 방향 (backend-developer 사전 정보)

> 아래는 **방향과 계약**이다. 실제 SQL·전환 절차 설계는 backend-developer 소관.

### 7.1 `content_type`에 `'notice'` 추가

CHECK 제약을 재생성한다. 제약 이름이 인라인 자동 생성이므로 **하드코딩하지 말고 introspection으로 찾아 drop/recreate** — 동일 파일의 `audit_log.action`(§8), `requests.category`(§4) 패턴을 따른다. **`'blog'` 값은 이 기회에 목록에서 제거**한다(§7.3 A-2 확정).

### 7.2 `target_audience` 컬럼 (N-R1)

| 항목 | 방향 |
|---|---|
| 위치 | `public.content_item` (아이템 단위 속성) |
| 값 | `'seepn_user'` / `'partner'` **2개만** |
| NULL 정책 | nullable + **`content_type='notice'`이면 NOT NULL** CHECK 권고 |
| 기본값 | **두지 않는 것을 권고.** 기본값이 있으면 대상을 고르지 않고 저장했을 때 **조용히 잘못된 대상으로 발행**된다 |
| 인덱스 | `(content_type, target_audience, is_active, sort_order)` 검토 |
| RLS | **변경 없음.** 표시 필터일 뿐 접근 통제 축이 아니다(§9 NS-1) |
| 감사 | 기존 `content.create/update/delete`로 자동 기록 — 추가 작업 없음 |

### 7.3 블로그 → 공지사항 전환 — **A-2(물리적 전환) 확정** (D-N0-3 + D-N0-7)

> **v2.0에서는 A-1(논리적 전환)을 권고했다. D-N0-7(게시된 블로그 글 0건)로 그 권고의 근거가 사라졌으므로 A-2로 확정한다.**

A-1을 권고했던 유일한 이유는 **"기존 공개 `/blog` URL과 글 데이터를 잃지 않기 위해"** 였다. 지킬 자산이 0건이므로:

| 항목 | 확정 내용 |
|---|---|
| **방식** | 기존 `blog` 관련 자산을 **공지사항으로 물리적 전환**한다. `content_type` 허용값에서 `'blog'`를 제거하고 `'notice'`를 추가한다 |
| **데이터 마이그레이션** | 게시글 0건이므로 실질 대상이 없다. **다만 마이그레이션은 방어적으로 작성한다** — 초안(draft) 행이 남아 있을 수 있고, 로컬/스테이징 DB 상태가 프로덕션과 다를 수 있다. 잔여 행이 있으면 `content_type`과 **`content_key` 프리픽스를 함께** 갱신해야 한다(G-4) |
| **공개 라우트** | `app/[locale]/blog/page.tsx`, `app/[locale]/blog/[slug]/page.tsx` **제거** |
| **부수 정리** | `components/Footer.tsx`의 Blog 링크, `lib/i18n/{types,en,ja}.ts`의 `blog.*` / `footer.blogLinkText` 키, `lib/content/contentTypes.ts`의 `ArticleContentType`·`CONTENT_TYPE_URL_SEGMENT`·`URL_SEGMENT_TO_CONTENT_TYPE`에서 blog 제거 |
| **Admin 경로** | `/admin/board/blog` → `/admin/board/notice`. 메뉴 행은 대표가 메뉴관리 UI에서 수정(코드 하드코딩 금지) |
| **가드레일 해제** | v2.0의 "블로그 글 0건 손실" 가드레일은 **불필요**(§4.2) |
| **되돌리기** | 0건이므로 롤백 비용도 낮다 |

> **주의**: `case_study`가 위 상수·컴포넌트를 **공유**한다. blog만 걷어내는 과정에서 사례 게시판이 깨지기 쉽다(§7.5 G-5 — qa-reviewer 필수 회귀 항목).

### 7.4 "별도 테이블이 필요한가" 재검증 — 필요 없다

| 기준 | 결과 |
|---|---|
| 다른 테이블의 FK 대상인가? | ❌ → `content_item`(jsonb 계열)이 맞는 자리 |
| 공지 전용 컬럼이 필요한가? | **⚠️ `target_audience` 1개만** — 컬럼 1개로 테이블을 신설하는 것은 과잉 |
| 대상별 접근 제어가 다른가? | ❌ **D-N0-8로 확정** — 둘 다 published 공개 읽기 |
| 다국어가 별도 테이블을 요구하는가? | ❌ `content_translation.locale`이 **이미 ko/en/ja/zh를 허용**한다(§1.1) |
| 별도 테이블 비용 | 테이블 + RLS 6개 + RPC 3개 + 감사 + 화면 신규 = **Effort 3배 이상**, 블로그 자산 재사용 불가 |

**결론: 기존 스키마 확장(`content_type='notice'` + `target_audience` 컬럼)으로 진행한다.**

### 7.6 이미지 업로드 파이프라인 (N-R16 / D-N0-6) — 방향

> 값(용량·MIME·경로 규칙)은 backend-developer + privacy-security-officer가 확정한다. PM은 **결정해야 할 항목과 기존 자산과의 관계**만 고정한다.

| 항목 | 방향 |
|---|---|
| **전용 버킷 필요 여부** | **필요하다(확정).** 기존 `partner-doc`은 **비공개 + 서명 URL** 방식인데, 서명 URL은 **만료되므로 본문에 박으면 이미지가 깨진다.** 콘텐츠 이미지는 **공개 읽기 버킷**이어야 한다 — 성격이 정반대이므로 재사용하면 안 된다 |
| 버킷명 | 예: `content-image` (backend 확정) |
| 읽기 권한 | **공개 읽기**(anon). 공지 본문이 이미 anon 읽기 가능하므로(NS-1) 일관됨 |
| 쓰기 권한 | **`content_management` create/update 보유 관리자만.** Storage RLS로 게이트 — `partner-doc`의 버킷 레벨 제약 선례(`20260904100000_...sql` §4a) 참고 |
| MIME 허용 | jpeg/png/webp 수준(backend 확정). SVG는 **스크립트 삽입 벡터이므로 제외 권고** |
| 용량 상한 | 보수적으로 시작(예: 2MB/장). 늘리는 건 쉽고 줄이는 건 어렵다 |
| 경로 규칙 | 콘텐츠 아이템 단위 폴더 권고(삭제·추적 용이) |
| 고아 파일 정리 | **v1.0 미구현(W-N11).** `partner-doc`과 달리 법정 보관기한 이슈가 없어 수동으로 충분 |
| 렌더러 | **이미지 문법 지원 추가가 필수**(C-3 ③). 현행 렌더러는 이미지를 지원하지 않는다 |

|---|---|:---:|:---:|:---:|:---:|:---:|:---:|

| ~~A-1안~~ | 논리적 전환 | — | — | — | — | — | ❌ **D-N0-7로 근거 소멸** |

**RICE 추이(15.0 → 12.9 → 11.3)와 그 의미**

> 기획이 구체화될수록 값이 내려갔다. 요구가 늘어서가 아니라 **처음에 안 보이던 부수 비용이 드러났기 때문**이다(대상 2종 분기, 다국어 열 구성, 블로그 자산 정리, AI 버튼 분기). **우선순위 결론은 세 번 모두 동일하다: MVP 아님, 트리거 조건부.** 오히려 **MVP에 넣지 말아야 할 근거가 계속 강해졌다.**

**8.2-a. `seepn_user` Phase 0을 지금 하는 게 맞는가 (Reach 0인데)**

| | 지금 하기 | 나중에 하기 |
|---|---|---|
| 비용 | 컬럼 1개 + 셀렉트 1개 + 경고 배지 + 로케일 열 분기 ≈ **0.5인일**(WS-1 포함) | 컬럼 추가 마이그레이션 + **기존 공지 전량 백필** + 화면 재작업 ≈ 1.0인일 + 재분류 리스크 |
| 리스크 | 대표가 "올렸는데 안 보인다"고 오해 → **N-R6 경고로 방어** | seepn.me 오픈 시 공지 0건 → 빈 게시판 오픈 |

→ **지금 하는 것이 맞다. 단 N-R6(경고 배지)이 붙는다는 조건에서만.**

**8.2-b. 에디터(WS-3)는 RICE로 평가하지 않는다**

RICE의 Reach는 사용자 수 기반이라 **사용자가 운영자 1~3명인 내부 도구에서는 항상 0에 가깝게 나온다**(RICE의 알려진 한계). 다른 척도를 쓴다:

| 척도 | 평가 |
|---|---|
| Impact | **중간~높음** — 공지가 길수록 효과가 크고(P-N6) 문법 오류 재게시를 없앤다(보조지표 2). 다만 **P-N1(법적 의무)은 에디터 없이도 풀린다** |
| Effort | **높음(5~7인일)**, 불확실성 최대. **이미지 요구(D-N0-6)로 v2.0 추정 대비 커졌다** |
| 우선순위 근거 | **대표 직접 요청(D-N0-4/6)** — 다만 요청은 "무엇을"이지 "언제"가 아니다 |
| **권고** | **WS-1/WS-2와 분리해 뒤에 둔다.** ① 에디터 없이도 P-N1을 이행할 수 있고, ② WS-3 지연이 법적 의무 이행 지연으로 전이되는 결합을 만들면 안 되며, ③ 에디터는 **사례·FAQ에도 함께 적용되는 별도 가치**를 갖는다. **단 §6.4 C-1(저장 포맷 결정)은 WS-1 착수 전에 끝낸다** |

### 8.3 로드맵 위치 — MVP 아님, 트리거 조건부

| 질문 | 답 |

| 언제 하는가? | **아래 트리거 중 먼저 오는 시점 직후** |
