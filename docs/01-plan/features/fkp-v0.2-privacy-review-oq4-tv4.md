## 1. TV-4 — Supabase 리전 및 국외이전

### 1.1 코드/설정에서 리전을 확인할 수 있는가 → **불가능**

확인한 사실:

- `.env.local:13-14`에 프로젝트 URL과 anon key가 존재. 리전 정보는 없음.
- anon key JWT payload는 `{iss, ref, role, iat, exp}`만 포함 — **리전 필드 없음**. (`iat=1787549472` → 프로젝트 생성 ≈ 2026-08-22, `exp` ≈ 2036년. 즉 **리드 데이터 0건 상태**이며, 리전 변경 비용이 사실상 0인 유일한 시점입니다.)
- 리포지토리 전체에 Supabase 클라이언트 코드·config·마이그레이션 파일 없음 (grep 결과 PRD 문서 언급뿐).

**결론: Supabase 대시보드 > Project Settings > General > Region 에서 직접 확인해야 합니다.**
보조 확인 수단(참고용, 법적 근거로 쓰지 말 것): Management API `GET /v1/projects` (Personal Access Token 필요), `db.omlymbohmdyesgnqexbp.supabase.co`의 DNS → AWS IP 대역 역추적.

### 1.2 권고 리전: **ap-northeast-2 (Northeast Asia, Seoul)**

| 관점 | 서울(ap-northeast-2) | 도쿄(ap-northeast-1) | 싱가포르/미국 |
|------|------|------|------|
| PIPA 국외이전 | **발생 안 함** (§28조의8 절차 불요) | 발생 → 고지·공개 의무 | 발생 |
| GDPR (EU 유입분) | 한국은 **EU 적정성 결정 대상국(2021.12)** → SCC 없이 이전 적법 | 일본도 적정성 대상국 (동등) | 미국/싱가포르는 SCC·TIA 필요 |
| APPI (일본 이용자) | 처리자 YLIA가 한국 소재이므로 **어느 리전이든 越境移転 규율은 동일하게 발생** | 동일 | 동일 |
| 성능 | 폼 제출은 1회성 write. 일본·동남아 대비 지연 수십 ms → **전환율 영향 무시 가능** | 미세 우위 | 열위 |

핵심 논리: **도쿄를 골라도 APPI 부담은 줄지 않습니다.** 데이터를 실제로 열람·처리하는 주체(YLIA, 한국)가 일본 밖에 있으므로 일본 밖으로의 이전은 어차피 발생합니다. 반면 서울을 고르면 **PIPA 국외이전이 통째로 사라지고**, GDPR도 적정성으로 커버됩니다. 규제 표면적을 가장 크게 줄이는 선택은 서울입니다.

> **주의(보수적 판단)**: 서울 리전이어도 Supabase Inc.(미국 법인)의 운영·지원 인력이 원격 접근할 수 있다면 "국외 보관은 아니지만 국외 접근"이라는 해석 여지가 남습니다. 실무 권고: **서울 리전 + 처리방침에 Supabase를 수탁자로 기재 + 국외이전 항목도 병기**. 이렇게 하면 어느 해석을 따라도 안전합니다. (변호사 검토 필요)

**의사결정 요청 (대표)**: 현재 리전이 서울이 아니면 → 프로젝트를 폐기하고 서울로 재생성. 데이터가 0건이라 비용은 URL/키 교체뿐입니다. 리드가 쌓인 뒤에는 Supabase가 리전 변경을 지원하지 않아 수동 마이그레이션 + 다운타임이 필요합니다.

### 1.3 만약 국외 리전으로 확정될 경우 — PIPA 요건

근거: 개인정보 보호법 §28조의8. 국외 이전은 원칙 금지이며, 아래 중 하나에 해당해야 합니다.

| 경로 | 요건 | 이 서비스 적용성 |
|------|------|------|
| ① 정보주체의 **별도 동의** | §28조의8② 5개 항목 사전 고지 후 동의 | 가능하나 폼 마찰 증가, 비권장 |
| ③ **계약 체결·이행에 필요한 처리위탁·보관** + 처리방침 **공개** 또는 이메일 등 **통지** | 아래 5개 항목 전부 공개 | **실무 표준. 이 경로 권고** |

③ 경로에서 처리방침에 공개해야 하는 항목 (§28조의8② 준용):
1. 이전되는 개인정보 항목
2. 개인정보가 이전되는 **국가, 시기 및 방법**
3. 이전받는 자의 성명(법인명 및 연락처)
4. 이전받는 자의 **이용목적 및 보유·이용 기간**
5. 이전 거부 방법·절차 및 거부의 효과

> ③은 "정보주체와의 **계약** 체결·이행에 필요한" 경우입니다. 리드 접수는 계약 전 상담 단계라 이 요건 충족 여부에 해석 여지가 있습니다 → **변호사 검토 필요**. 서울 리전을 택하면 이 논쟁 자체가 사라집니다. 이것이 서울을 권고하는 두 번째 이유입니다.

### 1.4 일본(APPI) / EU(GDPR) 노출

- **APPI**: `/ja` 페이지로 일본 거주자에게 서비스를 제공하므로 APPI 역외적용(§171) 대상 가능성이 높습니다. 일본어 처리방침에는 PIPA 번역본이 아니라 APPI 고유 항목(利用目的の公表, 開示・訂正・利用停止の請求手続, 苦情申出先, 外国にある第三者への提供 시 이전처 국가명·해당국 제도 정보, 安全管理措置 중「外的環境の把握」)이 들어가야 합니다. **ux-writer에게 "번역"이 아니라 "일본 요건 반영"으로 지시할 것.** (변호사 검토 필요)
- **APPI 클라우드 예외**: 클라우드 사업자가 계약상 개인데이터를 취급하지 않고 접근통제가 되어 있으면 "제3자 제공"이 아니라는 PPC 해석이 있습니다. Supabase DPA에 해당 조항이 있는지 확인하면 부담이 줄어듭니다.
- **GDPR**: `/en`이 공개 페이지이고 해외 아웃리치를 하므로 Art.3(2) 적용 여지. 처리근거는 "계약 체결 전 조치(Art.6(1)(b))" 또는 동의. 정보주체 권리(열람/삭제/이동/반대) 안내가 처리방침에 필요합니다. **EU 트래픽이 사업상 목표가 아니라면, EU를 명시 타깃하지 않는다는 방침을 문서화하고 최소 대응(권리 안내 + 문의 창구)만 하는 것도 합리적 선택**입니다. (변호사 검토 필요)

### 2.2 보관기간 권고안

법정 최소 보관 의무는 **없습니다.** 전자상거래법상 계약·청약철회 기록 5년 / 소비자 불만·분쟁 처리 기록 3년은 **재화·용역 거래가 실제 발생한 경우**에 적용되며, 계약 전 단계의 미성사 리드에는 적용되지 않습니다. 따라서 "3년/5년"을 관성적으로 붙이면 오히려 §21(목적 달성 시 지체 없이 파기) 위반 소지가 생깁니다.

| 리드 상태 (OQ-3 확정값) | 보관기간 | 근거 |
|------|------|------|
| 신규접수 / 검토중 / 파트너매칭중 | **최종 상태변경일 + 12개월** | B2B 리드는 예산·타이밍 미스매치로 6~18개월 후 재문의가 흔함. 12개월이 재접촉 실익과 최소보유의 균형점 |
| 보류 | **최종 상태변경일 + 12개월** | 동일 |
| 매칭완료 | **매칭완료일 + 24개월** | 사후 대응·재의뢰 대응. **실제 계약이 체결되면 그 시점에 계약관계를 별도 근거로 하여 별도 관리**(리드 테이블 보관기간과 분리) |
| 종료 / 스팸 | **판정 후 30일 이내 하드 삭제** | 보관 목적이 존재하지 않음. 재발 차단이 필요하면 이메일 **해시만** 별도 테이블에 90일 |

> 더 보수적으로 가려면 기본값을 **6개월**로 낮출 수 있습니다. 다만 실제 운영 리듬(월 20건 규모, 수동 매칭)을 고려하면 12개월이 현실적이라 판단합니다. **대표 확정 필요.**

### 2.3 파기 방식 — **"선(先) 익명화 + 행 유지"** 권고

하드 삭제(행 DELETE)를 하면 북극성 지표(누적 리드 수, 카테고리 분포, locale 분포)의 과거 데이터가 함께 사라집니다. 반대로 가명처리만 하면 여전히 개인정보라 **파기 이행으로 인정되지 않습니다** (PIPA §58조의2는 "시간·비용·기술을 합리적으로 고려할 때 재식별 불가능"한 익명정보만 법 적용에서 제외).

권고 절차:
1. 보관기간 만료 시 **개인정보 컬럼을 NULL 처리**: `contact`, `companyNameWebsite`, `purpose`, `description`, `internal_note`, `consent_ip`(수집 시)
2. 통계 컬럼만 잔존: `category`, `partner_type`, `budget`, `timeline`, `english_speaking`, `locale`, `status`, `created_at`
3. `anonymized_at` 기록. 이후 이 행은 익명정보로 취급
4. **스팸·종료 건은 예외적으로 행 자체를 DELETE** (통계 가치 없음)

이 방식이면 "파기 의무 이행"과 "지표 연속성"을 동시에 달성합니다.

> 주의: `created_at` + `category` + `locale` 조합만으로도 건수가 극히 적은 구간에서는 재식별 가능성이 있습니다. 리드가 100건을 넘기 전까지는 익명화 행에 대해 `created_at`을 **월 단위로 절삭**(`date_trunc('month', ...)`)해 저장하는 것을 권고합니다.

### 2.4 파기 실행 및 증빙

- **실행**: Supabase `pg_cron` 일 1회 배치. 애플리케이션 코드가 아니라 DB 레벨에서 실행 (앱 배포 실패 시에도 파기가 멈추지 않도록)
- **증빙**: `retention_jobs` 테이블에 실행시각 / 대상 조건 / 익명화 건수 / 삭제 건수 기록. **파기 이행의 입증 책임은 처리자에게 있습니다.** 로그가 없으면 "했다"를 증명할 수 없습니다
- **백업 정합성** — 놓치기 쉬운 항목: Supabase의 일일 백업/PITR에는 파기한 개인정보가 남습니다. 백업 보존기간을 확인하고 처리방침에 "파기 후 백업본에서는 최대 N일 내 소멸"로 명시할 것. Free 플랜은 백업 정책이 제한적이므로 **유료 플랜 전환 시 PITR 보존기간을 7일 등으로 명시적으로 설정**하세요
- **스키마 반영 권고 컬럼**:
  - `retention_expires_at timestamptz not null` — 생성 시 계산, `status` 변경 시 트리거로 재계산
  - `anonymized_at timestamptz null`
  - partial index: `create index on requests (retention_expires_at) where anonymized_at is null;`

### 2.5 기존 Google Sheets 데이터 처리 (미결 항목)

`.env.local:4`의 Apps Script 엔드포인트로 6~8월 리드가 **운영자 개인 Google 계정** Sheets에 적재되어 있습니다. 문제:
- 개인 계정 = 접근권한 감사 불가, 계정 사고 시 통제 불가, 퇴사/승계 시 이관 불가
- **동의 절차·처리방침 없이 수집된 데이터** → 계속 이용하려면 사후 동의를 받거나 파기해야 합니다

권고 (PRD §9에서 "이관 Won't"이므로 **파기 시점을 명시**해야 함):

## 3. 처리위탁 고지 필요 여부

### 3.1 판단: **Supabase 이용은 개인정보 처리위탁(§26)에 해당합니다. 제3자 제공(§17)이 아닙니다.**

구분 기준은 "누구의 목적을 위해 처리하는가"입니다. Supabase는 YLIA의 목적을 위해 데이터를 보관·처리하는 **수탁자**이며, 자신의 목적으로 이용하지 않습니다. 따라서 **정보주체의 별도 동의는 불필요**하고, 대신 아래 두 가지 의무가 발생합니다.

### 3.2 의무 ① — 위탁계약 문서화 (§26①)

위탁 시 다음이 포함된 **문서**가 필요합니다: 위탁업무 목적·범위 / 재위탁 제한 / 개인정보 안전성 확보조치 / 관리·감독 / 손해배상.

**실행 항목: Supabase의 DPA(Data Processing Addendum)를 체결하고 사본을 보관하세요.** Supabase는 표준 DPA를 제공합니다(Dashboard 또는 legal 페이지). 이건 개발 작업이 아니라 대표가 지금 처리할 수 있는 항목이며, **Phase 1 배포 전 완료를 게이트로 요구합니다.** AWS(Amplify), Google(GA4/GTM)에 대해서도 동일하게 DPA/약관 수락 상태를 확인하세요.

### 3.3 의무 ② — 처리방침 공개 (§26⑤)

위탁업무 내용과 수탁자를 정보주체가 확인할 수 있도록 **처리방침에 공개**해야 합니다. (홍보·판매권유 업무 위탁이 아니므로 개별 통지 의무는 없습니다.)

- "전체 동의" 단일 체크박스만 두지 말 것. 개인정보 동의 / 이용약관 동의 **분리**
- 각 체크박스 옆에 전문 링크(새 창) + 요약 문구 병기
- 필수/선택을 시각적으로 구분
- 미체크 시 제출 차단 + 어느 항목이 누락됐는지 명시적 에러

### 4.3 스키마 컬럼 권고 — **필요합니다. 아래 그대로 반영 권고**

```
-- 동의 기록
privacy_consent          boolean     not null,
consent_version          text        not null,   -- 예: 'privacy-v1.0-2026-09'
consented_at             timestamptz not null,
consent_locale           text        not null,   -- 어느 언어 문안에 동의했는지
terms_consent            boolean     not null,
terms_version            text        not null,
marketing_consent        boolean     not null default false,
marketing_consented_at   timestamptz,

-- 미래 확장용 (Phase 1 미사용, 컬럼만 확보)
third_party_consent      boolean     not null default false,
third_party_consented_at timestamptz,
third_party_recipient    text,                    -- 어느 파트너사에 대한 동의인지

-- 보관/파기
retention_expires_at     timestamptz not null,
anonymized_at            timestamptz,

-- DB 레벨 강제
constraint chk_privacy_consent check (privacy_consent = true),
constraint chk_terms_consent   check (terms_consent   = true)
```

**backend-developer가 놓치기 쉬운 3가지:**

1. **`consent_version`은 반드시 동의 문안 원문과 1:1로 결속되어야 합니다.** 문자열만 저장하고 문안을 나중에 고치면 "이 사람이 정확히 무엇에 동의했는지"를 증명할 수 없습니다. 최소 요건: 버전별 문안 원문을 리포지토리에 파일로 고정 보관(`docs/legal/privacy-v1.0.md`)하고 커밋 해시로 추적. 더 나은 방법: `consent_documents(version, locale, body, sha256, effective_from)` 테이블 + FK.

2. **`consent_locale`이 필요한 이유**: 4개 언어 문안 중 어느 것을 보고 동의했는지가 분쟁 시 쟁점이 됩니다. 특히 번역본 간 의미 차이가 있을 때. (정본 언어 지정 여부는 **변호사 검토 필요**)

3. **`consent_ip` — 수집 여부 결정 필요**: 동의 입증에는 유용하나 IP도 개인정보입니다.
   - **권고: 수집하지 않거나, 수집한다면 `/24` 마스킹 저장 + 6개월 보관.**
   - 수집한다면 처리방침의 "자동 수집 항목"에 반드시 명시.
   - 최소수집 원칙상 **미수집도 충분히 정당합니다.** 서버 타임스탬프 + 버전만으로도 실무상 입증력이 있습니다. **대표 결정 필요.**

4. **동의값은 클라이언트를 신뢰하지 말고 서버에서 검증** (E1-R3에 추가). 위 `check` 제약을 DB에 걸면 동의 없는 행이 **물리적으로 존재할 수 없게** 됩니다 — 애플리케이션 버그로 뚫려도 안전합니다.

5. **`honeypot` 값은 저장하지 마세요.** 서버에서 판정 후 폐기.

## 5. RLS 권고 (원칙 수준 — backend-developer 참고용)

> 배경 원칙: **RLS 정책을 쓰기 전에 GRANT를 회수하는 것이 더 강한 방어입니다.** 정책은 실수로 무력화될 수 있지만, 권한이 없으면 정책 평가 자체에 도달하지 않습니다.

| # | 원칙 | 구체 지침 |
|---|------|-----------|
| R-1 | **RLS는 ENABLE + FORCE 둘 다** | `alter table requests enable row level security; alter table requests force row level security;` FORCE가 없으면 테이블 소유자(postgres)는 RLS를 우회합니다 |
| R-2 | **anon/authenticated에 `requests` 권한 자체를 부여하지 않는다** | Supabase는 기본적으로 `public` 스키마에 anon/authenticated GRANT를 부여합니다. `revoke all on public.requests from anon, authenticated;` 및 `alter default privileges in schema public revoke all on tables from anon;` 를 마이그레이션 최상단에 명시 |
| R-3 | **쓰기 경로: insert-only RPC 권고** | `security definer` 함수 `public.submit_request(...)`를 만들고 anon에게 **EXECUTE만** 부여. 테이블 SELECT 권한은 없음. → **anon 키가 유출돼도 리드를 읽을 수 없습니다.** service_role 키를 서버 라우트에서 쓰는 방식(대안)은 단순하지만 그 키가 새면 RLS를 완전히 우회해 전량 노출됩니다. E1-R1(서버 라우트 경유)과 조합하면 후자도 허용 가능하나, **전자를 기본 권고**합니다 |
| R-4 | `security definer` 함수는 `set search_path = ''` 필수 | search_path 하이재킹 방지. 모든 객체를 스키마 수식자로 참조 |
| R-5 | **정책은 명령별로 분리** | `for select` / `for insert` / `for update` / `for delete` 각각 작성. `using`과 `with check`를 **둘 다** 명시. `for all using (true)` 절대 금지 |
| R-6 | **Admin 조회 정책의 순환 참조 주의** | `requests` 정책이 `admin_user`를 조회하고 `admin_user`에도 RLS가 걸리면 무한 재귀가 발생합니다. 권한 판정은 `security definer` 헬퍼 함수(예: `private.has_menu_permission(code, action)`)로 캡슐화하고, 그 함수만 권한 테이블에 접근하게 하세요 |
| R-7 | **민감 컬럼 분리** | `internal_note`, `consent_ip`는 `requests`가 아닌 별도 테이블 또는 `private` 스키마로. PostgREST에 노출되는 스키마 목록에서 `private`을 제외 |
| R-8 | **Realtime 비활성** | `requests`를 `supabase_realtime` publication에 넣지 마세요. 노출면만 늘어납니다 |
| R-9 | **성능 함정** | 정책 내 `auth.uid()`는 `(select auth.uid())`로 감싸 initplan 캐싱. 정책이 참조하는 컬럼에 인덱스 |
| R-10 | **테스트로 증명 (Phase 1 DoD)** | 라이브러리 경유가 아니라 **raw HTTP(curl 수준)** 로: ① anon 키 `GET /rest/v1/requests` → `permission denied` ② anon 키 `POST /rest/v1/requests` → 차단 ③ RPC만 성공 ④ 로그인하지 않은 상태에서 Admin API 접근 → 차단. qa-reviewer와 공동 검증 |
| R-11 | **INV-8(이중 방어) 준수** | RLS만 믿지 말고 서버 라우트에서도 권한 재검증. 반대도 마찬가지 |
| R-12 | **감사 대비 설계** | Phase 3에서 `audit_log`를 붙일 것을 전제로, Phase 1부터 `requests` SELECT 경로를 **서버의 단일 함수**로 통일하세요. 조회 경로가 흩어지면 나중에 감사 로그를 빠짐없이 끼워 넣을 수 없습니다 |

### 5.1 즉시 조치 (RLS 이전 문제) — **심각도: 치명적**

Supabase 프로젝트는 이미 생성되어 있고 anon 키가 유효합니다. 즉 **현재 누구나 `POST https://omlymbohmdyesgnqexbp.supabase.co/auth/v1/signup` 으로 계정을 생성할 수 있는 상태일 가능성이 높습니다** (Supabase 기본값: 회원가입 허용). E3-R1의 "공개 회원가입 차단"은 Phase 3 항목이지만, **지금 대시보드에서 Authentication > Sign In / Providers > "Allow new users to sign up" 을 OFF로 즉시 변경하세요.** 코드 변경 불요, 1분 작업입니다.
