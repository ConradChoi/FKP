### 0.3 이 문서를 쓰며 발견한 Gap (backend-developer 착수 전 확인 필요)

실제 마이그레이션(`20260829140000_partner_schema.sql`, `20260829150000_standard_category_schema.sql`)을 그라운드 트루스로 대조한 결과 발견한 것들이다. PRD §3.1.6이 "재사용 자산 있음"으로 적어둔 항목 중 일부는 **재사용 가능하지만 그대로 쓰면 안 되는 상태**였다.

| # | Gap | 상세 | 영향 |
|---|---|---|---|
| **GAP-1 (중요)** | `public.partner_public` 뷰가 **anon에게 이미 전체 컬럼을 grant**하고 있어, "상세는 로그인 필요"가 **DB가 아니라 Next.js 페이지 가드로만** 지켜지고 있다 | 뷰 코드: `grant select on public.partner_public to anon, authenticated;` — 회사소개/대표품목/레퍼런스/MOQ/가격밴드 등 **상세 전용으로 의도된 필드까지 anon에게 이미 열려 있다.** 즉 지금 상태로는 REST를 직접 호출(`/rest/v1/partner_public?id=eq.xxx`, anon key)하면 **로그인 없이 상세 데이터 전체를 그대로 받는다** — UI 가드는 우회 가능 | **D-S3로 해소를 제안**: 목록용 요약 컬럼만 담은 뷰(anon)와, 지금의 `partner_public`을 `revoke ... from anon`으로 좁혀 상세 전용(authenticated)으로 재정의하는 두 개로 분리(§4.4 RPC 매핑표). **privacy-security-officer가 "로그인 게이트가 UX 장치인지 접근통제인지"를 명시적으로 정해야 한다** — 지금처럼 두면 "정책 문서상 로그인 필요"와 "실제 DB 권한상 로그인 불필요"가 어긋난 상태로 배포된다 |
| **GAP-2 (중요)** | 카테고리 필터(B-9′)에 필요한 `partner_standard_category` 조인 테이블이 **anon은 물론 authenticated(신규 바이어 포함)에게도 읽기 권한이 없다** | 마이그레이션: `revoke all on public.partner_standard_category from anon, authenticated;` 후 `grant select ... to authenticated`는 있지만 그 SELECT는 `partner_standard_category_self_select`(본인 파트너 소유자)/`admin_select`(관리자) RLS만 있고, **"이 파트너가 공개 목록에 있다면 그 카테고리 링크는 누구나 봐도 된다"는 정책이 없다** | B-9′(카테고리 필터)와 B-13(0건 카테고리 처리)이 **지금 스키마로는 구현 불가능**. `partner_public` 뷰와 같은 방식으로 `partner_category_public` 뷰(공개 파트너의 카테고리 링크만 조인)를 신설해야 한다(§4.4) |
| **GAP-3** | `public.partner_public` 뷰에 **`created_at`, `capability_completeness_pct`가 없다** — B-12c의 "최신순"/"완성도순" 정렬 재료 자체가 뷰에 없다 | 뷰 SELECT 목록 확인 결과 두 컬럼 모두 미포함(PII 아니므로 추가에 안전) | 뷰에 두 컬럼 추가 필요 |
| **GAP-4** | B-12c의 정렬 옵션 "**검증 우선**"은 공개 목록에서 **의미가 없다** | `partner_public`/GAP-1 이후의 신규 뷰 모두 `WHERE verification_state='verified'`로 이미 필터링됨(B-14) — 공개 목록에 뜨는 행은 전부 이미 검증됨이므로 이 정렬축은 차이를 만들지 못한다 | "검증우선" 옵션은 **제거하고 "완성도순"으로 대체** 권고 — product-manager 확인(§10 OQ-B1) |
| GAP-5 | `seepn_inquiry`/`buyer_account`/`bookmark` 테이블은 **전혀 존재하지 않는다**(신규 확인, 우려 아님) | 마이그레이션 전체 grep 결과 0건 | PRD 서술과 일치 — 순수 신규 스키마. §7/§8에서 화면이 요구하는 최소 형태를 정의 |
| GAP-6 | 최근 커밋 이력(2026-09-08~09, `20260906100000` 이후)에 `/supplier` 로그인에서 **`@supabase/ssr` 쿠키 스토리지 어댑터의 `setSession()` 관련 실사고**가 있었다(`b.endsWith is not a function`, `setSession()` 성공 응답 후 즉시 `getUser()`가 세션 없음을 반환하는 read-after-write 갭) | `lib/supabase/supplierServerAuthClient.ts`의 WORKAROUND 주석 — 이미 원인 규명·우회 완료(수동 base64url 디코드 + `Authorization` 헤더 직결 + `getUser(accessToken)` 명시적 JWT 오버로드) | **바이어 인증 서버 클라이언트는 이 우회 패턴을 처음부터 그대로 복제**해서 구현할 것(§1.3). `@supabase/ssr`의 기본 쿠키 스토리지 어댑터로 새로 짜면 같은 버그를 다시 밟는다 — backend-developer 필수 인지 사항 |

> **핸드오프**: GAP-1/GAP-2는 privacy-security-officer 사전검토(§4.4 P5a DoD 체크항목 ①③)와 정확히 겹친다. 이 문서가 검토 착수 전에 구체 항목으로 먼저 정리해 둔 것이니, 검토 시작점으로 바로 써도 된다.

### 1.3 세션 아키텍처 (D-S2, GAP-6, "바이어·파트너 세션이 절대 섞이지 않아야 한다")

`/supplier`가 `/admin`과 세션을 분리한 것과 **완전히 동일한 이유로, 동일한 방법으로** `/seepn`을 분리한다. 이번엔 두 축이 아니라 **세 축**(admin/partner/buyer)이 공존하므로 상호 배타성이 한 번 더 중요해진다.

| 계층 | `/admin` | `/supplier` | `/seepn` (신규) |
|---|---|---|---|
| `auth_principal.principal_kind` | `admin` | `partner` | **`buyer`(신규 3번째 값 추가 필요)** |
| 계정 테이블 | `admin_user` | `partner_account` | **`buyer_account`(신규, `partner_account`와 동일 shape: `status` ∈ `pending_email/active/suspended/withdrawn`)** |
| 세션 쿠키명 | (기본값) | `sb-supplier-auth` | **`sb-buyer-auth`** |
| 서버 클라이언트 구현 | `lib/supabase/serverAuthClient.ts` | `lib/supabase/supplierServerAuthClient.ts`(GAP-6 우회 패턴 포함) | **동일 우회 패턴으로 신규 구현** — `@supabase/ssr` 기본 쿠키 어댑터로 새로 짜지 말 것(GAP-6) |
| 요청마다 재검증 | `get_my_admin_context()` | 자기 `partner_account` 행 재조회(`requireSupplierSession`) | **자기 `buyer_account` 행 재조회**(`requireBuyerSession`, 동일 구조) — 행 없음/`withdrawn`/`suspended`는 즉시 `/seepn/login`으로 리다이렉트 |
| MFA(AAL2) | 필수 | 불필요 | **불필요**(파트너와 동일 — 일반 소비자 계정) |

**세 principal_kind 간 자연 차단이 성립하는 이유**: `auth_principal`의 `unique(auth_user_id, principal_kind)` + 각 계정 테이블의 복합 FK 제약으로 **한 Auth 사용자는 세 종류 중 정확히 하나만 될 수 있다**(DB 제약, 애플리케이션 로직이 아님). 따라서:
- 관리자 세션으로 `/seepn`에 들어오면 `buyer_account` 행이 없으므로 `requireBuyerSession()`이 자연 차단.
- 파트너 세션으로 `/seepn`에 들어와도 동일하게 차단.
- 바이어 세션으로 `/supplier`나 `/admin`에 들어와도 대칭적으로 차단.

**단, `auth.users.email`은 세 principal 전체에서 유일해야 한다**(Supabase Auth 자체 제약) — 즉 이미 관리자/파트너로 가입된 이메일로는 바이어 가입이 **막힌다**. 이건 사고가 아니라 Auth 계층의 정상 동작이며, §9 EDGE-B1~B2에서 UX 처리를 정의한다.

> **PR-8 승계, 신규 확인 항목**: `private.is_active_admin()` 등 기존 판정 함수가 새 `buyer` principal_kind를 관리자로 오인하지 않는지 회귀 테스트 필요(P5a DoD에 이미 명시됨). 화면 설계 관점에서는 **바이어 세션으로 어떤 Admin 화면에도 접근이 안 된다는 것**과 **바이어 세션으로 `requests`/`partner_contact`/`private.*`에 닿지 않는다는 것**이 눈에 보이는 형태로 증명돼야 하므로, qa-reviewer 체크리스트에 "바이어 세션 토큰으로 `/admin/leads` REST 직접 호출 시 거부" 항목을 명시적으로 추가할 것을 권고한다(§10).

### 1.4 로그인 게이트의 성격 (GAP-1과 직결)

이 문서는 "로그인 필요"를 **두 가지 서로 다른 것**으로 나눠서 다룬다 — 지금까지 이 프로젝트에서 이 구분이 암묵적이었는데, GAP-1이 드러난 이상 명시가 필요하다.

| 구분 | 의미 | 이 문서의 적용 |
|---|---|---|
| **UX 게이트** | 로그인 안 해도 데이터에 접근할 수는 있지만, 화면상 유도로 로그인을 권한다 | (해당 없음 — 이 문서는 채택하지 않음) |
| **접근통제 게이트** | 로그인하지 않으면 **DB 권한 자체가 없어** 데이터를 받을 수 없다 | **BY-09(상세)는 이쪽으로 설계한다.** GAP-1 해소(D-S3: 뷰 분리)가 전제조건 |

> 이 결정은 대표/product-manager가 이미 "로그인 필요"라고 명시했으므로(D-3′) **접근통제로 구현하는 것이 기본값**이라고 판단했다. 만약 실제로는 "가입 유도 목적의 UX 장치일 뿐, 데이터 자체는 민감하지 않다"는 의도였다면 GAP-1을 굳이 안 고쳐도 되므로 — **이 판단 자체를 product-manager/privacy-security-officer가 재확인**해달라(§10 OQ-B2).

### 1.5 용어

PRD §3.0 OQ-6에 따라 "파트너"를 쓴다. 사용자 지칭은 "바이어" 또는 2인칭("고객님" 대신 서비스 톤에 맞는 문구는 ui-ux-designer/ux-writer 결정).

### 1.6 로케일 범위 (확인 필요 항목, D-S6과 연결)

PRD는 FKP(D-2)는 "en/ja 현행 유지"라고 명시했지만, **SEEPN 바이어 웹(P5a)의 UI 로케일 범위를 명시적으로 정하지 않았다.** D-3가 "SEEPN은 국내+해외 바이어 포괄"이라고 한 점, TR-4″-2 논의가 "SEEPN 바이어에게 en/ja로 보여줘야" 한다고 전제한 점을 볼 때 최소 en/ja는 필요해 보이고, "국내 바이어"가 포함된다면 ko도 필요하다. 이 문서는 **ko/en/ja 3로케일 대응 가능하게 설계**하되(`content_translation`/`standard_category_translation` 패턴이 이미 이 3개 로케일 체계이므로 구조적으로 자연스러움), 실제로 P5a 배포 시 몇 개 로케일을 켤지는 **product-manager 확인 필요(§10 OQ-B3)**로 남긴다.

**단, 파트너 원문 텍스트(회사소개 등)는 다르다** — TR-4″-2b가 사용자 생성 콘텐츠 자동번역의 4개 선행조건(전용 번역 스키마/소비 화면/국외이전 검토/본인 검수 경로) 중 "소비 화면"만 P5a로 충족되고 나머지 3개는 **여전히 미해소**다. 즉 **UI 문구는 ko/en/ja를 지원해도, 파트너가 입력한 회사소개·레퍼런스 원문은 번역되지 않고 원문 그대로(대개 ko) 노출된다.** BY-09가 이걸 명시적으로 표시해야 한다(§6.2).

**복귀 URL 처리 (B-17의 실체, SP-14)**: 로그인/가입 진입 시 항상 `?redirect=` 파라미터로 원래 목적지를 들고 다닌다. 로그인 성공 시 해당 URL로, 없으면 `/seepn/partners`로 이동한다. **관심등록 게이트**의 경우 단순 URL 복귀로는 "찜 액션"까지 재현되지 않으므로 `?redirect=/seepn/partners/[id]&action=bookmark` 형태로 액션 의도까지 함께 실어 보내고, 로그인 직후 상세 페이지가 이 쿼리를 보고 자동으로 찜 토글을 1회 실행한다(§9 EDGE-B7 — 실패 시 처리 포함).

| 항목 | 내용 |

> **로케일 문서 부재 리스크**: BY-02는 P5a DoD의 실질적 선행조건이다 — 약관 문서가 없으면 화면 자체를 열 수 없다(placeholder로 열 수는 있으나 실서비스 배포 불가). `/supplier`의 SUP-02가 "문서 본문 미작성 상태(플레이스홀더)"로 동일한 리스크를 이미 안고 있었던 전례를 볼 때, **이 작업도 문서 작성이 화면 개발과 병렬로 반드시 필요**하다 — product-manager/법무 검토 트리거로 명시(§10 OQ-B4).

### 3.3 BY-03 회원가입 Step2 — 계정정보

| 필드 | 필수 | 비고 |
|---|:---:|---|
| 표시명(`display_name`) | ✅ | "이름 또는 회사명" 정도로 자유 — 문의 화면(BY-11)에 표시되는 발신자명으로 재사용됨(INQ-3, 새 PII 수집면 회피 원칙) |
| 이메일 | ✅ | 로그인 ID + **연락처(INQ-3의 "계정에 있는 것") 자체가 된다** — 별도 phone 필드는 **v1.0에서 받지 않는다**(§10 OQ-B5, 아래 근거) |
| 비밀번호/확인 | ✅ | 최소 12자, `/supplier`와 동일 전역 정책 |
| 허니팟 | — | 동일 패턴 재사용 |

> **연락처 필드를 이메일 하나로 제한하는 이유**: PRD INQ-3의 목표가 "신규 PII 수집면을 만들지 않는 것"이다. 이메일은 로그인에 어차피 필수이므로 추가 수집이 아니지만, 전화번호를 추가로 받으면 그 자체가 **새로운 PII 수집면**이 되어 INQ-3의 취지와 충돌한다. 따라서 **운영자 문의(BY-11)의 회신 채널은 이메일만 전제**한다. 전화 회신이 필요하면 문의 본문(자유 텍스트)에 바이어가 스스로 남기는 방식으로 충분하다(단, 이는 INQ-4가 이미 예견한 "본문에 PII가 들어올 수 있음" 상황 그 자체다 — §7.3 참고).

### 3.4 `POST /api/seepn/signup`

`POST /api/partner/signup`과 동일 계약 형태(§7 참고), 대상만 `finalize_buyer_signup(p_auth_user_id, p_display_name, p_consents, p_locale)`(신규 RPC, backend-developer 설계)로 바뀐다. **"Confirm email" 등 Auth 프로젝트 설정은 파트너와 공유**하므로 SUP-03/04의 EDGE-3와 동일한 이중 방어가 필요하다.

### 3.5~3.7 BY-04/05/06/07

SUP-04/05/06/07과 완전히 동일한 구조(안내 문구의 "파트너"→"바이어/SEEPN" 치환, 대상 RPC/테이블만 buyer 계열로 치환). 반복 기술 생략 — frontend-developer는 `/supplier`의 해당 화면을 그대로 포크해서 문구/대상만 바꾸는 것으로 충분하다.

| 필터 결과 0건(전체는 있음) | "조건에 맞는 파트너가 없습니다" + "필터 초기화" 버튼(§5 필터-empty state, 전체-empty state와 톤 다름) |
| 전체 공개 파트너 0~5곳(D-13②) | §5 전용 empty state |
| 쿼리 실패(네트워크/서버 에러) | "목록을 불러오지 못했습니다" + 재시도 버튼 |

### 4.2 카테고리 0건 필터 문제 대응 (D-S4)

**문제**: 표준 카테고리 마스터는 ~374~380노드(L0~L3)인데 공개 파트너는 최대 수백 곳 수준이라 **대부분의 리프 노드가 0건**이다(§0의 GAP-2 해소를 전제로 한 설계).

**방식 — "숨김"이 아니라 "동적 필터링 + 배지"를 기본으로 하되, 레벨별로 다르게 처리한다**:

| 레벨 | 처리 | 이유 |
|---|---|---|
| L1(대분류, ~20개) | **전부 표시**, 0건이어도 숨기지 않고 옅게 표시 + "(0)" 배지, 클릭 비활성화(disabled, 클릭 시 "아직 등록된 파트너가 없습니다" 툴팁) | L1 자체를 숨기면 "이 카테고리는 SEEPN에 아예 없다"는 오해를 주고 특정 버티컬(예: 제품 계열) 전체가 안 보이는 것처럼 느껴질 수 있음 — 서비스 전체 스코프를 보여주는 것이 우선 |
| L2/L3(세부, 리프 근처) | **0건 노드는 드릴다운 목록에서 아예 표시하지 않는다**(숨김) | 여기서까지 0건을 다 보여주면 스크롤이 압도적으로 길어지고(374개 대부분) "골라도 빈 화면"이 반복됨(PM이 지적한 실제 위험) — 리프 레벨은 "실제로 고를 수 있는 것"만 보여주는 것이 탐색 경험상 낫다 |
| 카운트 집계 | **쿼리 시점 실시간 집계**(캐시 없이 시작, 트래픽이 유의미해지면 materialized view/캐시 도입 검토 — v1.0은 파트너 수가 적어 실시간 집계 비용이 낮음) | `partner_category_public` 뷰(GAP-2 해소안) 기준 `group by standard_category_id` |
| 필터 조합 결과 0건 | 카테고리+지역+언어 등 **조합**이 0건일 수 있음(개별 카테고리는 1건 이상이어도) — 이 경우는 §4.1의 "필터 결과 0건" 표준 empty state로 처리, 카테고리 트리 자체를 다시 손보지 않음 | 조합 단위까지 실시간으로 반영하면 트리가 필터를 바꿀 때마다 재계산돼야 해서 v1.0에서는 과함 — **카테고리 트리의 카운트는 "다른 필터 미적용 상태의 순수 카테고리별 건수"** 로 단순화(확인 필요, §10 OQ-B6) |

> **UX 세부는 ui-ux-designer 재량**(PRD SP-11이 명시적으로 이 문서의 임무로 넘긴 항목) — 이 문서는 "L1은 배지로 보여주고 L2/L3는 숨긴다"는 **정책**까지만 확정한다.

### 4.3 empty state — 필터 없이도 전체가 0~5곳인 경우

§5에서 별도로 다룬다(요청 5번 항목, D-13② 신규 요구사항).

## 5. Empty State 설계 (D-13②, 공개 파트너 0~소수)

**전제**: 최소 개수 게이트가 없으므로(D-13②) 이 상태가 **실제로 배포된다.** "준비 중입니다"류의 정적 문구는 PRD가 명시적으로 금지한 방향이다(SP-11: "파트너 가입 유도 + 문의 경로로 채울 것").

### 5.1 전체 0곳 (목록 자체가 비어 있음)

| 구성요소 | 내용 |
|---|---|
| 헤드카피 | "지금 SEEPN에 파트너를 모으고 있습니다" (또는 유사 — ux-writer 확정) — "비어 있다"를 부정적으로 프레이밍하지 않고 **성장 중인 상태**로 프레이밍 |
| CTA 1 | **"한국 파트너이신가요? 지금 등록하기"** → `/supplier/signup`(파트너 자가등록, 도메인이 다르면 절대경로) — 공급 확보 유도(§4.3.1의 "P5a가 200곳 온보딩의 전환 자산" 논리와 직결) |
| CTA 2 | **"원하는 파트너를 찾고 계신가요? 문의를 남겨주세요"** → 로그인 필요 시 게이트를 거쳐 BY-11로. 이 경우 **참조 파트너 없이** 문의가 발생하므로 D-S5("문의는 항상 파트너 1건 참조")와 충돌한다 — **이 시나리오만 예외적으로 참조 파트너 0건을 허용해야 하는지 PM 확인 필요**(§10 OQ-B8). 대안: FKP 요청 폼(`/[locale]/request`)으로 안내(OQ-14 원문에서 검토했던 경로, PM이 "채택 안 함"이라 명시했지만 그건 "목록 검색 이후"의 정책이지 "목록이 아예 비어 있을 때"는 별도로 열어둘 여지가 있음 — 판단은 PM 몫) |
| 카테고리 필터 | 비활성 표시(모든 노드 "(0)") 또는 필터 UI 자체를 숨기고 안내만 표시 — ui-ux-designer 결정 |

### 5.2 전체 1~5곳 (희소 상태)

| 구성요소 | 내용 |
|---|---|
| 목록 상단 배너 | "지금 {N}곳의 파트너가 있습니다. 계속 추가되고 있어요" — 5.1보다는 덜 방어적인 톤(실제 콘텐츠가 존재하므로) |
| CTA | 5.1과 동일한 2종(파트너 등록 유도 + 문의 유도) 배너 형태로 목록 하단에 유지 |
| 카테고리 필터 | §4.2 그대로(대부분 0건 배지가 될 것) |

### 5.3 필터 결과 0건 (전체는 존재)

§4.1에서 이미 정의 — "조건에 맞는 파트너가 없습니다" + 필터 초기화. **5.1/5.2와 다른 톤**(전체가 없는 것과 "당신이 고른 조건"이 안 맞는 것은 사용자에게 주는 인상이 달라야 한다).

### 6.3 상세 화면 액션 배치 (요청 6번 항목 — 관심등록 + 운영자 문의)

D-13③이 확정한 "관심등록 + 회원가입 유도 + 운영자 문의" 3종 액션 중, **BY-09(상세)는 이미 로그인된 상태에서만 도달**하므로 실제로 이 화면에 놓이는 액션은 2개뿐이다(회원가입 유도는 상세 진입 자체가 게이트이므로 "도달 이전"에 이미 소진됨).

```
┌───────────────────────────────────────────┐
│ [회사명]                     [♡ 관심등록]  │  ← 헤더 우측 고정, 토글형(찜/찜해제)
│ 지역 · 버티컬 · 대응언어 배지                │
├───────────────────────────────────────────┤
│  ... 본문(회사소개/제품·서비스/역량 필드) ...  │
├───────────────────────────────────────────┤
│         [운영자에게 문의하기]  (하단 고정 CTA) │  ← 스크롤 내내 노출(sticky) 권고
└───────────────────────────────────────────┘
```

| 배치 | 근거 |
|---|---|
| 관심등록 = **헤더에 상시 노출, 토글형 아이콘** | 목록 카드의 찜 아이콘과 시각적 일관성(같은 상태를 다른 화면에서 다시 확인) — 클릭 즉시 반영(낙관적 업데이트) + 실패 시 롤백 |
| 운영자 문의 = **본문 하단 sticky CTA(버튼형, 아이콘 아님)** | 관심등록보다 무거운 행동(폼 진입)이므로 아이콘이 아니라 명시적 버튼. 본문을 다 읽고 나서도 놓치지 않도록 sticky 권고(ui-ux-designer 확정) |
| 둘 다 로그인 이후에만 보이는 화면이므로 별도 게이트 카피 불필요 | BY-09 진입 자체가 이미 로그인 게이트를 통과한 상태 |

> **확인 필요(§10 OQ-B10)**: "문의 내역 보기"는 PRD가 명시적으로 요구하지 않았지만, INQ 스키마가 이미 `status`를 갖도록 설계돼 있어(§0) **구현 비용이 거의 0**이고(본인 행 self-select RLS 하나) 없으면 "문의가 실제로 접수됐는지 확인할 방법이 없다"는 불만이 발생할 수 있다. **Should로 권고**하되 product-manager 확정 필요 — 절대 "스레드형 대화"(답장 가능한 대화창)로 확장하지 않는다(Out of Scope 유지, §5 PRD 표).

### 7.4 `seepn_inquiry` — 화면이 요구하는 최소 입력/출력 (backend-developer 설계 입력)

정확한 컬럼·제약은 backend-developer 소관(PRD 원칙)이지만, **화면이 실제로 필요로 하는 최소 계약**은 아래와 같다.

**입력(바이어 → 서버, `create_seepn_inquiry` RPC)**
```
p_partner_id: uuid (필수, D-S5로 항상 정확히 1건)
p_body: text (필수, 20~2000자)
```
- 발신자(연락처)는 **파라미터로 받지 않는다** — 서버가 `auth.uid()` → `buyer_account`/`auth.users.email`에서 조회(INQ-3).
- 카테고리/예산/납기 등 구조화 필드 파라미터는 **존재해서는 안 된다**(SP-13 경계).

**출력(서버 → 바이어, 문의 내역 화면)**
```
id, partner_id, partner_company_name_ko (조인),
body, status ('new'|'in_progress'|'closed'),
created_at, updated_at
```
- 담당 운영자 식별자는 **바이어에게 노출하지 않는다**(내부 배정 정보).

**Admin 측 최소 출력(BY-A1, §8)**
```
id, buyer_display_name, buyer_email(마스킹, PR-1 준하는 원칙 — INQ-4),
partner_id, partner_company_name_ko,
body, status, assigned_admin, created_at
```
