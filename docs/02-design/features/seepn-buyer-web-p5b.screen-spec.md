## 1. SP-12 답변 — 버티컬 분기 정책 (D-C1)

**질문**: product와 service를 한 표에 담을 수 있게 할 것인가, 비교 진입 자체를 동일 버티컬로 제한할 것인가.

**결정: 동일 버티컬 내에서만 비교를 허용한다.** 두 버티컬을 한 표에 놓는 대안은 채택하지 않는다.

**근거**:

| 근거 | 설명 |
|---|---|
| 필드 중첩이 거의 없다 | PRD §3.2.2(B) Vertical A(제품) 필수 필드: **MOQ, 리드타임**(권장: 단가밴드/샘플가능여부/수출실적), 필수 **OEM/ODM/자사브랜드 구분**. §3.2.2(C) Vertical B(서비스) 필수 필드: **서비스 유형, 프로젝트 최소 규모/가격 산정 방식, 표준 리드타임/착수 가능 시점, 대표 레퍼런스 프로젝트**(권장: 팀규모/원격·온사이트). **7개 핵심 비교축 중 겹치는 것이 0개**다 — "리드타임"조차 제품은 "납기일수"(`lead_time_days`), 서비스는 "착수 가능 시점"(`standard_lead_time`)으로 성격이 다르다 |
| 코드가 이미 이 경계로 나뉘어 있다 | BY-09(상세, P5a) 자체가 `partner.vertical === 'product'` / `=== 'service'`로 섹션 전체를 분기해서 렌더링한다(`app/seepn/partners/[id]/page.tsx` L153/L197). 상세에서 이미 "둘은 다른 모양의 데이터"로 취급하고 있는데, 비교표에서만 한 표로 합치면 **상세와 비교의 정보구조가 서로 다른 모델을 갖게 된다** |
| "공통 코어만 비교"도 기각 | 대안으로 "공통 코어(회사명/지역/언어/해외경험 등)만 한 표에 놓고 나머지는 각자 표시"를 검토했으나, **비교가 필요한 이유 자체가 거래조건 축(MOQ vs 프로젝트 규모 등)을 나란히 보기 위함**이므로 공통 코어만 비교하면 비교의 존재 이유가 사라진다. 기각 |
| PM의 "절반이 N/A" 우려가 현실적 리스크 | 5개를 담았는데 2개는 product, 3개는 service이면 표의 절반 이상 셀이 항상 비어 있는 채로 보인다 — §4.3의 "정보 없음" 정책과 겹치면 **"이 서비스는 데이터가 부실하다"는 오해**를 주기 쉽다. 버티컬을 분리하면 이 리스크 자체가 발생하지 않는다 |

**분리 방식**: 화면 레벨에서 강제한다(§3 BY-13의 체크박스 비활성화 + §5 서버 재검증). DB 레벨 제약(예: 비교 테이블에 CHECK 제약)은 두지 않는다 — 비교는 상태를 영속 저장하지 않는 휘발성 조합(URL 파라미터)이므로 DB 제약의 대상이 아니다.

## 3. BY-13 — 비교 후보 선택 (BY-10 관심목록 확장)

**변경 대상**: `components/seepn/BookmarksListClient.tsx`. 기존 컴포넌트에 "선택 모드"를 얹는다(신규 페이지 아님).

| 구성요소 | 동작 | 상태별 표시 |
|---|---|---|
| "비교하기" 토글 버튼(목록 상단) | 클릭 시 카드에 체크박스 노출(선택 모드 진입) | 관심목록이 **2곳 미만**이면 버튼 비활성 + 툴팁("비교하려면 관심등록을 2곳 이상 해주세요") — §5 EDGE-C3 |
| 카드 체크박스 | 클릭 시 선택/해제 | 이미 5개 선택된 상태에서 6번째 클릭 → **비활성 + 토스트** "비교는 최대 5곳까지 가능합니다"(EDGE-C1) |
| 버티컬 불일치 카드 | 이미 선택된 항목과 `vertical`이 다르면 체크박스 자체를 비활성 | 툴팁: "제품 파트너와 서비스 파트너는 함께 비교할 수 없습니다"(EDGE-C2, D-C1) — 선택 항목이 0개일 때는 전부 활성 |
| 비공개 전환된 카드(EDGE-B5, `partner: null`) | 체크박스 비활성 | 이미 BY-10에 있는 "현재 비공개 상태인 파트너입니다" placeholder와 동일 — 애초에 비교 대상이 될 수 없음 |
| 하단 sticky 바(선택 모드 중) | "N곳 선택됨 · 비교하기" | N<2면 버튼 비활성. N≥2면 클릭 시 `/seepn/compare?ids=<선택id들 콤마구분>`으로 이동 |
| "선택 취소" | 선택 모드 종료, 체크박스 숨김 | 선택 상태는 페이지 이탈 시 유지하지 않음(휘발성 — D-C2와 일관) |

> **v1.0에서 만들지 않는 것(명시적 범위 제외)**: 목록(BY-08)·상세(BY-09)에서의 별도 "비교 담기" 액션. D-C2 근거. 이후 관심등록 행동 데이터를 보고 "목록에서 바로 담고 싶다"는 수요가 확인되면 Should로 재검토(§10 OQ-C1).

### 4.3 빈 필드 표시 (SP-12 두 번째 질문 답변, D-C4)

| 정책 | 내용 |
|---|---|
| 표시 방식 | 값이 `null`/빈 배열인 셀은 **"정보 없음"**(회색, 본문보다 옅은 톤)으로 명시적으로 표시. 빈칸이나 "-"만 쓰지 않는다 — 리드타임 등 **숫자 필드에서 "-"는 "0"과 혼동**될 수 있어 반드시 문구로 구분 |
| 집계 퍼센트(`capability_completeness_pct`) 노출 | **하지 않는다.** 이유 3가지: ① 애초에 두 공개 뷰 어디에도 이 컬럼이 없다(GAP-C2, BP-12 결정) — 노출하려면 이미 내려진 privacy 결정을 재여는 것. ② 완성도는 "데이터 입력량"이지 "품질"이 아닌데, 숫자로 보여주면 바이어가 **품질 순위처럼 오독**할 위험이 크다. ③ M-R12("임의 생성 숫자로 순위를 암시하지 않는다")의 정신에 어긋난다 — B-12d(점수 랭킹)를 P7까지 안 여는 것과 같은 논리를 비교표에도 일관 적용 |
| 대안(Could, 선택) | 집계 퍼센트 대신 **이미 화면에 내려받은 필드만으로 클라이언트에서 계산한 "표시 가능 항목 N/M개"** 캡션은 허용 가능(신규 컬럼·재검토 불필요, 이미 받은 데이터의 null 개수를 세는 것뿐). 숫자를 굳이 넣을지는 ux-writer/PM 재량 — §10 OQ-C4 |
| 그룹 전체가 비는 경우 | 권장 필드 다수가 비어 특정 그룹(예: "수출 실적")이 전 후보 공통으로 비어 있어도 **행 자체를 숨기지 않는다** — 비교의 목적은 "차이"를 보여주는 것이고, 전원이 비어 있다는 것도 하나의 정보다 |

## 6. BY-15 — 비교 화면에서의 운영자 문의 (B-18 × B-12b 연동)

### 6.1 설계 원칙 (SP-13 경계 승계)

PRD §3.1.5(2)의 B-11 경계는 **문의에 적용되는 것이지 "몇 건을 참조하는가"와 무관**하다. 즉 이번 변경은 **"참조 파트너가 1건에서 최대 5건으로 늘어나는 것"뿐**이며, 절대로 다음을 추가하지 않는다:
- 카테고리/예산/납기 등 구조화 필드 — 여전히 금지(SP-13)
- 문의자 연락처 입력 필드 — 여전히 계정에서 가져옴(INQ-3)

### 6.2 필요한 스키마 변경 (GAP-C1 해소안 — backend-developer 설계 입력)

**현재(P5a, 그대로 둘 수 없음)**: `seepn_inquiry.partner_id uuid not null` (1건 고정), `create_seepn_inquiry(p_partner_id uuid, p_body text)`.

**제안 방향**(정확한 스키마는 backend-developer 소관, 화면이 요구하는 최소 계약만 정의):

| 항목 | 요건 |
|---|---|
| 참조 관계 | `partner_id` 단일 컬럼 → **파트너 참조 1~5건을 저장할 수 있는 구조**로 변경(조인 테이블 `seepn_inquiry_partner(inquiry_id, partner_id)` 신설 + 기존 `seepn_inquiry.partner_id` 백필/이관, 또는 backend-developer가 판단하는 동등한 대안) |
| RPC | 기존 `create_seepn_inquiry(p_partner_id uuid, p_body text)`를 **`create_seepn_inquiry(p_partner_ids uuid[], p_body text)`로 일반화**하고, 배열 길이 1~5를 검증. **BY-11(P5a, 단건)은 새 RPC에 `[partnerId]` 1개짜리 배열을 넘기는 것으로 계속 동작**시켜 RPC를 이원화하지 않는다 |
| 프런트 | `InquiryForm` 컴포넌트를 `partnerId: string` → `partnerIds: string[]` prop으로 일반화. 참조 파트너 표시 영역이 단일 카드 → **최대 5개 카드 목록**(읽기전용, D-S5의 "변경 불가" 원칙은 유지 — 비교표로 돌아가서 다시 골라야 함) |
| 레이트리밋(INQ-6) | 다중 참조 문의 **1건 제출 = 레이트리밋 1건**으로 계산(참조 파트너 수와 무관) — 비교 후 한 번에 문의하는 행동을 페널티 주지 않기 위함(§10 OQ-C6 — backend-developer 확인) |
| Admin 소비 화면(BY-A1) | 문의 상세에 참조 파트너가 **1~5개 칩/링크**로 표시되도록 수정 필요(기존엔 1개 전제) — INQ-5 확장, D-5 원칙(신규 메뉴 아님) 그대로 유지 |
| 감사(INQ-7) | 다건 참조도 **문의 1건 생성 = 감사 로그 1건**(참조 파트너 목록은 `p_target_id`에 준하는 필드나 별도 상세 조회로 확인 가능하게, 감사 로그 자체를 파트너 수만큼 늘리지 않음) |

## 7. B-12e — 운영자 큐레이션 "추천 파트너"

### 7.1 배치 판단: 비교와 독립된 목록 상단 섹션 (D-C6)

| 검토한 대안 | 판정 | 이유 |
|---|---|---|
| 비교 화면(BY-14) 전용 기능 | **기각** | 비교는 바이어가 이미 2곳 이상을 관심등록한 **후반 단계** 사용자만 도달한다. B-12e의 목적("대표가 원하는 '랭킹의 체감'을 데이터 없이 정직하게 제공")은 **가장 이른 단계(첫 목록 진입)**에서 체감돼야 효과가 있다 — 후반 단계에 숨겨두면 정의된 목적을 달성하지 못한다 |
| **목록(BY-08) 상단 독립 섹션(채택)** | **채택** | 비로그인도 볼 수 있고(BY-08은 비로그인 접근 가능), 필터를 아직 안 걸었을 때도 노출되므로 "SEEPN에 좋은 파트너들이 이미 있다"는 첫인상을 만든다 |
| 비교표 안에 "운영자 선정" 배지만 부가 | **Could로 채택**(부가 기능) | 비교 중인 파트너가 마침 추천 파트너이기도 하면, 이미 내려받은 flag를 재사용해 열 헤더에 작은 배지만 추가 — 신규 비용 없음 |

### 7.2 BY-16 화면 정의 (BY-08 확장)

| 구성요소 | 동작 | 상태 |
|---|---|---|
| "운영자 선정" 섹션(목록 최상단, 일반 결과 그리드 위) | 관리자가 지정한 파트너를 노출 | 추천 파트너가 0곳이면 섹션 자체를 숨김(EmptyAll과 별개 — "준비 중" 문구조차 필요 없음, 그냥 안 보이면 됨) |
| 필터와의 관계 | **현재 필터 조건과 무관하게 항상 같은 세트를 보여주지 않는다** — 활성 필터(버티컬/카테고리/지역 등)에 매칭되는 추천 파트너만 이 섹션에 남긴다 | 필터를 걸었는데 추천 파트너가 섹션에 그대로 남아 있으면 "내가 고른 조건과 안 맞는데 왜 추천됐지"라는 혼란을 줄 수 있음 — 필터 순응을 기본값으로 함(§10 OQ-C4에서 대안 열어둠) |
| 라벨링(M-R12 승계, **필수 준수**) | **"운영자 선정"**(또는 동급 문구, ux-writer 확정) 배지만 표시 | **순위 숫자·점수·"TOP" 같은 서수 표현을 절대 붙이지 않는다.** 노출 순서는 관리자가 정한 순서(§7.3 `display_order`)를 따르되, **화면에는 그 순서를 "1위/2위"로 드러내지 않는다** — 그냥 나열 순서일 뿐 |
| 카드 컴포넌트 | 기존 `PartnerCard` 재사용 + 배지 하나 추가(신규 컴포넌트 아님) | — |

### 7.3 BY-A2 — Admin 추천 파트너 지정 (신규 Admin 기능, 범위 포함 판단)

**판단: 필요하다.** 사람이 고르는 기능인 이상 "고르는 화면" 없이는 운영이 불가능하므로 Admin 측 신규 기능을 범위에 포함한다. 단 D-5 원칙("신규 Admin 앱/메뉴 신설 금지, 기존 메뉴 위에 추가")을 그대로 따라 **새 최상위 메뉴를 만들지 않는다.**

| 항목 | 설계 |
|---|---|
| 배치 | `/admin/partners/[id]` 상세의 기존 액션 영역에 **"추천 파트너로 지정" 토글 버튼**을 추가(공개 전환 토글 `partner_set_public_listing`과 나란히, 같은 UI 패턴 재사용) |
| 목록 측 보조 화면 | `/admin/partners` 목록에 "추천 파트너만 보기" 필터(기존 정렬/필터 UI 패턴 재사용, L124~126 코드와 동일한 형태) — 전용 신규 화면 대신 **기존 화면의 필터 옵션 1개 추가**로 최소화 |
| 데이터 모델(제안, backend-developer 최종 결정) | boolean 플래그 단독보다 **소형 테이블**을 권고: `partner_featured_pick(id, partner_id, display_order, active, picked_by admin_id, picked_at)`. 이유: ① M-R12가 요구하는 "누가/언제 골랐는가"의 감사 추적을 boolean 하나로는 남길 수 없다. ② 이 저장소의 기존 관례(동의·감사 로그 전부 "누가/언제"를 구조화)와 일관 |
| 노출 게이트 상속 (**필수, EDGE-C11**) | 추천 지정 테이블은 **`partner_list_public`(또는 그 기반 뷰)이 이미 통과한 3계층 게이트(공개+검증+동의)를 그대로 상속**해야 한다 — 추천 지정이 게이트를 우회하는 별도 경로가 되면 안 됨. 즉 BY-16 조회는 "추천 테이블 ∩ `partner_list_public`"이어야 하며 "추천 테이블 단독"으로 조회하면 안 됨 |
| 개수 상한 | DB 하드 제약은 두지 않되, **Admin UI에서 권고 문구**("추천 파트너는 6~8곳 내외를 권장합니다 — 너무 많아지면 '선정'의 의미가 옅어집니다")로 소프트 가이드 — 정확한 상한은 PM 확인(§10 OQ-C4) |
