## 1. UI-B5 — 파기 워커 부재

### (a) 결정 / 권고

**Go. 즉시 착수하되, privacy officer가 잡은 게이트 시점("가입 오픈 전")을 한 단계 앞으로 당긴다 — `P1(Admin 파트너 관리) 프로덕션 배포 전`.**

backend-developer 작업 범위에 포함시킨다. **첫 티켓으로 잡아라.**

### (b) 근거

1. **이 문제는 파트너 가입 오픈보다 먼저 터진다.** 워커가 소비하지 못하는 큐는 셋인데, 그중 둘(`partner_doc_purge` 검증 후 90일, `partner_rejected_purge` 반려 후 90일)과 기준선 §3.5의 `consent_deadline_at` 파기는 **`admin_entry` 아웃리치 데이터에도 그대로 적용된다.** 파트너 자가등록을 한 명도 받지 않아도, PRD §4.2의 W1(파트너 30~50곳 Admin 입력)을 실행하는 순간 파기 의무가 시작된다. privacy officer가 "가입 오픈 전"으로 잡은 것은 이 문서의 범위가 `/supplier` 화면이기 때문이고, 회사 리스크 관점에서는 그보다 앞이다.
2. **지금이 가장 싼 시점이다.** 파트너 스키마(`20260829130000`~`20260829180000`)와 Admin 파트너 화면은 **아직 커밋조차 되지 않았다**(작업트리 미커밋 58건, 해당 마이그레이션 전부 untracked). 즉 프로덕션에 파트너 실데이터가 0건이고, **지금 워커를 넣으면 소급 처리할 데이터가 없다.** 오픈 후에 넣으면 이미 파기시한을 넘긴 데이터를 뒤늦게 지우게 되고, 그 지연 이력 자체가 증거로 남는다.
3. **방어가 불가능한 유형이다.** "고지한 대로 파기하지 않았다"는 코드 한 줄로 확인되고, 우리는 마이그레이션 주석(1882~1887행)에 이 gap을 **스스로 적어 두었다.** 인지하고도 방치했다는 기록이 된다. 반대편 비용은 스케줄 라우트 하나다. 이건 트레이드오프가 아니다.

### (c) backend 착수 차단 여부

**차단하지 않는다.** 단 **순서 조건**을 건다 — SUP-14 탈퇴 모달에 "첨부 문서가 삭제됩니다"를 **화면에 그리는 작업은 워커가 머지된 뒤에 한다.** 스펙에 없는 약속을 화면에 먼저 그리는 것이 애초에 이 사고가 만들어진 경로다. 워커 전에는 §5.3 확정 문구에서 해당 줄을 빼고 간다.

### Next action

- **backend-developer**: `/supplier` 백엔드 첫 티켓 = 파기 워커. `pending_deletion_at is not null` 폴링 → `storage.remove()` → `delete from partner_document`, 실행 결과를 `retention_jobs`에 기록(§5.1 권장 조치 그대로). **UI-B6(개인사업자 익명화)는 `purge_unconsented_partner_pii()`의 UPDATE 블록 재사용이므로 같은 티켓에 묶는다.**
- §5.1의 **임시 대안(탈퇴 라우트 동기 삭제)을 단독 채택하지 말 것.** 탈퇴 경로만 정직해지고 90일 배치 2건은 여전히 미이행이라 반쪽이다. 워커 일정이 밀릴 때의 보험으로만 쓴다.
- **project-manager**: P1 DoD 체크리스트(UI 검토 §9)의 "탈퇴 후 Storage 객체가 실제로 존재하지 않음" 항목을 **P1 배포 게이트로 이동**.

## 2. UI-B10 — BRN 중복확인의 영업 파이프라인 노출

### (a) 결정 / 권고

**기능 제거는 No-Go. 레이트리밋(1일 10회) + 중립 문구는 Go. 다만 레이트리밋만으로 끝내지 않는다 — 조회 범위 축소를 함께 검토한다.**

### (b) 근거

1. **기능을 빼면 안 되는 이유 — 이건 개인정보 장치가 아니라 데이터 품질 장치다.** 같은 회사가 두 번 등록되면 매칭 후보가 오염되고, 그 정리 비용을 우리가 진다(북극성 지표가 매칭이다, PRD §1.3). 자가등록을 켜는 순간 중복 유입을 입력 시점에 막는 것이 가장 싸다. 30~50곳 규모의 수동 정리는 지금이니까 가능한 것이고, 자가등록은 그 전제를 없애려고 하는 일이다.
2. **그러나 1일 10회는 대량 크롤을 막는 장치이지 표적 조회를 막는 장치가 아니다.** 경쟁사가 정말 알고 싶은 것은 전량이 아니라 "SEEPN이 접촉 중인 상위 20~30곳"이다. 그 정도는 계정 2~3개로 며칠이면 확인된다. privacy officer의 "열거는 실효적으로 불가능해진다"는 **전수 열거에 대해서는 맞고, 표적 조회에 대해서는 과한 낙관이다.**
3. **근본 조치의 비용이 거의 같다.** `check_business_registration_duplicate`가 보는 범위를 `public.partner` 전체가 아니라 **자가등록 경로에서 실제로 충돌이 나는 행**(파트너 계정이 연결되어 있거나 `verified`인 행)으로 좁히고, `admin_entry` 아웃리치 draft는 `true`를 반환하지 않게 한다. 중복 방지 목적은 그대로 달성되고, 영업 파이프라인은 boolean으로 새지 않는다. 아웃리치 대상이 직접 가입해 오는 케이스는 운영자 병합으로 처리하면 된다 — **D-6이 오프라인 인력의 역할을 "가입 권유"로 재정의한 이상, 접촉 중인 회사가 스스로 가입하러 오는 것은 충돌이 아니라 성공 경로다.**

### (c) backend 착수 차단 여부

**차단하지 않는다.** §8 매핑표대로 **SUP-09 화면 착수만** 이 결정에 종속된다. 서버 라우트와 문구는 backend가 만들면서 확정하면 된다.

### Next action

- **backend-developer**: `POST /api/partner/check-brn`을 **Must로 구현**(계정당 1일 10회, 초과 호출 감사 기록 — §6.1 표 2·3·4 그대로).
- **backend-developer + privacy-security-officer**: 위 3의 **조회 범위 축소가 기준선 PR-12 / PC-4(중복 경고)와 충돌하는지 1일 내 회신.** 충돌하면 v1.0은 레이트리밋 + 문구만으로 가고 범위 축소는 P2로 넘긴다 — **이 경우 파이프라인 노출은 "완화됐지만 남아 있는 리스크"로 명시적으로 기록한다.** 조용히 해결된 것으로 처리하지 말 것.
- **ux-writer**: §6.1 표 1번 문구 확정. `onBlur` 자동확인은 채택하지 않는다(표 5번).

## 3. CPO 지정과 내부관리계획

### (a) 결정 / 권고

**개발 착수와 완전히 무관하다 — 병행한다. 단 "파트너 가입 오픈 블로커"로는 유지한다.**
**지정 대상 선정은 이 메모가 대신 결정하지 않는다 — 대표가 직접 답해야 할 사항이다(§3 Q-A).**

### (b) 근거

1. **조직 규모를 문서로 단정할 수 없다.** 이 저장소에서 확인되는 사실은 다음이 전부다.
   - 법인 실체는 있다 — YLIA Co., Ltd. (`docs/legal/terms-v1.0-en.md`, `privacy-v1.0-en.md`)
   - **기존 처리방침에 CPO 성명 기재가 없고**, 문의 창구가 대표 개인 이메일 + 개인 휴대폰 단일 채널이다(`docs/legal/privacy-v1.0-en.md` §11)
   - 커밋 히스토리상 개발 주체는 단일 저자(26 커밋, 2026-06~08)
   - PRD는 인력을 "운영자 / 오프라인 인력"으로만 구분하며, 조직도·인원수·예산 문서는 저장소에 없다

   → **전담 CPO를 둘 인력이 있다는 근거도, 없다는 근거도 문서에 없다.** 따라서 "대표 겸임이 유일한 선택지"라고 여기서 단정하지 않는다.
2. **다만 결정 자체의 비용은 0에 가깝고, 미뤄서 얻는 것이 없다.** 채용도 예산도 개발 리소스도 필요 없는 순수 조직 결정이다. 그리고 이것은 기준선 §7.3-3에서 **이미 한 번 지적된 항목의 재확인**이다. 두 번 올라온 항목을 세 번째로 미루면 그건 우선순위 판단이 아니라 방치다.
3. **CPO보다 앞에 있는 항목이 하나 더 있다 — 파트너용 한국어 처리방침이 아예 존재하지 않는다.** `docs/legal/`에는 `en` / `ja` 두 언어뿐이고, 그 대상은 FKP 해외 바이어다. 파트너는 한국 사업자이고 준거법이 PIPA다. 즉 CPO 성명은 "완성된 문서의 빈칸 하나"가 아니라 **아직 착수하지 않은 문서의 한 필드**다. CPO 지정이 늦어지면 그 문서 작성 착수 자체가 늦어지고, **이쪽이 가입 오픈 일정의 실제 임계경로다.** UI-B8(푸터·고객센터)과 `partnerConsentVersions.ts` PLACEHOLDER 제거가 모두 여기에 물려 있다.

### (c) backend 착수 차단 여부

**차단하지 않는다.** 코드 작업이 아니다. 단 **UI-B8(인증 후 셸 푸터·고객센터 경로)은 아래 Q-B 답 없이 착수하면 재작업**이므로, SUP-08 셸 작업 시작 전까지 답이 필요하다.

### 대표가 답해야 할 질문 (추정하지 않는다)

| ID | 질문 | 답할 사람 | 언제까지 |
|---|---|---|---|
| **Q-A** | **CPO를 누구로 지정하는가** — 대표 겸임인가, 별도 지정인가 | **대표** | 파트너용 처리방침 작성 착수 전 |
| **Q-B** | 처리방침·고객센터에 공개할 연락처를 **현행 개인 휴대폰(+82-10-…)으로 유지하는가.** 파트너 가입이 열리면 이 번호가 한국 사업자 대상으로 노출된다 | **대표** | SUP-08 셸 착수 전 (UI-B8 표 2번과 같은 결정이므로 한 번에 답할 것) |
| **Q-C** | **소규모 사업자에 대한 CPO 지정 의무·겸임 범위 특례가 우리에게 적용되는가** | **변호사** | 처리방침 게시 전 |

> Q-C는 이 메모에서 추정하지 않는다. UI 검토 **§10 변호사 검토 목록에 6번 항목으로 추가**한다.

## 4. 착수 조건 정리 (backend-developer 확인용)

**3건 모두 착수를 막지 않는다. 대신 조건 3가지.**

1. **UI-B5 파기 워커의 게이트 시점을 "가입 오픈 전" → "P1 프로덕션 배포 전"으로 상향한다.** backend 첫 티켓, UI-B6 동봉.
2. **SUP-14 모달의 "첨부 문서가 삭제됩니다" 문구는 워커 머지 이후에만 화면에 그린다.** 그 전에는 해당 줄을 뺀다.
3. **Q-A / Q-B는 SUP-08 셸 착수 전까지 대표 답변**, Q-C는 변호사 큐 등록.

**여기서 뒤집지 않는 것**: §8 매핑표의 UI-B3 / UI-B4(구현 착수 전 해소)는 그대로다. SUP-11과 SUP-13은 여전히 착수 보류다.
