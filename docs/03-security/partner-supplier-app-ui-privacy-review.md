## 0. 결론 요약

### 0.1 판정

**두 화면정의서 모두 기준선 문서의 결정(PR-1~PR-16, 3계층 게이트, PII 분리)을 정확히 승계했고, 스키마를 상상으로 채우지 않았다는 점에서 품질이 높다.** 특히 screen-spec §1.2(`private` 스키마 호출 불가), §4.2(BRN 중복검증 위치를 로그인 후로 이동), §4.4(스토리지 선(先)업로드 후(後) 메타 INSERT 순서), ui-spec §3.11(동의값 미확인을 거짓 OFF로 그리지 않는 3-상태 토글)은 이 검토가 지적하려던 것을 이미 스스로 잡아냈다.

**그러나 아래 11건은 배포/오픈 전 반드시 해소해야 한다.** 대부분은 "화면이 사용자에게 약속한 것을 DB가 실제로 하지 않는" 유형이며, 개별 수정 비용은 낮다.

#### 결정

> **탈퇴 시 `auth.users` 행을 즉시 하드 삭제한다. 기준선 PR-9 step 7("auth.users 행은 즉시 삭제하지 않는다")을 본 문서로 정정한다.**

**정정 근거 — 원 판단의 전제가 틀렸다.** PR-9 step 7의 이유는 "① `on delete restrict`로 묶여 있고 ② 감사로그 귀속이 깨진다"였다. ②는 위 사실 (d)로 **성립하지 않는다.** `auth.users` 행을 지워도 감사로그의 행위자 귀속은 `partner_account` 행과 이메일 스냅샷으로 온전히 남는다(이 스냅샷 컬럼이 존재하는 이유가 정확히 "계정 익명화 후에도 귀속 보존"이라고 `20260825120000` 322~323행에 명시되어 있다). ①은 삭제를 막는 사유가 아니라 **삭제 순서를 규정하는 사유**일 뿐이다.

정정 후 남는 것은 원칙뿐이고, 원칙은 명확하다:

- **법 제21조**: 회원 탈퇴로 보유 근거가 소멸하면 지체 없이 파기. 로그인 이메일은 "회원 지위"가 유일한 보유 근거였고 그 근거가 사라졌다. 파트너 계정에는 결제·거래 기록이 없어 전자상거래법상 별도 보존의무가 걸리지 않는다(**변호사 검토 필요** — 계약 관련 기록 5년 보존의무 해당 여부).
- **기준선 PR-5**: `partner_account`는 "탈퇴 시까지", `private.partner_contact`는 "탈퇴 즉시 파기". 이미 담당자 이메일은 즉시 지우면서 로그인 이메일만 무기한 남기는 것은 그 자체로 정합성이 없다.
- **SS-12 정책과의 일치**: "재가입 제한 없음"이 실제로 성립한다.

#### 구현 절차 (`POST /api/partner/withdraw`, service_role — 순서가 곧 안전장치)

```
1. rpc('partner_withdraw', { p_partner_id })                  ← 기존, 변경 없음
2. auth.admin.signOut(auth_user_id, 'global')                 ← 기존 계획(PR-9 step 3)
3. rpc('partner_detach_auth_principal', { p_account_id })     ← 신규, service_role 전용
     - update partner_account set auth_user_id = null, anonymized_at = now()
     - delete from public.auth_principal where auth_user_id = <uid>
     - ※ 새 감사 action 문자열을 쓰지 말 것 — audit_log.action은 고정 CHECK라
       미등록 문자열은 INSERT 실패한다. 기존 'partner.withdraw'에 흡수하거나
       CHECK를 함께 확장할 것
4. auth.admin.deleteUser(auth_user_id)                        ← 신규
5. 3 또는 4 실패 시 보상 경로(필수):
     auth.admin.updateUserById(uid, { ban_duration: '876000h' })로 즉시 무력화 +
     실패 건을 재시도 큐에 남긴다. "실패했지만 사용자에겐 탈퇴 완료로 보이는"
     상태를 방치하지 말 것
```

`p_partner_id`를 인자로 받는 3번 RPC를 만들지 말 것 — 계정 식별자는 서버가 1번의 반환/조회로 확보한 값을 쓰고, RPC는 `service_role`에만 GRANT한다.

#### 기각한 대안

| 대안 | 기각 사유 |
|---|---|
| 이메일에 접미사를 붙여 즉시 반환(`user+withdrawn-{uuid}@…`) | 원본 이메일에서 파생된 식별자가 그대로 남는다 — 파기가 아니라 **파기한 것처럼 보이게 하는 변형**이다. 게다가 GoTrue의 `identities`/`email_change` 잔재 때문에 실제 재사용 가능 여부가 버전 종속적이라 정책 보증을 코드로 담보할 수 없다 |
| 30일 유예 후 hard delete 배치 | 기준선 PR-9이 **명시적으로 기각한 "재가입 제한 30일"을 사실상 도입**하는 것과 동일한 효과다. 또 그 30일 동안 이메일을 보유하는 목적을 설명할 수 없다(어뷰징 방지라면 PR-9이 요구한 HMAC 해시 구조를 써야 하고, 그건 "지금은 만들지 마십시오"로 확정됨) |
| 정책 문서를 "재가입은 고객센터 경유"로 수정 | 파기 의무(법 제21조)를 UX 문구로 덮는 것일 뿐, 탈퇴자 이메일을 무기한 보유하는 문제는 그대로 남는다. **가장 나쁜 선택지** |

| **SUP-14 모달** | "탈퇴 후 재가입 제한은 없습니다 — 같은 이메일로 다시 가입할 수 있습니다"는 **그대로 유효**. 여기에 1줄 추가: `탈퇴하면 로그인 계정(이메일·비밀번호)이 즉시 삭제되며 복구할 수 없습니다.` |
| **SUP-13** | 변경 없음(탈퇴 버튼 위치 유지) |
| **screen-spec §6 EDGE-9** | 항목 전체 재작성 — "auth.users가 남아 재가입이 막힌다"는 서술이 무효가 됨 |

#### 수용하는 잔여 위험

반려된 파트너가 탈퇴 후 즉시 같은 이메일로 재가입해 이력을 세탁할 수 있다. PR-9이 이미 판단한 대로 BRN 중복검증(PC-4)과 검증 큐(A1-R5)가 방어선이며, 파트너 규모(30~50) 대비 실효 리스크가 낮다. **제재 회피 경로는 이미 구조적으로 막혀 있다** — `partner_withdraw()`가 `is_active_partner()`(=`status='active'`)를 요구하므로 `suspended` 계정은 스스로 탈퇴할 수 없다(1593행).

### 1.2 [UI-B2] G-S1 / OQ-S1 — 파트너 본인 동의 이력 조회

#### 권고의 타당성 판정: **타당하다. RPC 신설을 채택한다.**

service-planner의 OQ-S1 권고(좁은 RPC 신설, `get_own_partner_contact` 패턴)는 개인정보 관점에서 옳고, 대안(`partner_consent`에 self-select RLS 정책 추가)은 기각한다.

**RLS 정책 대안을 기각하는 이유:**

1. `public.partner_consent`는 `revoke all ... from anon, authenticated, service_role` + 정책 부재 + **무조건 예외를 던지는 append-only 트리거**(GUC 우회구멍조차 없음, `20260829140000` 724~745행)의 3중 방어 테이블이다. "쓰기도 읽기도 DEFINER RPC만"이라는 단일 규칙이 이 테이블의 방어를 단순하게 유지하고 있다. SELECT 정책 하나를 여는 순간 그 규칙이 깨지고, 이후 누군가 "읽기가 되니 쓰기도"라고 넓힐 여지가 생긴다.
2. SELECT를 열면 컬럼 단위 GRANT를 따로 관리해야 한다. 이 테이블에는 `recorded_by_admin_id`(**다른 정보주체인 운영자의 식별자**)와 `evidence_kind`가 같은 행에 있다.
3. PostgREST로 열면 전체 이력·임의 필터·정렬이 함께 열린다. 필요한 것은 "타입별 최신 1건"인데 노출되는 것은 "전부"가 된다 — 최소 노출 원칙에 반한다.

#### 확정 반환 규격

```sql
public.get_own_partner_consents() returns jsonb
-- 인자 없음(중요: p_partner_id를 받으면 IDOR 표면이 새로 생긴다.
--            get_own_partner_contact()가 인자를 받지 않는 것과 같은 이유)
-- security definer, set search_path = ''
-- 권한 가드: private.is_active_partner(auth.uid()) — get_own_partner_contact와 동일
-- 감사: 하지 않는다(PR-15, 자기정보 접근)
-- 대상 consent_type: 'terms', 'privacy', 'public_listing', 'marketing'
--   ('third_party_share'는 v1.0 미사용이며, 도입 시 매칭 건별 동의라
--    타입 단위로 뭉뚱그리면 안 된다 — 이 RPC에 넣지 말 것)
-- 각 타입별 recorded_at 최신 1행만(철회 = granted=false 새 행이므로
--   최신 행의 granted가 곧 현재 상태)
```

반환 예:
```json
{
  "terms":          { "granted": true,  "collected_at": "2026-09-03T04:12:00Z", "document_version": "partner-terms-v1.0-2026-09" },
  "privacy":        { "granted": true,  "collected_at": "2026-09-03T04:12:00Z", "document_version": "partner-privacy-v1.0-2026-09" },
  "public_listing": { "granted": false, "collected_at": "2026-09-20T02:00:00Z", "document_version": null },
  "marketing":      { "granted": true,  "collected_at": "2026-09-03T04:12:00Z", "document_version": null }
}
```
동의 이력이 없는 타입은 키 자체를 생략한다(`null` 객체를 만들지 말 것 — 프론트에서 "미동의"와 "기록 없음"을 구분할 수 있어야 한다).

#### 필드별 포함/제외 판단 (요청받은 핵심 결정)

| 필드 | 판정 | 근거 |
|---|:---:|---|
| `granted` | **포함** | 토글 렌더의 유일한 필수값. 본인의 의사표시 그 자체 |
| `collected_at` | **포함** | ① 본인의 자기정보이고 새로운 PII를 만들지 않는다. ② 법 제35조 열람권의 실질(언제 동의했는지). ③ **정보통신망법 제50조 제8항 — 수신동의를 받은 날부터 2년마다 수신동의 여부를 확인할 의무**가 있고, 그 재확인 UX("2026-09-03에 동의하셨습니다. 계속 받으시겠습니까?")의 전제가 이 값이다. 마케팅 토글 아래에 `동의일: 2026-09-03`을 표기할 것 |
| `document_version` | **포함** | "무엇에 동의했는가"를 특정하는 유일한 수단. 이 값이 없으면 열람권이 형식적으로만 충족된다. 단 **문자열만** 반환하고, 문서 본문은 프론트가 `docs/legal/<version>-ko.md` 링크로 별도 렌더 |
| `method` | **제외** | `admin_entry` 경로에서는 `'phone'`/`'in_person'`이 들어간다 — 이는 **내부 수집 경로를 드러내는 값**이고, 사칭자가 계정을 탈취했을 때 "이 회사 정보가 어떻게 수집됐는지"를 알아내는 정찰 단서가 된다. 법 제20조(수집 출처 고지)는 **정보주체가 요구하면** 알릴 의무이지 상시 화면 노출 의무가 아니므로, v1.0은 고객센터 경유 수동 대응으로 처리한다(UI-B8의 고객센터 경로가 이 대응의 창구) |
| `evidence_kind` / `evidence_ref` | **제외** | 증빙은 **처리자인 우리의 입증 수단**이지 정보주체에게 제공할 정보가 아니다. 특히 `evidence_ref`는 Storage 경로/메시지 ID라 노출 자체가 접근 시도 표적이 된다(`private.partner_consent_meta`에 격리해 둔 이유가 그것) |
| `recorded_by_admin_id` | **제외** | **다른 정보주체(운영자 개인)의 식별자.** 본인 열람권의 범위 밖이다 |
| `consenter_name` / `consenter_title` | **제외** | `private.partner_consent_meta`에 있으며, 계정을 나중에 claim한 파트너 입장에서는 **제3자(전임 담당자)의 실명**일 수 있다 |
| `consent_ip` | **제외** | /24 마스킹된 값이라 보여줄 실익이 없고, 화면에 IP를 띄우는 것 자체가 불필요한 노출 |
| `recorded_at` | **제외** | 시스템 입력 시각은 내부 운영 정보다. 정보주체에게 의미 있는 시각은 `collected_at` |
| `revoked_reason` | **제외** | v1.0 자가서비스 철회에는 사유 입력이 없어 항상 null |
| **전체 이력 배열** | **제외 — 최신 1건만** | 이력 전체를 노출하면 `admin_entry` 경로에서 운영자가 기록한 과거 행이 그대로 드러난다. 전체 이력 열람 요구는 법 제35조 절차(고객센터)로 처리 |

### 1.3 [UI-B3] 공개노출 동의를 철회할 수단이 UI에 없다 — **치명적**

#### 이슈

screen-spec §4.6 표의 공개노출 토글 동작:

- **ON**: `partner_grant_consent('public_listing', true)` → `partner_set_public_listing(p_on: true)`
- **OFF**: `partner_set_public_listing(p_on: false)` **만 호출**

즉 **동의를 주는 데는 1클릭, 동의를 철회하는 데는 경로 자체가 없다.** 화면 어디에도 `partner_grant_consent('public_listing', false)`를 호출하는 지점이 없다.

여기에 두 번째 문제가 겹친다. 미검증 상태에서 토글을 켜면 ①은 성공하고 ②만 `not_verified`로 실패하는데, screen-spec은 이때 "동의가 저장되었습니다 … 검증 완료 후 이 토글을 다시 켜주세요"라고 안내하고 **토글은 시각적으로 OFF로 되돌린다.** 결과적으로 사용자가 보는 화면은 "OFF"인데 DB에는 `granted=true`인 유효한 공개노출 동의가 남고, 그것을 되돌릴 방법이 없다.

#### 관련 법 근거

- **법 제22조·제39조의7 취지 및 시행령 제17조**: 동의 철회 방법은 동의 방법보다 어렵지 않아야 한다. "1클릭으로 동의 / 철회 불가"는 이 요구의 정반대다.
- **법 제37조(처리정지 요구권)**, **법 제4조 제4호**: 동의 철회는 정보주체의 기본 권리다.
- 처리방침 작성지침(2026.4.24 개정)이 요구하는 "정보주체 권리 행사 방법" 기재와도 어긋난다.

#### 위험도: **치명적** (배포 전 반드시 해결)

3계층 게이트가 실제 공개는 막아주므로 **데이터 유출 사고로 번지지는 않는다.** 그러나 "유효한 동의 레코드가 본인 의사와 무관하게 존속하고 철회할 수 없다"는 상태 자체가 법 위반 소지이며, 승인 이후 파트너가 무심코 토글을 켜는 순간 즉시 공개로 이어진다.

#### 권장 조치 (둘 다 반영)

**(1) 토글 OFF는 동의 철회까지 수행한다 — 대칭 복원**

```
토글 OFF 클릭 시:
  ① rpc('partner_set_public_listing', { p_partner_id, p_on: false })   ← 먼저(안전한 방향 우선 확정)
  ② rpc('partner_grant_consent', { p_consent_type: 'public_listing', p_granted: false })
  ※ ②가 실패해도 ①이 성공했으면 공개는 이미 중단됨. ② 실패 시 재시도 + 에러 토스트
```
`partner_withdraw()`가 이미 같은 패턴(공개 off + 철회행 기록)을 쓰고 있으므로(1608~1611행) 새로운 발명이 아니다. 다시 ON으로 켜면 기존 ON 플로우가 동의를 새로 받으므로 대칭이 유지된다.

**(2) 검증 전에는 동의를 아예 수집하지 않는다 — 토글 비활성화**

`verification_state !== 'verified'`이거나 사업자등록증 문서가 없으면 **토글을 `disabled`로 렌더**하고, 클릭 시 RPC를 호출하지 않는다.

| 상태 | 토글 | 보조 문구 |
|---|---|---|
| `verified` 아님 | disabled | `검증이 완료되면 공개 노출을 설정할 수 있습니다.` |
| `verified` + 사업자등록증 없음 | disabled | `사업자등록증을 첨부하면 공개 노출을 설정할 수 있습니다.` + 문서 탭 딥링크 |
| `verified` + 증빙 있음 | 활성 | (§1.4의 동의 고지문) |
| `suspended` | disabled | 현행 문구 유지(정확함) |

효과가 없는 시점에 동의를 받아두는 것은 최소수집 원칙에 반하고, screen-spec §3.2가 OQ-S4에서 "검증 전 공개노출 동의를 묻지 않는다"고 판단한 논리와도 일관된다. 이 조치를 넣으면 `not_verified` / `business_registration_cert_missing` 실패 경로(EDGE-12, ui-spec §3.11-1)는 **경합 상황의 방어코드로만 남는다.**

**ui-spec §3.11-1 수정**: 실패 응답 안내 박스는 유지하되, 정상 경로에서는 도달하지 않는 상태로 격하.

### 1.4 [UI-B3 연장] SUP-13 공개노출 토글이 3계층 게이트를 사용자에게 설명하지 못한다

#### 이슈

현재 스펙에 있는 것은 라벨("SEEPN에 프로필 공개") + 상태 문구뿐이다. 이것은 **선택 동의를 받는 화면인데 동의 고지사항이 없다.**

법 제22조 제1항·제15조 제2항이 요구하는 고지사항(수집·이용 목적 / 항목 / 보유·이용 기간 / **동의 거부권과 거부 시 불이익**)이 하나도 표시되지 않고, 사용자는 "무엇이 누구에게 공개되는지"를 알 수 없다. 특히 **개인사업자**의 경우 상호·소재지 공개가 사실상 개인정보의 인터넷 공개다(PR-10, 기준선 §7.3-2가 이미 ceo-advisor 에스컬레이션 항목으로 지목).

#### 권장 조치 — 토글 아래 상시 표시 고지 블록 (ux-writer 확정, 아래는 필수 요소)

```
[토글] SEEPN에 프로필 공개                                    (선택)

공개되는 정보: 회사명(국/영문), 설립연도, 임직원 규모, 소재지(시/도),
  홈페이지, 대응 언어, 해외거래 경험, 회사소개, 대표 제품/서비스,
  보유 인증, 역량정보(제품/서비스 상세)
공개되지 않는 정보: 담당자 이름·직함·이메일·전화번호, 대표자명,
  사업자등록번호, 첨부한 증빙 문서
공개 대상: SEEPN 웹사이트를 방문하는 누구나(로그인 불필요)
목적: 해외 바이어가 귀사를 찾을 수 있도록 하기 위함
기간: 이 설정을 끄거나 탈퇴하실 때까지
동의하지 않으셔도 파트너 등록과 운영자 매칭 이용에는 아무런 제한이 없습니다.
언제든 이 토글을 꺼서 공개를 중단하고 동의를 철회할 수 있습니다.
```

## 2. [UI-B7] SUP-02 약관동의 화면 — 법 제22조 요건 충족 여부

### 2.1 판정

**screen-spec §3.2의 판단 자체는 옳다.** 필수 2 / 선택 1 분리, 선택 미동의로도 진행 가능, "다음" 버튼이 필수 2개만으로 활성화 — 법 제22조의 핵심 요구를 정확히 짚었다. `finalize_partner_signup`도 `terms`+`privacy`만 강제하고 나머지는 검사하지 않는다(`20260829140000` 1046~1059행) — **코드와 문서가 일치한다.**

## 3. [UI-B10 / 참고] SUP-03 이메일 중복 처리(EDGE-1)가 계정 열거를 실제로 막는가

### 3.1 판정: 응답 설계는 옳다. 다만 **알림 메일이 새 공격면을 연다.**

`POST /api/partner/signup`이 이메일 존재 여부와 무관하게 `{ success: true }`를 반환하고 SUP-04로 보내는 설계는 표준적이고 정확하다(기준선 §2.8 "계정 존재 여부를 노출하지 않는 중립 메시지"). EDGE-4(관리자 이메일로 파트너 가입 시도)도 같은 경로로 흡수된다 — `auth_principal` 상호배타 덕분에 관리자 이메일이 파트너로 등록될 수 없고, 화면상 구분도 되지 않는다.

**그러나 "실제 소유자에게 알림 메일 발송"에는 아래 4개 조건이 붙어야 한다.** 조건 없이 구현하면 알림 메일 자체가 (a) 이메일 폭탄 도구, (b) 관리자 콘솔 존재 노출 경로가 된다.

### 3.2 알림 메일 필수 조건 (가입 오픈 전)

| # | 조건 | 이유 |
|---|---|---|
| 1 | **주소당 쿨다운 24시간 1통** + IP 레이트리밋(기존 `lib/forms/rateLimit.ts` 재사용) | 공격자가 피해자 이메일을 반복 제출해 메일함을 폭격하는 것을 막는다. 쿨다운이 없으면 **우리 도메인이 스팸 발송 주체**가 된다(기준선 §2.8이 공개 가입을 켜지 말라고 한 것과 같은 논리) |
| 2 | **`auth_principal.principal_kind = 'admin'`인 주소에는 이 메일을 보내지 않는다** | 관리자에게 "파트너 콘솔에 이미 계정이 있습니다"를 보내면 (a) 사실과 다르고, (b) **`/supplier`와 `/admin`이 같은 Auth 풀을 쓴다는 내부 구조를 외부 트리거로 확인시켜 준다.** 공격자 입장에서는 응답이 동일하므로 무발송이 오히려 정보를 덜 준다 |
| 3 | 메일 본문에 **공격자가 입력한 값(표시명 등)을 절대 반영하지 말 것.** 발송 시각·"가입 시도가 있었습니다" 사실만. 로그인/비밀번호 재설정은 **본문 링크가 아니라 사이트 주소 안내**로 | 본문에 공격자 입력을 실으면 메일이 그대로 피싱·문자 삽입 벡터가 된다 |
| 4 | 성공/실패 경로의 **응답 지연 편차를 없앨 것** — 메일 발송·정리 작업을 응답 이후 비동기로 처리하거나 최소 응답시간을 고정 | `admin.createUser` 실패는 빠르게, 성공 경로는 `finalize_partner_signup` + 메일까지 거치므로 응답 시간만으로 계정 존재를 추론할 수 있다. 이걸 놓치면 §1.3의 중립 메시지가 무력화된다 |

**조건 1·4를 붙일 수 없다면 알림 메일 기능 자체를 v1.0에서 빼는 편이 낫다.** 열거 방어는 중립 응답만으로도 성립하며, 알림 메일은 "선의의 사용자를 돕는" 부가 기능이지 방어의 필수 요소가 아니다.

### 3.3 EDGE-2 고아 계정

`finalize_partner_signup` 실패 시 방금 만든 `auth.users` 행 정리(`admin.deleteUser`)는 **필수 구현**이다. 정리하지 않으면 (a) 실제 사용자의 이메일이 우리 DB에 계정 없이 남고, (b) 그 주소로는 영영 재가입이 안 된다(UI-B1과 같은 증상). 정리 실패 시에도 반드시 서버 로그에 남겨 수동 회수가 가능해야 한다.

## 4. SUP-11 문서 탭

### 4.1 [UI-B4] 브라우저 → Storage 직접 업로드는 성립하지 않는다 — **치명적**

#### 이슈

screen-spec §4.4는 업로드를 ①클라이언트 MIME/용량 검증 → ②브라우저에서 SHA-256 계산 → ③`storage.upload()` 직접 호출 → ④`partner_document` INSERT로 정의한다. 그런데 실제 GRANT는 `grant select, insert on public.partner_document to authenticated`(824~826행)이고 Storage 정책도 파트너에게 직접 INSERT를 허용한다(944~951행). 즉 **①②를 포함해 전부 클라이언트가 통제한다.** 확인된 결과:

| # | 문제 | 근거 |
|---|---|---|
| a | **서버측 매직바이트 검증이 원천적으로 불가능하다.** screen-spec 스스로 "backend-developer가 서버에서 한 번 더 해야 한다"고 적었지만, 브라우저가 Storage에 직접 올리는 구조에서는 그 서버가 경로상 존재하지 않는다 | 아키텍처 |
| b | **버킷에 `allowed_mime_types` / `file_size_limit`가 설정되어 있지 않다.** `insert into storage.buckets values ('partner-doc','partner-doc',false)`가 전부다. PR-2가 반드시 차단하라고 한 **SVG/HTML 업로드를 막는 서버측 통제가 하나도 없다**(저장형 XSS) | 920~922행 |
| c | **SHA-256 해시를 클라이언트가 계산해 그대로 INSERT한다.** 파일과 무관한 값을 넣어도 DB는 `char_length = 64`만 검사한다 → **해시가 무결성 증빙으로서 가치가 0** | 785행 |
| d | **`storage_path`와 `partner_id`의 정합성을 아무도 검사하지 않는다.** RLS INSERT 정책은 `owns_partner(partner_id)`만 보고 경로의 파트너 세그먼트는 보지 않는다. 즉 `partner_id=내것`이면서 `storage_path=p/{남의id}/...`인 메타 행을 만들 수 있다 | 781행, 835~842행 |
| e | (d)의 실질 위험: 읽기는 Storage RLS가 막지만, **`partner_delete_document` + 서버의 `storage.remove(storage_path)` 경로가 남의 파일을 지우게 된다.** 파일 UUID가 추측 불가라 실현 난도는 높으나(관리자 화면에는 경로가 보인다), 구조적 결함임은 분명하다 | G-S3 삭제 절차 |
| f | 파트너당 총 업로드 용량 상한이 없다(PR-2 권고 50MB) | — |

#### 권장 조치 (blocking)

**업로드를 서버 라우트 경유로 바꾼다** — Admin이 이미 `uploadPartnerDocumentAction`에서 하고 있는 것과 같은 구조다(`app/admin/(protected)/partners/[id]/actions.ts` 291~320행: 서버에서 바이트를 받아 `createHash('sha256')`로 직접 계산하고 경로도 서버가 생성한다). 새 패턴을 발명할 필요가 없다.

```
POST /api/partner/documents  (Route Handler, multipart)
  1. 세션 검증 + partner_id 자체 조회(클라이언트 입력값을 신뢰하지 않는다)
  2. 용량(≤10MB) + 파트너 총량(≤50MB) 검사
  3. 매직바이트 검증 — %PDF / JPEG(FFD8FF) / PNG(89504E47) 화이트리스트.
     확장자·선언 MIME은 참고값으로만 쓴다
  4. 서버가 SHA-256 계산
  5. 서버가 경로 생성: p/{partner_id}/{doc_type}/{randomUUID()}.{ext}
     — partner_id는 1번에서 서버가 얻은 값
  6. service_role Storage 클라이언트로 upload
  7. partner_document INSERT (성공 후, 순서는 screen-spec §4.4 그대로 유지)
  8. 실패 시 storage.remove로 정리 (admin 액션의 315~319행 선례)
```

**병행 조치(값 문제라 즉시 가능):** 버킷에 `allowed_mime_types = {application/pdf, image/jpeg, image/png}`, `file_size_limit = 10485760` 설정. 선언 MIME은 위조 가능하므로 3번을 대체하지는 못하지만, 방어선을 하나 더 얹는다.

**후속(UI-R2):** `partner_document`에 `check (storage_path like 'p/' || partner_id::text || '/%')` 제약 추가. 서버 라우트로 옮기면 실현 경로는 사라지지만, 제약은 "코드가 바뀌어도 남는" 방어다.

**화면 영향:** SUP-11의 업로드 진행바(ui-spec §3.9-2)는 그대로 유지 가능(라우트 응답까지의 진행). 드롭존·검증 문구·에러 문구 변경 없음. **클라이언트 검증은 UX용으로 남기되, 그것이 보안 통제가 아님을 구현 메모에 명시**할 것.

### 4.2 [UI-B11] 주민등록번호 — 사전 스캔이 v1.0에 필요한가

#### 판정: **사전 OCR 스캔은 v1.0에 불필요하다. 그러나 "사후 경고"만으로는 부족하다 — 아래 3가지를 대신 넣는다.**

**사전 OCR을 기각하는 이유:**

1. **비용 대비 효과가 맞지 않는다.** 대상은 30~50개사, 문서는 사업자등록증 1장이 대부분이며 관리자가 100% 사람 눈으로 검증한다(A1-R5/A1-R6). 이 규모에서 OCR 파이프라인은 과투자다.
2. **서버측 OCR은 그 자체가 주민등록번호 처리 행위다.** 탐지 목적이라도 원본을 읽어 패턴을 추출하는 순간 처리에 해당하고, 외부 OCR API를 쓰면 **국외 이전 + 위탁**이 새로 발생해 처리방침 수정과 동의 구조 변경까지 파생된다. 막으려던 리스크보다 큰 리스크를 들여오는 셈이다.
3. **탐지 실패율이 오히려 위험하다.** 스캔 이미지 품질에 따라 놓치는 경우가 반드시 생기는데, "자동 검사를 통과했다"는 인상이 관리자 검증을 느슨하게 만든다.

**그러나 위험은 가설이 아니라 실재한다.** 개인사업자 사업자등록증에는 발급 양식·시기에 따라 주민등록번호가 표기된 사본이 실제로 존재한다. 그리고 이 프로젝트에서 개인사업자는 정확히 PR-10이 "개인정보로 취급된다"고 판정한 대상이다. 즉 **가장 위험한 케이스에서 가장 발생하기 쉽다.**

#### 대신 넣을 것 (3가지, blocking)

| # | 조치 | 상세 |
|---|---|---|
| 1 | **업로드 전 명시적 확인 체크박스** (`business_entity_type='sole_proprietor'`일 때만) | 드롭존 위에 `☐ 첨부 파일에 주민등록번호가 표시되어 있지 않음을 확인했습니다`. 체크 전 업로드 버튼 비활성화. ui-spec §3.9-1의 배너(수동적 경고)를 능동적 확인으로 승격 — **개인사업자에게만** 요구해 법인 파트너의 마찰은 늘리지 않는다 |
| 2 | **클라이언트 텍스트 레이어 정규식 검사**(PDF 한정, OCR 아님) | 텍스트 레이어가 있는 PDF는 브라우저에서 `\d{6}[-\s]?[1-4]\d{6}` 패턴을 검사할 수 있다. **파일을 서버로 보내기 전에 브라우저 안에서만** 수행하므로 새 처리·이전이 발생하지 않는다. 검출 시 차단이 아니라 경고("주민등록번호로 보이는 숫자가 포함되어 있습니다. 가려서 다시 첨부해주세요") + 계속 진행 선택지. 이미지·스캔 PDF는 검사 대상이 아님을 인정하고, 이것을 통제로 과신하지 말 것. **Should(구현 여유 시), 1·3은 Must** |
| 3 | **주민등록번호 사유 반려 시 문서 즉시 파기 경로** — 이것이 진짜 blocking | 아래 상세 |

#### 3번 상세 — 현재 상태가 명백한 결함이다

확인된 사실: `admin_reject_partner`(1405~1441행)는 `verification_state='rejected'`, `rejected_at`, `rejection_reason`만 쓰고 **문서를 삭제 큐에 넣지 않는다.** 파기는 `purge_rejected_partner_pii()`가 `rejected_at + 90일`에 수행한다(1895~1943행). 즉 **주민등록번호가 들어 있어서 반려한 파일이 우리 스토리지에 90일간 남는다.**

법 제24조의2는 법령 근거 없는 주민등록번호 처리를 원칙적으로 금지한다. "반려했으니 90일 뒤 지운다"는 이 금지에 대한 답이 될 수 없다.

| 담당 | 조치 |
|---|---|
| backend-developer | `admin_reject_partner`에 `p_purge_documents boolean default false` 인자를 추가하거나, 별도 `admin_purge_partner_document(p_document_id)` RPC를 만들어 **관리자가 반려와 동시에 해당 문서를 즉시 `pending_deletion_at = now()`로 큐잉**할 수 있게 한다 (**UI-B5 워커가 있어야 실효** — 두 항목은 함께 처리) |
| Admin 화면(별도 문서) | 반려 사유 프리셋에 "주민등록번호 포함"을 두고, 이 사유 선택 시 문서 즉시 파기를 **기본 체크**로 |
| **SUP-11 (이 문서 범위)** | 상태배너가 `rejected`이고 사유에 주민등록번호가 언급된 경우, 문서 탭 상단에 조치 유도 배너: `첨부하신 문서에 주민등록번호가 포함되어 있습니다. 해당 파일을 삭제하고, 주민등록번호를 가린 파일로 다시 첨부해주세요.` + 해당 문서 행 강조. 파트너 본인 삭제 경로(`partner_delete_document`)가 이미 있으므로 화면 작업만으로 가능 |

## 5. [UI-B5 / UI-B6] SUP-14 탈퇴 모달이 실제보다 많은 것을 약속한다

### 5.1 [UI-B5] 문서가 실제로 삭제되지 않는다 — **치명적**

모달 문구: "탈퇴하면 … 담당자 연락처와 **첨부 문서가 삭제됩니다**."

실제:
- `private.partner_contact` DELETE → **사실**(1621행)
- 문서 → `pending_deletion_at = now()`로 **큐에 넣기만 한다**(1615~1617행). SQL은 Storage REST API를 호출할 수 없어 실제 삭제는 별도 워커의 몫이며, 마이그레이션 주석도 이를 "명시적으로 남긴 gap"이라고 적어 두었다(1882~1887행).
- **그 워커는 코드베이스에 존재하지 않는다** — `pending_deletion_at`를 참조하는 애플리케이션 코드는 Admin 상세 화면의 표시용 참조뿐이고, 스케줄 라우트·Edge Function 어디에도 소비자가 없다(전수 확인).

즉 현재 배포 상태에서 파트너가 탈퇴하면 **사업자등록증 원본이 스토리지에 그대로 남는다.** 이는 `partner_doc_purge`(검증 후 90일)와 `partner_rejected_purge`(반려 후 90일) 배치에도 똑같이 해당한다 — **세 개의 파기 정책이 전부 큐잉까지만 하고 실제 파기가 일어나지 않는다.**

| 항목 | 내용 |
|---|---|
| 관련 법 근거 | 법 제21조(파기), 안전성 확보조치 기준 제7조 |
| 위험도 | **치명적** — 처리방침·화면 고지와 실제 동작의 불일치는 그 자체가 위반이며(기준선 §4 PR-5 "문서와 실제 배치 동작이 어긋나면 그 자체가 위반"), 조사 시 가장 먼저 드러나는 유형 |
| 권장 조치 | **파기 워커 신설을 파트너 가입 오픈의 게이트로 지정.** `pending_deletion_at is not null` 행을 폴링해 (1) `storage.remove(storage_path)` → (2) `delete from partner_document` 순으로 처리하는 Next.js 스케줄 라우트 또는 Supabase Edge Function. 실행 결과를 `retention_jobs`에 남겨 감사 가능하게 할 것 |
| 임시 대안(워커보다 먼저 배포 가능) | `/api/partner/withdraw` 서버 라우트가 `partner_withdraw()` 성공 직후 **그 파트너의 문서만** service_role Storage 클라이언트로 동기 삭제. 탈퇴 경로만 정직해지고 90일 배치 2건은 여전히 미이행이므로 **완전한 해결이 아님**을 명시 |

### 5.2 [UI-B6] 개인사업자 회사정보가 남는다

`partner_withdraw()`는 개인사업자 익명화(PR-5 / step 8)를 수행하지 않는다(1576~1578행이 "PM/service-planner 결정 사항이라 추측하지 않았다"고 명시). 따라서 개인사업자 파트너가 탈퇴해도 `public.partner`에 **상호·사업자등록번호·소재지·회사소개**가 남는다. PR-10이 이 값들을 개인정보로 판정했으므로, 탈퇴 후 이 상태는 보유 근거가 없다.

`purge_unconsented_partner_pii()`(1831~1840행)에 개인사업자 익명화 로직이 **이미 구현되어 있다** — 같은 UPDATE 블록을 `partner_withdraw()`에서 재사용하면 되므로 추가 설계가 필요 없다. **backend-developer 조치, 가입 오픈 전.**

### 6.1 [UI-B10] BRN 중복확인 — 코드는 옳고 문구가 틀렸다

- **재확인 결과**: `check_business_registration_duplicate`는 `returns boolean`, 본문 `select exists(...)` 한 줄, `anon` GRANT 없음. **어느 회사인지도, 어떤 상태인지도 반환하지 않는다** — 설계는 PR-12를 정확히 구현했다.
- **문제 1 — 문구**: 화면이 `이미 등록된 사업자등록번호입니다`라고 확정해준다. PR-12 (2)는 `이 사업자번호는 등록할 수 없습니다. 고객센터로 문의해 주세요` 형태의 중립 문구를 요구했다. 사업자등록번호는 대량으로 확보 가능한 값이므로, 로그인 계정 하나만 있으면 "어느 회사가 SEEPN에 등록되어 있는지" 전량 확인이 가능하다.
- **문제 2 — 노출 범위가 `partner_public`보다 넓다**: 이 함수는 `public.partner` 전체를 본다. 즉 **아직 검증되지 않은 draft, 공개 동의가 없는 행, 그리고 `admin_entry`로 수집한 아웃리치 대상까지** 포함한다. 공개 뷰로는 절대 알 수 없는 "우리가 접촉 중인 회사 목록"이 이 boolean 하나로 확인 가능하다. **경쟁사가 파트너로 가입하면 우리 영업 파이프라인을 열거할 수 있다.**
- **위험도**: **주요**

| 4 | 초과 호출을 `audit_log`에 기록(`log_auth_event`의 고정 액션 목록에 파트너 액션을 추가하지 말 것 — 기준선 §2.4-(4). 별도 감사 RPC 또는 서버 로그) |
| 5 | 화면은 screen-spec §4.2 권고대로 **버튼 명시 확인만** 지원하고 `onBlur` 자동확인은 채택하지 않는다(호출량이 곧 열거량) |

### 6.2 [UI-R4] `display_name`에 실명이 들어오면 PII 게이트가 우회된다

`partner_account_admin_select` 정책은 `is_active_admin AND is_aal2 AND has_menu_permission('partner_management','read')`만 요구하고 **`has_pii_access()`를 요구하지 않는다**(`20260829130000` 227~233행). 이는 `display_name`이 실명이 아니라는 전제 위에서 옳은 설계다. 그러나 사용자는 가입 폼에 자기 이름을 적는다.

SUP-03의 안내 문구(`회사명 또는 별칭 — 담당자 실명이 아닙니다`)는 이미 정확하다. 여기에 더한다:
- 안내를 **입력 필드 아래 상시 표시**(placeholder가 아니라)로 유지하고, `홍길동` 같은 예시를 절대 넣지 말 것.
- SUP-13에서 `display_name` 편집을 노출한다면 같은 안내를 반복(현재 스펙에 편집 UI 자체가 없음 — 추가하지 않는 편이 안전).
- viewer 권한 관리자에게도 보인다는 사실을 파트너용 처리방침의 "수집 항목" 설명에 반영.

심각도 **권고**(구조가 아니라 입력값 문제이며, 완전 차단이 불가능).

## 7. [UI-B8 / 기타] 인증 후 셸의 법정 표시사항과 잔여 권고

### 7.1 [UI-B8] 처리방침·약관 링크와 고객센터 경로 부재

ui-spec §2.2의 인증 후 셸은 상단바(워드마크 + 계정 메뉴)와 콘텐츠 영역으로만 구성되며 **푸터가 없다.** 그 결과:

1. **법 제30조 제2항**: 개인정보 처리방침을 정보주체가 쉽게 확인할 수 있도록 공개해야 한다. 파트너는 로그인 후 전 화면에서 처리방침에 접근할 수 없다.
2. 두 문서 합쳐 **8곳 이상**에서 "고객센터로 문의해주세요"라고 안내한다(SUP-01 정지 계정, SUP-09 BRN 중복, SUP-13 공개중단, EDGE-9, EDGE-11 등). **그 고객센터가 무엇인지 정의된 곳이 없다.** 안내만 있고 도달 경로가 없는 것은 실질적으로 권리행사 창구가 없는 것과 같다.
3. **법 제30조 제1항 5호** — 개인정보 보호책임자(CPO) 성명·연락처는 처리방침 필수 기재사항이며, §1.2에서 RPC 밖으로 뺀 항목들(수집 출처 고지, 전체 동의 이력 열람, `consent_ip` 열람)의 처리 창구가 바로 여기다.

**권장 조치 (가입 오픈 전)**

| # | 조치 |
|---|---|
| 1 | 인증 후 셸 하단에 최소 푸터 추가: `이용약관 · 개인정보처리방침 · 고객센터` (`text-label-caption text-neutral-500`, `max-w-6xl mx-auto px-6 py-6 border-t border-neutral-200`). 비인증 셸(§2.1 카드)에도 카드 아래에 동일 링크 |
| 2 | 고객센터 경로를 **하나로 확정** — 전용 이메일 주소 또는 `/supplier/support` 정적 안내 페이지. 모든 "고객센터로 문의해주세요" 문구를 이 경로로 링크 |
| 3 | 그 페이지/처리방침에 **개인정보 보호책임자 및 열람·정정·삭제·처리정지·동의철회 요구 접수 방법** 명시 |

### 7.2 [UI-B9] SUP-13 비밀번호 변경에 재인증이 없다

screen-spec §4.6은 "현재 비밀번호 재확인 없이 `supabase.auth.updateUser({password})`(세션이 이미 있으므로 재인증 불필요 — Supabase 기본 동작)"이라고 적었다. Supabase 기본 동작인 것은 맞지만, **기본값이 적절하다는 뜻은 아니다.**

파트너 경로는 (a) MFA를 요구하지 않고(§1.3 상속, 그 결정 자체는 옳다), (b) 세션이 30분간 유효하다. 따라서 XSS·기기 공유·세션 탈취 상황에서 **재인증 없는 비밀번호 변경은 곧바로 영구적 계정 탈취**로 이어지고, 정당한 소유자는 알아차릴 수단이 없다.

| 관련 근거 | 안전성 확보조치 기준 제5조·제6조(접근권한·접근통제) 취지 |
|---|---|
| 위험도 | **주요** |
| 권장 조치 | ① Supabase Auth 프로젝트 설정의 **"Secure password change"(최근 인증 요구) 활성화**, 또는 앱 레벨에서 변경 직전 `signInWithPassword`로 현재 비밀번호 재확인. ② 변경 성공 시 **변경 알림 메일 발송**("본인이 변경하지 않았다면 즉시 고객센터로 연락"). ③ 변경 후 **다른 모든 세션 무효화**(`/api/partner/withdraw`와 같은 얇은 라우트에서 `auth.admin.signOut(uid,'global')`) |
| 화면 영향 | SUP-13 비밀번호 섹션에 "현재 비밀번호" 필드 1개 추가. ui-spec §3.11-3의 레이아웃(2필드 → 3필드)만 조정 |

## 10. 변호사 검토 필요 항목 (파트너 가입 오픈 전)

기준선 §6.3·§7.3의 항목에 더해:

1. **탈퇴 시 로그인 이메일 즉시 파기(UI-B1)** — 전자상거래법 등 계약·거래 기록 보존의무가 파트너 계정에 적용되는지. 적용된다면 UI-B1의 즉시 삭제 대신 **분리보관** 구조로 바뀌어야 하므로, 구현 전에 답이 필요하다.
2. **개인사업자 파트너의 공개 노출 범위(§1.4)** — 상호·소재지 공개의 적법성 및 고지 수준(기준선 PR-10 재확인).
3. **다크패턴 규제 세부기준(§2)** — 개정 규정의 시행 시점·적용 유형이 파트너 가입 동의 화면에 미치는 범위.
4. **동의 증빙 보관기간(기준선 Q-3, 탈퇴 후 3년 권고)** — SUP-14 모달 문구와 처리방침에 그대로 표기되므로 값이 확정되어야 한다.
5. **정보통신망법 제50조 제8항 2년 재확인 의무의 이행 방식** — 재확인 미이행 시 기존 동의의 효력, 재확인 통지 수단.

## 11. ceo-advisor 에스컬레이션

1. **UI-B5(파기 워커 부재)는 이 프로젝트에서 가장 큰 평판·법적 리스크다.** 처리방침과 화면이 "삭제됩니다"라고 약속하는데 세 개의 파기 배치가 전부 큐잉까지만 하고 멈춰 있다. 개별 이슈로 보면 워커 하나지만, **"고지한 대로 파기하지 않았다"는 것은 조사에서 가장 먼저 확인되고 가장 방어하기 어려운 유형**이다. 파트너 가입 오픈 일정을 잡기 전에 이 워커를 배포하십시오.
2. **UI-B10 문제 2(BRN 열거로 영업 파이프라인이 드러남)는 법적 리스크이자 동시에 사업 리스크다.** 파트너로 가입한 경쟁사가 "SEEPN이 어느 회사들을 접촉 중인지"를 확인할 수 있다. 일 단위 레이트리밋 하나로 막히므로 비용이 사실상 없다.
3. **기준선 §7.3-3(CPO 지정·내부관리계획)의 실행 시점이 지금이다.** UI-B8이 요구하는 "개인정보 보호책임자 연락처"는 CPO가 지정되어 있어야 쓸 수 있는 값이며, 그 값 없이는 파트너용 처리방침을 완성할 수 없다 — 즉 **가입 오픈의 실질적 선행조건**이다.
