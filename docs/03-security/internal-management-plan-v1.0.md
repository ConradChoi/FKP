## 2. 개인정보취급자의 범위와 책임

| 구분 | 정의 | 확인 방법 |
|---|---|---|
| 개인정보취급자 | `public.admin_user`의 `status = 'active'` 행 전원 | 이 테이블이 **유일한 SSOT**다. 별도 명부를 엑셀로 관리하지 않는다 |
| 파트너·바이어 | 정보주체이지 취급자가 아니다. 본인 정보에만 접근 | `private.is_active_partner()` / (P5a) `private.is_active_buyer()` |
| 외부 인력(오프라인 파트너 발굴 인력) | **관리자 계정을 부여받은 경우에만** 취급자. 계정 없이 개인 파일·메신저로 파트너 정보를 보관하는 것은 **금지** | PRD D-6(자가등록 기본 경로)이 이 위험을 구조적으로 줄인 것 |

**취급자 준수사항**
- 계정 공유 금지(1인 1계정), 비밀번호 타 사이트 재사용 금지.
- 개인정보를 **개인 PC·개인 클라우드·메신저·엑셀로 반출하지 않는다.** 열람은 관리자 화면 안에서만.
- 유출등 인지 시 **지체 없이 대표에게 보고**(유출 대응 절차 §2).
- 퇴직·업무 변경 시 **즉시 권한 회수**(§3).

## 3. 접근 권한의 관리

| 통제 | 실재 상태 |
|---|---|
| 계정 발급 | **공개 가입 차단**(Supabase Auth "Allow new users to sign up" = **OFF**). 관리자 계정은 `admin_access_request` 승인 또는 초대 경로로만 생성. 파트너·바이어 가입은 `service_role`을 쓰는 **서버 라우트 + `finalize_*_signup` RPC** 경유 |
| 권한 부여 | **RBAC** — `role` / `admin_user_role` / `menu` / `role_menu_permission`. 메뉴 단위 read/write 권한을 **업무에 필요한 범위로만** 부여 |
| PII 열람 권한 분리 | 일반 관리자 권한과 **개인정보(연락처 원문) 열람 권한이 분리**되어 있다(`can_access_pii` / `has_pii_access()`). 목록 화면은 마스킹 값만 표시 |
| 권한 변경 기록 | `audit_log`의 `admin_user.role_grant` / `role_revoke` / `admin_user.invite` / `.suspend` / `.withdraw` 등으로 기록 |
| 권한 회수 | `admin_user.status`를 `suspended` / `withdrawn`으로 전이. 계정 삭제가 아니라 상태 전이이므로 **감사 귀속이 유지**된다 |
| **정기 점검** | **반기 1회**, 대표가 `admin_user` × `admin_user_role` × `role_menu_permission`을 열람해 **불필요 권한을 회수**하고 점검 사실을 기록(§12) |

> **[주요 — 갭] 권한 변경 이력의 보관 기간이 법정 기준에 미달한다.**
> 「개인정보의 안전성 확보조치 기준」은 **접근 권한의 부여·변경·말소 내역을 최소 3년** 보관하도록 한다. 그런데 현재 `private.purge_expired_audit_log()`는 `delete from public.audit_log where occurred_at < now() - interval '2 years'`로 **action 구분 없이 2년에 일괄 삭제**한다. 즉 `admin_user.role_grant` / `role_revoke` 기록도 2년에 지워진다.
> **조치**: 권한 변경 계열 action을 purge 대상에서 제외하거나 별도 보관 기간(3년)을 적용하도록 함수를 수정한다. → **backend-developer 조치 요청(P5a와 별개, 기한: 서비스 오픈 후 2년이 되기 전. 즉시성은 낮으나 잊으면 되돌릴 수 없다)**.

## 4. 접근 통제 (기술적 조치)

| 계층 | 실재 상태 |
|---|---|
| DB 행 단위 | **전 테이블 RLS `enable` + `force`, deny-by-default.** `anon`/`authenticated`의 기본 GRANT는 명시적으로 `revoke` |
| 비공개 스키마 | 민감 컬럼은 `private` 스키마로 분리(`private.partner_contact`, `private.request_meta`, `private.partner_consent_meta`). **`private`는 Supabase API Exposed schemas에 포함되지 않는다**(GRANT/RLS와 독립된 2차 방어선) |
| 관리자 인증 | **MFA(TOTP) 필수 — AAL2 세션이 아니면 관리자 RLS 정책 자체가 통과되지 않는다**(`private.is_aal2()`). 화면 가드가 아니라 DB 조건이라는 점이 핵심 |
| 세션 | JWT 30분, 무활동 30분, 최대 8시간, 리프레시 토큰 회전 ON. **3개 축(관리자/파트너/바이어) 쿠키 분리** |
| 로그인 공격 방어 | `private.login_lockout` — 반복 실패 시 계정 일시 잠금. 가입·중복확인 등 요청 레이트리밋 |
| PII 원문 열람 | 정의자 함수(`get_partner_contact()` 등) 경유만 가능하며, **감사 기록 실패 시 열람 자체가 롤백**된다 |
| 전송 구간 | 전 구간 HTTPS |
| 파일 저장소 | `partner-doc` **비공개 버킷**. 열람은 **최대 300초 서명 URL**. 경로에 원본 파일명 미사용. 업로드는 형식(PDF/JPEG/PNG) + 크기 서버 검증 |
| 공개 노출 경계 | 파트너 공개 정보는 **3계층 게이트**(공개 토글 ON AND 검증 완료 AND 공개 동의 유효 AND 미탈퇴)를 통과한 행만. 담당자 연락처·사업자등록번호·대표자명·증빙문서는 **공개 뷰에 컬럼 자체가 존재하지 않는다** |

**비밀키 관리 (AWS Amplify)**
- `SUPABASE_SERVICE_ROLE_KEY`, `PARTNER_DOC_PURGE_CRON_SECRET`, `GOOGLE_TRANSLATE_CREDENTIALS_JSON`은 **Amplify 환경변수(Secrets)로만** 관리하고 저장소에 커밋하지 않는다.
- 이 값들은 Amplify SSR 런타임 전달 버그 때문에 `next.config.js`의 `env` 블록에 등재되어 **빌드 시점에 인라인**된다. 따라서 **`'use client'` 파일이나 클라이언트 번들에서 도달 가능한 모듈에서 이 이름들을 참조하면 그 순간 브라우저 번들에 비밀키가 박힌다.**
  - **상시 규칙**: 이 이름들은 Route Handler / Server Component / Server Action에서만 참조한다.
  - **배포 전 확인**: 빌드 산출물(`.next/static`)에서 해당 키 값이 검색되지 않는지 확인한다. → **qa-reviewer 배포 게이트 항목**.
- `NEXT_PUBLIC_SUPABASE_ANON_KEY`는 정의상 공개 값이다. **"키를 모르니 안전하다"는 방어를 어떤 설계에서도 근거로 삼지 않는다.**

## 5. 개인정보의 암호화

| 대상 | 조치 |
|---|---|
| 비밀번호 | Supabase Auth가 **복호화 불가능한 해시**로 저장. 최소 12자, 유출 이력 비밀번호 차단. **앱은 평문 비밀번호를 로그·감사·에러 리포트에 절대 남기지 않는다** |
| 전송 구간 | HTTPS(TLS) 전 구간 |
| 저장 매체 | Supabase(Postgres) 및 Storage의 저장 시 암호화는 **수탁자(Supabase/AWS) 제공 기능에 의존** |
| **고유식별정보·민감정보** | **수집하지 않는다.** 주민등록번호·여권번호·운전면허번호·외국인등록번호, 건강·생체·심리검사 정보, 결제·계좌정보 어느 것도 수집 항목에 없다 → **법정 암호화 의무 대상 항목이 현재 없다** |
| 예외 위험 | 파트너가 증빙 서류(`partner-doc`)에 **주민등록번호가 노출된 서류를 임의로 첨부**할 수 있다. 이를 처리방침 §16 및 업로드 화면에서 금지 안내하고, 검증 큐에서 발견 시 **즉시 파기**한다 |
| 세션 토큰 | `access_token` / `refresh_token`을 로그·감사·에러 리포트에 남기지 않는다. 진단이 필요하면 존재 여부·길이만 기록 |

## 6. 접속기록의 보관 및 점검

| 항목 | 실재 상태 |
|---|---|
| 기록 대상 | 로그인 성공/실패, 로그아웃, MFA 등록·재설정, 비밀번호 변경, 접근 거부, **PII 열람(`*.contact_reveal`)**, 리드/파트너 조회·수정·상태변경·배정, 권한·역할·메뉴 변경, 감사로그 열람·내보내기 |
| 기록 내용 | 발생 시각, 행위자(계정 id + **당시의 이메일·성명·역할 스냅샷**), 행위, 대상, 결과(success/denied/error), IP, User-Agent, 요청·세션 식별자 |
| 위·변조 방지 | `audit_log`는 **append-only** — UPDATE/DELETE가 트리거로 차단되며, 유일한 예외는 보관기간 만료 purge 함수뿐(전용 GUC로만 열림). PK가 단조 증가 `bigint`라 **삭제 시도로 인한 결번이 드러난다** |
| 검색어 원문 | `query_filter`에 **원문 검색어를 넣지 않는다**(이메일·회사명이 검색창에 들어오므로) |
| 보관 기간 | **2년** (`private.purge_expired_audit_log()`). 처리방침 §13과 일치 |
| **정기 점검** | **월 1회**, 대표가 `*.contact_reveal`, `auth.login_failed`, `auth.access_denied`, `*.export`를 확인해 비정상 패턴 여부를 점검하고 결과를 기록(§12). **현재 자동 알림은 없으므로 이 수기 점검이 유일한 탐지 수단이다** |
| 갭 | §3의 권한 변경 이력 3년 보관 미달(재확인) |

## 7. 악성프로그램 등 방지

- 서버·애플리케이션은 **관리형 PaaS(Supabase / AWS Amplify)** 위에서 동작하며, 회사가 직접 운영하는 서버·OS가 없다. OS·런타임 보안 패치는 수탁자 책임 범위다.
- 업로드 파일은 **형식 화이트리스트(PDF/JPEG/PNG) + 크기 제한**을 서버에서 검사하고, `image/svg+xml`·`text/html`·`application/xml`은 **저장형 XSS 위험으로 차단**한다. 응답은 `Content-Disposition: attachment` 강제.
- 취급자 업무용 단말은 **OS 자동 업데이트 및 화면 잠금(5분 이내)을 켠다.** 백신 소프트웨어는 OS 기본 제공 기능으로 갈음한다.
- 애플리케이션 의존성의 알려진 취약점은 **분기 1회** 점검한다(§13 G-8: 자동화 없음).

## 8. 물리적 안전조치

- 회사는 **전산실·서버실·문서고를 보유하지 않는다.** 모든 개인정보는 Supabase(서울 리전)·AWS에 저장되며, 데이터센터의 물리적 통제는 수탁자 책임 범위다.
- **종이 형태의 개인정보를 수집·보관·출력하지 않는다**(처리방침 §12와 동일). 명함 등으로 수집된 정보는 시스템에 등록한 뒤 원본을 파기한다.
- 취급자 업무용 단말은 **디스크 암호화(FileVault/BitLocker) + 화면 잠금**을 적용하고, 분실 시 **즉시 대표에게 보고**하여 해당 계정의 세션을 전면 무효화한다.
- 공용 PC·공용 네트워크에서 관리자 화면에 로그인하지 않는다.

## 9. 재해·재난 대비

- 데이터 백업은 **Supabase 제공 자동 백업**에 의존한다. **현재 요금제의 백업 주기·보관 기간·복구 소요시간(RPO/RTO)은 미확인 상태**이며, 대표가 Dashboard에서 확인해 이 문서에 반영한다(§13 G-6).
- 스키마 변경은 **마이그레이션 파일로 저장소에 남으므로** 구조 복원은 가능하다. 데이터 복원은 백업에 전적으로 의존한다.
- **파기 배치 오작동은 재해와 동일하게 취급한다** — 유출 대응 절차 §1 S-4. 배치 함수 변경 시에는 반드시 로컬에서 먼저 실행한다.

요지: **인지 즉시 대표 보고 → 72시간 기산점은 "최초 인지 시각"(보고 시각이 아니다) → 봉쇄 우선 → 대상자 추출 → 72시간 내 정보주체 통지 + 보호위/KISA 신고 → 사고 기록 보존.**

## 11. 개인정보 취급자 교육

| 항목 | 내용 |
|---|---|
| 대상 | 관리자 계정 보유자 전원(대표 포함) |
| 주기 | **연 1회 이상**, 신규 계정 발급 시 **부여 전 1회** |
| 방법 | 자체 교육. 개인정보보호위원회·KISA가 공개한 교육자료 활용 |
| 필수 내용 | ① 이 문서와 처리방침의 요지 ② 취급자 준수사항(§2) ③ **유출 대응 절차 §2~§3(인지 즉시 보고, 72시간 기산점)** ④ 최소수집·목적 제한 ⑤ **바이어 식별정보를 파트너에게 전달하지 않는다는 원칙**(PRD D-14②) |
| 기록 | 실시일·대상자·내용을 §12 대장에 기록 |

## 12. 점검 및 기록

| 점검 | 주기 | 실행 | 기록 위치 |
|---|:---:|---|---|
| 접속기록 점검(§6) | 월 1회 | 대표 | `docs/03-security/compliance-log.md` (신규, 아래 형식) |
| 접근 권한 점검(§3) | 반기 1회 | 대표 | 동일 |
| 취급자 교육(§11) | 연 1회 | 대표 | 동일 |
| 이 계획의 이행 실태 점검 | 연 1회 | 대표 | 동일 |
| Supabase Dashboard 설정 재확인(공개 가입 OFF / Exposed schemas에 `private` 없음 / MFA 강제 / 세션 정책 / 비밀번호 정책) | **배포 시마다 + 반기 1회** | 대표 + qa-reviewer | 동일 |
| 유출 대응 모의 점검(§13 G-5) | 연 1회 | 대표 | 동일 |

**기록 형식(1줄/건)**: `| 날짜 | 점검 항목 | 실시자 | 확인 결과 | 발견 사항 | 조치 및 완료일 |`

> **콘솔 설정은 코드 리뷰와 마이그레이션 diff에 흔적이 남지 않는다.** 그래서 §12의 "배포 시마다 재확인"이 다른 항목보다 중요하다 — 누가 켠지도 모르게 되돌아가는 통제가 정확히 이 부류다.

## 13. 현재 없는 것 (정직한 표기 — 향후 계획)

| # | 항목 | 상태 / 계획 |
|---|---|---|
| **G-1** | 이상징후 자동 탐지·알림(APM/보안 모니터링) | **없음.** 월 1회 수기 점검(§6)으로 갈음. 취급자 2인 이상 또는 정보주체 1천 명 도달 시 재검토 |
| **G-2** | CPO 대행자, 개인정보 보호 조직·분리된 담당부서 | **없음.** 대표 1인 겸임 구조 |
| **G-3** | 대량 통지 메일 발송 수단 | **없음.** 유출 대응 절차 §5-2 |
| **G-4** | 통지 대상자 추출 함수 `private.breach_notification_targets()` | **없음 → 신규 구현 요청**(유출 대응 절차 §5-1) |
| **G-5** | 유출 대응 모의 훈련 | **미실시.** P5a 배포 후 1개월 내 1회 |
| **G-6** | 백업 주기·RPO/RTO 확인 | **미확인.** 대표가 Supabase Dashboard에서 확인 후 §9 갱신 |
| **G-7** | 권한 변경 이력 3년 보관 | **미충족(2년).** §3 갭 — backend-developer 조치 요청 |
| **G-8** | 의존성 취약점 자동 스캔(Dependabot 등) | **없음.** 분기 1회 수기 점검 |
| **G-9** | 파기 배치(pg_cron `private.run_daily_retention_batches()`)의 **실제 등록 여부** | **미확인.** cron 등록은 마이그레이션이 아니라 Dashboard 수동 단계였다. **처리방침 §5·§12가 "매일 1회 자동 파기"를 명시하고 있으므로, 등록되어 있지 않다면 문서와 실제가 어긋난 상태(=그 자체가 위반)다.** → **대표가 Supabase Dashboard에서 `cron.job` 등록 상태를 즉시 확인할 것. 이 문서에서 가장 시급한 확인 항목.** |
| **G-10** | ISMS-P 인증 | **미해당으로 판단**(대표 확정 D-14①). 해당 여부는 §14-3 변호사 검토 |

## 14. 변호사 검토 필요

1. 「개인정보의 안전성 확보조치 기준」상 **회사의 처리자 유형** 및 내부관리계획 수립 의무·항목 축소 적용 여부.
2. **CPO 지정·변경 신고 의무 및 이사회 의결·보고 요건**의 해당 여부(2026-09-11 개정법). 대표이사 겸임의 적법성 포함.
3. 2026-09-11 개정법상 **ISMS-P 의무 인증 대상**의 해당 여부.
4. `audit_log` 2년 보관이 **접속기록 법정 보관 기간**을 충족하는지, 권한 변경 이력 3년 요건과의 관계.

> 위 4건은 **`docs/03-security/legal-review-queue.md`**에 **M-1 / M-2 및 P-9~P-11**로 등재되어 있으며, 기존 항목과 함께 **1회 통합 발주**한다(개별 질의 금지 — 대표 확정 D-14①).
