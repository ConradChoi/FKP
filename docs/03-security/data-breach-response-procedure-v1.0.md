## 1. 이 절차가 다루는 사고 (개정법 '유출등' = 유출 + 분실·도난 + **위조·변조·훼손**)

개정법은 '유출등'에 **위조·변조·훼손**을 포함한다. **밖으로 나간 정황이 없어도 데이터가 훼손된 것만으로 통지·신고 의무가 생길 수 있다.** 이 시스템에서 실제로 개연성 있는 유형은 아래 5가지다.

| # | 시나리오 | 이 시스템에서의 구체적 형태 | 개연성 |
|---|---|---|:---:|
| S-1 | **권한 설정 실수로 인한 노출** | 마이그레이션에서 `grant ... to anon` / RLS 정책 누락 / 뷰에 `select p.*` 사용 → 비로그인 REST로 PII 조회 가능 | **가장 높음** |
| S-2 | **`service_role` 키 유출** | Amplify 환경변수·빌드 로그·클라이언트 번들·GitHub Actions Secret 경유 노출. 이 키는 RLS를 전부 우회한다 | 높음 |
| S-3 | **관리자 계정 탈취** | 관리자 1인이 PII 열람 권한(`has_pii_access`)을 가진다. MFA(AAL2)가 1차 방어 | 중간 |
| S-4 | **훼손 — 배치·마이그레이션 오작동** | 매일 실행되는 파기 배치(`private.run_daily_retention_batches()`)나 수기 SQL이 **파기 대상이 아닌 행을 지우거나 덮어씀** | 중간 |
| S-5 | **수탁자 측 사고** | Supabase / AWS의 사고 통보 수신 | 낮음 |

> **S-1과 S-4가 이 회사의 주 위험이다.** 외부 해킹보다 **우리 손으로 낸 권한 실수·배치 사고**가 훨씬 개연성이 높으므로, 마이그레이션·배치 변경은 그 자체가 사고 트리거로 취급한다.

## 2. 인지 (Detection) — 어떻게 알게 되는가

| 경로 | 실재 여부 |
|---|---|
| 파트너·바이어·외부 제보 (`support@seepn.me`) | **있음** |
| 보호위/KISA/언론/보안연구자의 통보 | **있음(수동)** |
| Supabase Dashboard 로그·이메일 알림 | **있음(수동 확인)** |
| `public.audit_log`(`auth.login_failed`, `auth.access_denied`, `*.contact_reveal`), `private.login_lockout` | **있음 — 단 자동 알림 없음. 사람이 열어봐야 보인다** |
| 오류·이상징후 자동 알림(Sentry 등 APM), 비정상 대량 조회 탐지 | **없음 — 향후 계획(§8 G-1)** |

> **따라서 현재 인지는 사실상 "제보"와 "배포 직후 자기 점검"에 의존한다.** 이 한계를 알고 있어야 §3의 72시간 기산점을 정직하게 잡을 수 있다.

**개인정보취급자의 즉시 보고 의무**: 취급자(관리자 계정 보유자)는 위 유형을 **인지한 즉시(지체 없이) 대표에게 전화 + 이메일로 동시 보고**한다. 확실하지 않아도 보고한다 — **"확인 후 보고"가 72시간을 잡아먹는 가장 흔한 실패 유형**이다.

## 3. 72시간 카운트 시작점 (가장 중요)

> **기산점 = "유출등이 있음을 알게 된 때". 우리 기준으로는 개인정보취급자(대표 포함) 중 누구든 유출등의 사실 또는 그 가능성을 최초로 인지한 시각이다.**

- **대표에게 보고된 시각이 아니다.** 취급자가 화요일에 알고 목요일에 보고했으면, 카운트는 **화요일**부터다.
- **조사가 끝난 시각도 아니다.** 개정법은 "유출 **가능성**"만으로도 통지 의무를 발동시킨다. "확실해지면 그때부터"로 계산하지 않는다.
- **행동 규칙**: 최초 인지자는 그 시각을 **분 단위로 기록**한다(무엇을 보고 그렇게 판단했는지 한 줄 포함). 이 기록이 사후에 72시간 준수를 입증하는 유일한 증거다.
- 72시간 내에 원인·범위가 확정되지 않으면 **확정된 사항만으로 먼저 통지·신고하고, 나머지는 확인되는 대로 추가 통지**한다. **지연 사유는 통지 지연을 정당화하지 못한다.**

**판단 주체**: 통지·신고 여부와 그 범위는 **대표가 단독으로 결정**한다. 대행자는 지정되어 있지 않다 → **대표 부재(해외·이동 중) 시에도 도달 가능한 연락 수단을 상시 유지**하는 것이 이 절차의 전제다(§8 G-2).

## 5. 통지 대상자 추출 · 통지 문안 · 신고

### 5-1. 통지 대상자 추출 — **현재 준비된 쿼리·함수는 없다. 아래를 그대로 쓴다.**

> **중요**: 아래 쿼리는 `auth` / `private` 스키마를 읽으므로 **PostgREST(anon/authenticated)로는 실행 불가**하다. **Supabase Dashboard SQL Editor(대표 계정 로그인)** 또는 `service_role` 접속에서만 실행된다. **대표는 평시에 SQL Editor 접근 경로를 확인해 두어야 한다** — 사고 당일 처음 열어보는 상황이 되면 72시간이 아니라 첫 4시간이 무너진다.

```sql
-- (1) 파트너 로그인 계정 (partner_account에는 email 컬럼이 없다 — auth.users가 SSOT)
select pa.id as partner_account_id, u.email, pa.display_name, pa.status
from public.partner_account pa
join auth.users u on u.id = pa.auth_user_id
where pa.status <> 'withdrawn';

-- (2) 파트너 담당자 (private.partner_contact — 성명·이메일·전화 원문)
select pc.partner_id, pc.contact_name, pc.contact_email, pc.contact_phone
from private.partner_contact pc
join public.partner p on p.id = pc.partner_id;

-- (3) SEEPN 바이어 계정  ※ P5a 배포 이후에만 존재
select ba.id as buyer_account_id, u.email, ba.display_name, ba.status
from public.buyer_account ba
join auth.users u on u.id = ba.auth_user_id
where ba.status <> 'withdrawn';

-- (4) FKP 요청 제출자 (익명화되지 않은 행만)
select r.id, r.contact as email, r.locale, r.created_at
from public.requests r
where r.anonymized_at is null;

-- (5) 관리자
select au.id, u.email, au.status
from public.admin_user au
join auth.users u on u.id = au.auth_user_id
where au.status = 'active';
```

**범위 축소가 필요한 경우**(특정 테이블만 노출된 경우) 위 쿼리에 사고 구간 조건(`created_at`/`updated_at` between 노출 시작~종료)을 덧붙인다. **범위를 좁히지 못하면 넓게 통지한다** — 누락이 과통지보다 위험하다.

**backend-developer 조치 요청 (P5a 착수 시 함께)**
- 위 (1)~(5)를 `private.breach_notification_targets(p_scope text, p_from timestamptz, p_to timestamptz)` **정의자 함수 1개**로 사전 구현할 것. `service_role`에만 grant, `anon`/`authenticated`에는 grant 금지.
- 이 함수 호출 자체를 `audit_log`(`security.breach_target_export`)에 기록할 것. 사고 대응 중의 PII 대량 조회도 감사 대상이다.
- P5a에서 `buyer_account`를 만들 때 **(3)번 쿼리가 성립하도록** `auth_user_id` 컬럼과 `status` 값 집합을 `partner_account`와 동일 shape로 유지할 것.

### 5-2. 통지 방법 — 실무 제약을 먼저 인정한다

현재 회사가 보유한 이메일 발송 수단은 **Supabase Auth의 트랜잭션 메일(가입·비밀번호 재설정)뿐**이며, **대량 통지 메일을 보낼 수단이 없다.** 사고 시에는 아래 순서로 처리한다.

1. 대상자가 **소수(수십 명 이하)**: 대표 계정(jhc@ylia.io)에서 **개별 발송**(수신자 주소는 반드시 BCC — 통지 메일 자체가 2차 유출이 되는 사고가 흔하다).
2. 대상자가 **다수**: 외부 메일 발송 도구를 즉시 계약해 발송한다. **동시에** `seepn.me`와 `findkoreanpartners.com`에 **팝업 또는 상단 배너로 30일 이상 게시**한다.
3. 연락처를 알 수 없는 정보주체가 있는 경우: 홈페이지 게시로 갈음하되, **알 수 있는 사람에게는 반드시 개별 통지**한다.

| 항목 | 내용 |
|---|---|
| 신고처 | **개인정보 포털** `privacy.go.kr` > 개인정보 유출 신고, 또는 **KISA 개인정보침해 신고센터** `privacy.kisa.or.kr` (보호위가 KISA를 접수 전문기관으로 지정) |
| 기한 | 인지 시점부터 **72시간 이내** |
| 신고 대상 기준 | ① 정보주체 **1천 명 이상** ② **민감정보·고유식별정보** 유출 ③ **개인정보처리시스템에 대한 불법적인 접근**에 의한 유출 |
| **우리 판단** | 이 회사는 민감정보·고유식별정보를 수집하지 않고 초기 정보주체 수도 1천 명 미만일 수 있으나, **§1의 S-1~S-3은 대부분 ③(불법적 접근·권한 우회)에 해당할 수 있다.** 따라서 **건수와 무관하게 신고 대상으로 보고 대응**하고, 미해당 판단은 **대표가 근거를 기록으로 남긴 경우에만** 한다 |
| 미신고 시 | 법 제75조에 따른 과태료(3천만원 이하) 대상 |
| 신고 준비물 | 유출 항목, 시점·경위, 정보주체 수, 대응조치, 통지 여부·방법, 담당자 연락처 |

## 6. 기록 보존

- 사고 1건당 파일 1개: `docs/03-security/incidents/YYYY-MM-DD-<slug>.md`
- 필수 기록 항목: **최초 인지 시각·인지자·인지 경로 / 72시간 기산점 / 봉쇄 조치와 실행 시각 / 영향 범위(테이블·건수) / 통지 대상자 수·발송 시각·방법 / 신고 접수번호 / 재발 방지 조치와 완료일**
- 이 기록은 **보호위 조사 시 제출 대상**이며, 사고 대응의 적정성을 입증하는 유일한 자료다. **사후에 정리하지 말고 대응 중에 실시간으로 적는다.**

## 7. 변호사 검토 필요 (실무 판단으로 확정하지 않음)

1. '유출등'에 포함된 **훼손**의 실무 해석 — 우리 파기 배치의 오작동(S-4)이 '훼손'으로서 통지·신고 대상인지.
2. **신고 대상 기준 ③(불법적 접근)**의 범위 — 권한 설정 실수로 anon에게 열려 있었고 실제 조회 흔적이 없는 경우가 여기 해당하는지.
3. 유출 사실을 **처리방침 본문에 별도 조항**으로 둘 필요가 있는지.

> 위 3건은 `docs/03-security/legal-review-queue.md`에 **P-8 / P-11**로 등재되어 있으며 통합 발주 대상이다(개별 질의 금지 — 대표 확정 D-14①).
